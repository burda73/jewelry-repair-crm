# 0007. TLS и маршрутизация — внешний nginx-proxy заказчика

Дата: 2025-09-16
Статус: Принято

## Контекст

Ответ A1: в инфраструктуре заказчика **уже есть отдельный nginx-proxy**, который выдаёт
сертификаты Let's Encrypt и маршрутизирует трафик между сервисами. Развёртывание —
Proxmox VE 7.4, корпоративный домен `remixgold.ru`.

Изначально проект предполагал **собственный** прокси-контейнер nginx с терминированием TLS,
собственными сертификатами и rate limit. Это решение было принято до того, как стало известно
о существующем прокси.

## Рассмотренные варианты

1. **Собственный nginx внутри compose-проекта.** Плюсы: проект самодостаточен, схема
   одинакова у всех. Минусы: **дублирование** уже существующей функции; два места выдачи
   сертификатов (конфликт за порты 80/443 на одном IP невозможен без дополнительных
   настроек); правила безопасности и HSTS расходятся между сервисами; администратор
   заказчика получает вторую точку, которую надо обслуживать и обновлять.

2. **Внешний прокси заказчика, проект публикует только порты.** Плюсы: сертификаты,
   HSTS, протоколы и общесетевые лимиты настраиваются **в одном месте** — там, где уже
   настроены для других сервисов; проект не претендует на порты 80/443; меньше компонентов
   для обновления. Минусы: требуется согласовать схему маршрутизации с администратором;
   корректность зависит от передаваемых заголовков.

3. **Прокси как отдельный сервис перед проектом.** Не рассматривался: усложняет схему
   без выгоды — внешний прокси уже стоит перед хостом.

## Решение

Вариант 2. Проект **не содержит собственного прокси** и не терминирует TLS.
`infra/docker/docker-compose.prod.yml` публикует только `web:3000` и `api:4000`;
трафик направляет существующий nginx-proxy заказчика.

Что это потребовало изменить:

1. **Удалён `infra/docker/nginx/`** (nginx.conf, proxy_params, каталог certs) и сервис
   `proxy` из prod-compose.
2. **`TRUST_PROXY=1`** — обязательная настройка приложения. За прокси `req.ip` иначе
   содержит адрес прокси, и ограничение частоты запросов считает всех клиентов одним
   адресом: несколько неудачных попыток входа одного сотрудника блокируют вход **всей сети**.
   Значение `true` запрещено — IP подделывается заголовком `X-Forwarded-For`.
3. **`X-Forwarded-Proto: https` обязателен** от прокси. Без него приложение считает
   соединение небезопасным и не отдаёт cookies с флагом `Secure` (токены доступа) —
   вход невозможен.
4. **Сеть `internal: true` убрана** у API: ему нужен доступ в локальную сеть для интеграций
   с 1С и IP-АТС. Изоляция достигается тем, что порты БД, Redis и MinIO не публикуются.
5. **Добавлен `infra/proxy/`** — готовый фрагмент конфигурации, файл `repair_proxy_params`
   (справочно: настройка выполняется через UI, см. ниже) и чек-лист проверки.

**Уточнение (ответ A1):** маршрутизация настраивается **через UI** прокси, вероятно
Nginx Proxy Manager. Значит, правка файлов в `conf.d/` не требуется — администратору
передаются параметры для заполнения полей UI: `docs/14-deployment.md` §8. Важная деталь
такого варианта: в Nginx Proxy Manager `client_max_body_size` по умолчанию **1 МБ**, и
загрузка фотографии изделия падает с ошибкой 413. Увеличение лимита до 25 МБ — обязательный
шаг инструкции, а не опциональный.

## Последствия

**Проще:** сертификаты и HSTS в одном месте; проект не занимает 80/443; меньше компонентов;
администратор заказчика применяет привычный ему процесс добавления сервиса.

**Сложнее:** приложение теперь зависит от корректности заголовков прокси — ошибка в
`X-Forwarded-Proto` проявляется как «не могу войти», а не как явная ошибка конфигурации.
Это компенсируется чек-листом в `infra/proxy/README.md` §6, который проверяет именно
вход и работу cookies, а не только HTTP-код 200.

**Явно зафиксировано как зона ответственности заказчика:** выпуск и продление
сертификатов, HSTS, протоколы TLS, общесетевые лимиты запросов, доступ LXC в локальную
сеть к серверам 1С и IP-АТС (см. `docs/14-deployment.md` §7).
