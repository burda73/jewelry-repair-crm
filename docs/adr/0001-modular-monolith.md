# 0001. Модульный монолит вместо микросервисов

Дата: 2025-09-16
Статус: Принято

## Контекст

Система обслуживает до 50 магазинов и 1000+ заказов в месяц — это около 35 заказов в день.
Развёртывание планируется **on-premise** на сервере заказчика, без выделенной команды
эксплуатации и без Kubernetes.

Требования ТЗ включают несколько интеграций (1С, IP-АТС), фоновые задачи (эскалации, очистка
записей, синхронизация) и тесную связность данных: заказ, калькуляция, платежи, согласования
и история статусов изменяются вместе и должны быть согласованы транзакционно.

## Рассмотренные варианты

1. **Микросервисы** (orders-service, payments-service, logistics-service, integration-service).
   Плюсы: независимое масштабирование, изоляция отказов. Минусы: распределённые транзакции
   (saga) для операций, которые сейчас атомарны; нужен service mesh, трассировка, отдельные
   БД или общая БД с распределёнными блокировками; эксплуатация на одном сервере заказчика
   кратно сложнее; команда из 2–3 разработчиков будет тратить время на инфраструктуру,
   а не на бизнес-логику.

2. **Модульный монолит** (NestJS с чёткими границами модулей).
   Плюсы: транзакционная целостность из коробки, одна сборка и один деплой, простой откат,
   минимум инфраструктуры. Минусы: масштабируется целиком (не отдельным модулем), границы
   модулей нужно соблюдать дисциплиной, а не сетью.

3. **Serverless / функции.** Не подходит: on-premise, требование к транзакционности,
   предсказуемая latency, отсутствие облачных сервисов в контуре заказчика.

## Решение

Модульный монолит на NestJS с явными границами модулей и одним процессом для HTTP,
отдельным процессом для воркеров (тот же образ, другая точка входа).

Признаки, при которых решение пересматривается: устойчивая нагрузка выше 5000 заказов в месяц,
появление второй команды, требование независимого релизного цикла для модуля.

## Последствия

**Проще:** транзакции (заказ + платежи + аудит + outbox в одном `$transaction`), отладка,
развёртывание, резервное копирование, найм (один стек, один способ запуска).

**Сложнее:** масштабирование только горизонтальное целиком; требуется дисциплина в границах
модулей — прямые импорты между модулями вместо вызова через сервис запрещены на ревью.

**В будущем:** если понадобится выделить модуль (например, интеграции), процесс уже
подготовлен: адаптеры вызываются через порты, воркеры — отдельный процесс.
