# 0002. Transactional outbox для интеграции с 1С

Дата: 2025-09-16
Статус: Принято

## Контекст

ТЗ п. 2.5 и 2.8 требуют синхронизации предоплат и оплат с 1С (включая ККТ). Приём платежа
происходит в магазине, в присутствии клиента. 1С — внешняя система, которая может быть
недоступна: обновление, сетевая проблема, ошибка конфигурации, плановые работы.

Ключевое требование бизнеса: **приёмщик не должен слышать «подождите, 1С недоступна».**
Оплата должна приниматься всегда.

## Рассмотренные варианты

1. **Синхронный вызов 1С в обработчике платежа.** Просто в реализации, но при недоступности
   1С платёж либо не принимается (блокирует работу магазина), либо теряется (недопустимо
   в финансовом учёте). Отклонено.

2. **Очередь в Redis (BullMQ) без записи в БД.** Плюс: ретраи из коробки. Минус:
   при потере Redis (или сбросе `maxmemory-policy`) задача исчезает безвозвратно вместе
   с фактом необходимости синхронизации. Платёж в БД есть, а в 1С никогда не уйдёт —
   расхождение обнаружится только при инвентаризации. Отклонено как единственный механизм.

3. **Transactional outbox.** Запись о необходимости отправки пишется в ту же транзакцию БД,
   что и платёж. Воркер читает таблицу и отправляет. Плюсы: атомарность (нет платежа без
   задачи на отправку), устойчивость к падению любого компонента, полный аудит попыток.
   Минусы: нужно реализовать воркер, идемпотентность и обработку «мёртвых» записей.

## Решение

Transactional outbox (`IntegrationOutbox`) — источник правды по необходимости синхронизации.
Redis/BullMQ используется только как ускоритель оповещения воркера; при его недоступности
воркер продолжает опрашивать таблицу по расписанию.

Обязательные свойства реализации:
- `idempotencyKey` уникален и передаётся в 1С — повтор не создаёт дубль документа;
- выборка задач через `FOR UPDATE SKIP LOCKED` — несколько воркеров не дублируют отправку;
- экспоненциальная задержка (30 с → 5 мин → 30 мин → 2 ч → 12 ч), после N попыток — `DEAD`
  и алерт администратору;
- ежедневная сверка сумм с 1С, расхождения — отчёт администратору и руководителю.

## Последствия

**Проще:** приём оплаты работает автономно; сбой 1С не блокирует магазины; история попыток
и ошибок доступна администратору в интерфейсе; сверка встроена в процесс.

**Сложнее:** нужно реализовать идемпотентный приём на стороне 1С (требование к 1С-подрядчику);
появляется эксплуатационная обязанность следить за очередью (алерты, действие при `DEAD`);
тестирование требует сценариев отказа 1С.

**В будущем:** тот же механизм переиспользуется для интеграции с АТС и отправки уведомлений —
новые потребители добавляются как новые `eventType`, без изменения схемы.
