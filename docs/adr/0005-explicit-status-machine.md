# 0005. Явная таблица переходов статусов

Дата: 2025-09-16
Статус: Принято

## Контекст

Заказ проходит 14 статусов — от черновика до выдачи, отказа или отмены. ТЗ накладывает
разные условия на разные переходы:
- старт работ заблокирован без предоплаты (п. 2.5);
- выдача только при полной оплате (п. 2.8);
- согласование клиента обязательно перед производством (п. 2.4);
- согласие на запись разговоров при создании заказа (п. 2.4);
- «невостребовано» — ровно через 30 дней (п. 2.8).

Разные роли имеют право на разные переходы. Наивная реализация «поле `status` + проверки
в контроллерах» быстро приводит к тому, что правила размазаны по коду, а фронтенд
и бэкенд расходятся в представлении о том, что разрешено.

## Рассмотренные варианты

1. **Поле `status` без формальной модели.** Проверки в каждом обработчике.
   Минусы: правила дублируются и расходятся; нельзя получить список доступных действий
   без повторения логики; добавить новый статус = найти все места в коде.

2. **Библиотека конечных автоматов** (xstate и подобные). Плюсы: визуализация, готовый
   рантайм. Минусы: ещё одна зависимость; бизнес-условия (предоплата, оплата, согласие)
   всё равно выходят за рамки автомата и живут рядом; сложнее типизировать доменные правила;
   для нашей задачи (22 перехода) оверинжиниринг.

3. **Явная декларативная таблица переходов** в общем пакете, с ролями и кодами условий.

## Решение

Вариант 3. `packages/shared/src/domain/order-transitions.ts` содержит `ORDER_TRANSITIONS` —
массив из 22 правил. Каждое правило описывает:
`id` (совпадает с номером в `docs/04-status-workflow.md` §2), `from`, `to`, `actors`
(роли или `SYSTEM`), `guards` (коды условий), `effects` (побочные эффекты),
`requiresReason`, `label` для UI.

Разделение ответственности:
- **таблица** отвечает на вопрос «разрешён ли переход этой роли при наличии причины»;
- **`OrderWorkflowService`** проверяет `guards`, требующие данных из БД (суммы, согласования,
  партии), и применяет `effects` в одной транзакции;
- **UI** получает доступные действия от сервера (`availableTransitions`) и не дублирует правила.

`packages/shared` не знает о БД и HTTP — только домен. Это позволяет использовать его
и в API, и в веб-интерфейсе, и в тестах без инфраструктуры.

## Последствия

**Проще:** правила в одном месте; новый статус добавляется правкой массива; UI не может
показать несуществующее действие; тестируется без БД; документация синхронизирована
автоматически.

**Сложнее:** разработчик обязан добавлять переход в таблицу И в документ — дисциплина
поддержана тестом `docs-sync.spec.ts`, который падает при расхождении; `effects` выполняются
в сервисе, то есть связь «правило → реализация эффекта» требует внимания на ревью.

**Защита от расхождения кода и документации:** `docs-sync.spec.ts` проверяет, что:
- число и номера переходов в коде совпадают с таблицей в `docs/04-status-workflow.md`;
- каждый статус упомянут в документе;
- русские названия статусов совпадают;
- ни один переход не описан в документе, но отсутствует в коде.

Так документация не может молча устареть — это самая частая проблема проектной документации.

**Тесты:** 23 теста в `order-transitions.spec.ts` проверяют целостность таблицы
(нет дублей, нет переходов из терминальных статусов, все статусы задействованы),
проверки ролей, обязательность причины и корректность списка доступных действий.
