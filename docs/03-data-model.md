# 03. Модель данных

Полная схема — `packages/db/prisma/schema.prisma` (источник правды). Этот документ объясняет
**почему** модель устроена именно так и как читать её при разработке.

## 1. Общие соглашения

| Соглашение | Правило |
|------------|---------|
| Деньги | `*Minor` — целое число в копейках. Валюта — поле `currency` (ISO 4217). `Float`/`Decimal` для денег **запрещены** |
| Вес камней | `Decimal(10,3)` — граммы/караты, точность важна для оценки |
| Время | `timestamptz`, хранение в UTC, отображение в таймзоне магазина |
| Идентификаторы | `cuid()` — неугадываемые, безопасны в URL |
| Человекочитаемые номера | Отдельные поля `orderNo`, `batchNo`, `actNo`, `claimNo` — генерируются через `Counter` в одной транзакции |
| Квитанция | `Order.qrPayload` (уникален) — содержимое QR-кода `repair://order/{orderNo}`; `receiptPrintCount`, `receiptLastPrintedAt` — учёт перепечаток (ответ A4, §6.14) |
| Версионируемые справочники | `PriceListVersion`, `StageNorm` — утверждённая версия неизменяема, изменения = новая версия |
| Простые справочники | `Store`, `Workshop`, `Performer`, `WorkCategory`, `StoneType` — НЕ версионируются: запись можно изменить, но нельзя удалить, если на неё ссылаются документы. Вывод из обращения — `isActive = false`; запись остаётся в истории заказов и прейскуранта, но исчезает из выбора (задача 1.3.1) |
| Нормативы этапов | `StageNorm` — **версионируемый** справочник (как `PriceListVersion`): правка создаёт новую версию, прежняя остаётся в истории, чтобы объяснить сроки уже принятых заказов. Версия — ПОЛНЫЙ набор, а не отдельная строка: уникальность `[version, stage, workType]` не позволяет собрать действующую версию из нескольких. Привязан к ЭТАПУ (`NORM_STAGE`), а не к статусу: соответствие задаёт `stageForStatus()`. `workType` не `NULL`, а `ANY`, потому что в PostgreSQL NULL в уникальном индексе не обеспечивает уникальность, — общий норматив `ANY` и есть запасной вариант для нераспознанной сложности (задача 1.3.4, «Дефект 26») |
| Рабочий календарь | `WorkingCalendar` — хранит **только исключения** (праздник, объявленный рабочим, перенос, особые часы); обычные рабочие дни и праздники ТК РФ вычисляются кодом (`isStateHoliday`), а не хранятся строками. Строка-зеркало, повторяющая обычное правило, перекрывает праздник и поэтому отклоняется API (`CALENDAR_REDUNDANT_DAY`). Приоритет: исключение из базы → праздник → день недели. Запись можно снять (`DELETE`): внешних ключей на таблицу нет, а «отключить дату» смысла не имеет (задача 1.3.3, «Дефект 25») |
| Аудит | `AuditLog` — append-only; у приложения нет прав `UPDATE`/`DELETE` на таблицу |

## 3. Пояснения по ключевым сущностям

### 3.1. Order — корневой агрегат
Заказ содержит **денормализованные денежные итоги** (`worksTotalMinor`, `stonesTotalMinor`,
`totalAmountMinor`, `paidAmountMinor`). Это осознанное решение: итоги нужны в списках и
отчётах постоянно, а пересчёт из дочерних строк на каждый запрос — дорого. Итоги
пересчитываются в той же транзакции, что и изменение строк, функцией
`recalculateOrderTotals(orderId)`. Инвариант проверяется тестом и ночным job-ом сверки.

Поле `version` — оптимистичная блокировка. Обновление выполняется как
`UPDATE ... WHERE id = ? AND version = ?`; при 0 затронутых строк → `409 Conflict`.

### 3.2. Деньги в заказе
```
totalAmountMinor = worksTotalMinor + stonesTotalMinor - discountMinor
paidAmountMinor  = SUM(Payment.amountMinor) WHERE status = 'CONFIRMED' AND kind != 'REFUND'
```

Два независимых условия, оба проверяются на сервере:
- **старт работ:** `paidAmountMinor >= prepaymentRequiredMinor` (ТЗ п. 2.5);
- **выдача:** `paidAmountMinor >= totalAmountMinor` (ТЗ п. 2.8).

### 3.3. Фиксация цены на момент приёма (ТЗ п. 2.2)
`OrderWork` хранит **копию** цены (`unitPriceMinor`) и ссылку на `PriceListItem`.
Ссылка нужна для аналитики («какие работы популярны»), копия — для юридической корректности
(«сколько клиент видел на бумаге»). Пересмотр прейскуранта не затрагивает принятые заказы.
Аналогично `Order.priceListVersionId` фиксирует, по какой версии считали.

#### 3.3.1. Цена зависит от металла изделия

Утверждённый прейскурант заказчика задаёт для каждой услуги **две цены** — по золоту
и по серебру (см. [ADR 0009](adr/0009-price-by-metal.md)). Металл сданного изделия
выбирает колонку, поэтому цена — функция от пары (позиция, металл):

```
PriceListItem ──< PriceListItemRate (metal, priceMinor, isFrom)
      │
      └── priceMinor — цена по умолчанию, для позиций без разбивки по металлам
```

Выбор ставки выполняет `resolveItemPrice(item, metal)` из `@app/shared` — **одна и та же
функция на сервере и в интерфейсе**. Она же нормализует металл: принимает код (`SILVER`)
и свободный текст («Серебро 925», «Ag925»), поскольку в `Item.metal` металл хранится
текстом, введённым приёмщиком. Если металл не распознан, возвращается цена по умолчанию
с признаком `usedFallback`, и интерфейс обязан предупредить приёмщика.

Три признака позиции, которые нельзя терять:
- `PriceListItem.priceFrom` / `PriceListItemRate.isFrom` — цена «от» (минимальная),
  5 позиций в документе. Итог подлежит уточнению.
- `PriceListItem.metalCostSeparate` — стоимость металла в цену не входит, считается
  отдельно, 3 позиции. Без признака работа посчиталась бы как полная стоимость.
- `PriceListItem.unit = 'грамм'` — тарификация по весу, 3 позиции (родирование, золочение).

**Признак «от» определяется по ячейке цены, а не по названию.** В позиции 6
(«...классического кольца **от 0,5 размера**...») слово «от» относится к размеру,
а цена фиксированная. Это проверяется тестом `packages/db/prisma/price-list-spec.spec.ts`.

`OrderWork.itemId` привязывает работу к конкретному изделию: в заказе из золотого кольца
и серебряной цепочки цена подбирается по металлу своего изделия. Индекс изделия приходит
в API полем `itemIndex` (0 по умолчанию).

**Сервер проверяет присланную цену** по действующему прейскуранту и отвечает
`409 PRICE_MISMATCH` при расхождении, кроме нетиповых работ (`isCustom`), цена которых
назначается сотрудником. Без этой проверки цену можно было занизить правкой запроса.

Источник данных прейскуранта — `packages/db/prisma/price-list-spec.ts` (24 позиции,
перенесены из `docs/reference/Прейскурант-Ремонт-утверждённый.docx`), сверяется с
`docs/reference/price-list-baseline.json`. Для развёрнутых баз —
идемпотентный `npx tsx packages/db/prisma/apply-price-list.ts`.

### 3.4. Корректировки (ТЗ п. 2.3)
`CalcAdjustment` хранит «до/после/дельта» и **обязательную** причину. Сумма заказа меняется
только через корректировку — прямой правки `totalAmountMinor` из API не существует, иначе
причина правки терялась бы, и в истории осталось бы необъяснимое изменение суммы.

`amountBeforeMinor` и `deltaMinor` вычисляет **сервер**: если принять «было» от клиента,
в истории окажется сумма, которой в заказе не было. Цель (`targetId`) проверяется на
принадлежность заказу — чужой идентификатор отдаёт `404`.

**Знак скидки.** `discountMinor` — это `работы + камни − итог`, поэтому он может быть
**отрицательным**: согласованная с клиентом сумма бывает больше суммы строк (надбавка за
срочность или сложность). Обнулять скидку и присваивать итог напрямую нельзя — инвариант
§3.2 сломается, и ночная сверка даст расхождение. Разницу считает `discountForTotal`,
итог — всегда `calcOrderTotal`; для интерфейса знак трактует `describeDiscount`
(«Скидка» со знаком «−» либо «Надбавка» со знаком «+»).

**Запрет на уменьшение ниже внесённого.** Корректировка, опускающая итог ниже
`paidAmountMinor`, отклоняется с `409 ADJUSTMENT_BELOW_PAID`: это фактически возврат денег,
а он оформляется операцией `REFUND` с фиксацией кассира и кассы. Иначе получился бы заказ,
где «оплачено» больше «итога».

### 3.5. Согласования (ТЗ п. 2.4)
`Approval` фиксирует канал связи. Для устного согласия:
`channel = PHONE_VERBAL`, `isVerbal = true`, обязательны `createdById` (кто получил согласие),
`amountMinor`, `termDays`, `approvedAt`. UI показывает бейдж «Согласовано устно».

**`isVerbal` и `promisedAt` вычисляет сервер, а не принимает от клиента.** `isVerbal` —
следствие канала (`channel === 'PHONE_VERBAL'`); отдельным флагом его можно было бы прислать
как `channel: SMS, isVerbal: true` и получить бейдж «согласовано устно» без устного
разговора. `promisedAt` считается как `addWorkingDays(сейчас, termDays)` по производственному
календарю — присланную дату можно поставить на выходной или задним числом, и нормативы
этапов (ТЗ п. 2.7) посчитали бы дедлайн неверно. `approvedAt` заполняется только при
`result = APPROVED`: у ответа «не дозвонились» момента согласия не существует.

**Согласование суммы создаёт корректировку.** Если согласованная сумма отличается от суммы
заказа, сервер фиксирует `CalcAdjustment` (§3.4) с причиной «Согласование с клиентом (канал)»
и приводит `totalAmountMinor` к согласованной сумме. Иначе сумма заказа и согласованная сумма
разошлись бы молча, а клиент подтвердил именно вторую.

Переход `AWAITING_APPROVAL → AWAITING_PREPAYMENT` заблокирован guard-условием
`APPROVAL_EXISTS`, которое считает **только** согласования с `result = APPROVED`:
отказ клиента или «не дозвонились» переход не открывают.
Требование ТЗ «обязательный пункт заявки о записи разговоров» реализовано как
`Customer.consentCallRecording` — без `true` заказ не создаётся (guard перехода #1).

### 3.6. Записи звонков (ТЗ п. 2.4)
`CallRecording.externalId` уникален → повторный импорт того же CDR не создаёт дубликат.
`retainUntil = startedAt + 1 год`; воркер `recording-retention` удаляет и запись, и объект
в S3 по достижении даты. Привязка к заказу — автоматическая (см. `docs/05-integrations.md` §2)
с сохранением `matchedBy` и `matchScore`, плюс возможность ручной привязки.

### 3.7. Платежи (ТЗ п. 2.5, 2.8)
- `storeId` — **где фактически внесён** платёж, а не магазин заказа: ТЗ прямо требует приём
  «в любом магазине по номеру заказа».
- `idempotencyKey` уникален — защита от дублей.
- `kind = REFUND`/`REVERSAL` уменьшают `paidAmountMinor`; сторно не удаляет исходный платёж,
  а ссылается на него через `reversedById` (финансовый след сохраняется).
- Синхронизация с 1С: `syncStatus`, `externalId`, ошибки в `syncError`. Пока 1С недоступна,
  платёж существует в системе со статусом `PENDING` синхронизации.

### 3.8. Исполнители производства (решение заказчика)
`Performer` — **не** `User`. У ювелира нет учётной записи. Менеджер производства создаёт
`OrderAssignment`, указывая исполнителя. Загрузка производства считается по
`OrderAssignment.plannedHours` и `PriceListItem.durationHours`.

### 3.9. Разграничение по магазинам (ответ на вопрос 4 ТЗ)
`UserStore` задаёт магазины пользователя, `UserRole.scope` — область видимости роли.
Приёмщик: `scope = STORE_PLUS_GLOBAL_SEARCH` → основная выборка ограничена его магазинами,
но поиск по **точному** номеру заказа ищет глобально (нужно для приёма оплаты в чужой точке).

### 3.10. AuditLog
Поля `before`/`after` — `jsonb`-снимки только изменённых полей (не всей сущности).
`reason` обязателен для действий `ADJUST`, `CANCEL`, `REVERSE`. Индексы по
`(entity, entityId)`, `(actorId, createdAt)`, `(createdAt)`.

## 4. Индексы и почему они такие

| Индекс | Обслуживает запрос |
|--------|--------------------|
| `Order(status, dueAt)` | Дашборд просрочек, воркер эскалаций |
| `Order(createdStoreId, status)` | Список заказов магазина с фильтром |
| `Order(customerId)` | История клиента |
| `Order(productionManagerId, status)` | Рабочий список менеджера производства |
| `OrderStatusHistory(orderId, createdAt)` | Лента истории в карточке |
| `Payment(orderId, status)` | Пересчёт `paidAmountMinor` |
| `Payment(storeId, paidAt)` | Отчёт по предоплатам и выручке точки |
| `Payment(syncStatus)` | Воркер синхронизации с 1С |
| `CallRecording(phoneFrom, startedAt)`, `(phoneTo, startedAt)` | Сопоставление звонка с заказом |
| `CallRecording(retainUntil)` | Воркер удаления по сроку хранения |
| `IntegrationOutbox(status, nextRetryAt)` | Выборка готовых к отправке |
| `Notification(userId, status)` | Колокольчик уведомлений |
| `WarrantyClaim(status, dueAt)` | Контроль 10-дневного срока рассмотрения |

Полнотекстовый поиск по ФИО/телефону: `pg_trgm` + GIN-индексы на `Customer.fullName`
и `Customer.phoneNormalized` (добавляются отдельной миграцией с `CREATE EXTENSION pg_trgm`).

## 5. Миграционная стратегия

1. Изменения только обратно совместимые: `add column (nullable) → backfill → switch code → drop`.
2. Каждая миграция проверяется на копии продовых данных в CI (`migrate diff` + прогон на дампе).
3. Тяжёлые операции (`CREATE INDEX`) — через `CONCURRENTLY`, отдельной миграцией.
4. `prisma migrate deploy` выполняется до старта новой версии API, отдельным шагом.

## 6. Генерация номеров

Все номера генерируются в одной транзакции через `Counter` с `SELECT ... FOR UPDATE`:

| Сущность | Формат | Пример |
|----------|--------|--------|
| Заказ | `{КодМагазина}-{ГГ}{ММ}-{6 цифр}` | `MSK1-2509-000142` |
| Партия | `П-{ГГ}{ММ}{ДД}-{3 цифры}` — дата **плановая**, не создания (`docs/07` §8.2) | `П-250915-004` |
| Акт приёма-передачи | `АПП-{ГГ}-{6 цифр}` | `АПП-25-000118` |
| Акт отказа | `АО-{ГГ}-{6 цифр}` | `АО-25-000007` |
| Рекламация | `РЕК-{ГГ}-{5 цифр}` | `РЕК-25-00031` |

Формат заказа содержит код магазина — приёмщик сразу видит точку приёма, а поиск по номеру
работает глобально без дополнительных условий.
