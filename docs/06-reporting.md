# 06. Отчётность (ТЗ п. 2.11)

Все отчёты строятся **на сервере**, SQL-агрегатами. Клиент получает готовые числа и не
выполняет вычислений. Каждый отчёт фильтруется по области видимости роли (приёмщик видит
свой магазин, руководитель — всю сеть).

## 1. Сроки по этапам

**Вопрос бизнеса:** где мы теряем время и укладываемся ли в нормативы?

Источник — `OrderStatusHistory` (`durationMinutes` на каждый переход).

| Метрика | Формула |
|---------|---------|
| Среднее время этапа | `AVG(durationMinutes)` по этапу за период |
| Медиана | `percentile_cont(0.5)` — устойчива к выбросам |
| 90-й перцентиль | `percentile_cont(0.9)` — показывает «хвост» проблемных заказов |
| Доля в норме | `COUNT(duration <= norm) / COUNT(*)` |
| Число нарушений | `COUNT(duration > norm)` |

**Разрезы:** этап, магазин, вид ремонта (простой/сложный), исполнитель производства, период.
**Визуализация:** таблица «этап × метрика» + столбчатая диаграмма «план/факт» по этапам.

## 2. Загрузка производства

**Вопрос бизнеса:** справляется ли цех, не пора ли нанимать ювелира?

| Метрика | Формула |
|---------|---------|
| Заказов в работе | `COUNT(Order WHERE status IN (IN_PRODUCTION, REWORK))` |
| Плановая трудоёмкость | `SUM(OrderWork.durationHours)` по активным заказам |
| Фактическая трудоёмкость | `SUM(assignment.finishedAt - startedAt)` |
| Загрузка исполнителя | `плановые часы / доступный фонд часов` за период |
| Очередь по цехам | число заказов, ожидающих назначения (`QUEUED_FOR_DISPATCH`) |
| Средний срок производства | `AVG(productionFinishedAt - productionStartedAt)` |
| Пропускная способность | `COUNT(заказов завершено) / период` |

**Разрезы:** цех, исполнитель, специализация, период.
**Индикатор перегрузки:** загрузка > 90 % — красный, 70–90 % — жёлтый, < 70 % — зелёный.

## 3. Просрочки

**Вопрос бизнеса:** кто и где систематически нарушает сроки?

| Метрика | Формула |
|---------|---------|
| Просрочено сейчас | `COUNT(Order WHERE dueAt < now() AND status NOT IN терминальные)` |
| Просрочено за период | `COUNT` заказов, у которых был хотя бы один просроченный этап |
| Средняя просрочка | `AVG(now() - dueAt)` по просроченным |
| Максимальная просрочка | `MAX(now() - dueAt)` — «худший случай» |
| Доля просроченных | `просрочено / всего за период` |
| Просрочки по этапам | распределение по статусу, где возникла просрочка |

**Разрезы:** магазин, цех, этап, ответственный сотрудник, период.
**Действие:** переход из отчёта в список конкретных заказов (клик по числу → отфильтрованный список).
**Регламент:** руководителю — ежедневная сводка, если доля просрочек > 5 %.

## 4. Выручка

**Вопрос бизнеса:** сколько заработали и на чём?

| Метрика | Формула |
|---------|---------|
| Выручка | `SUM(Payment.amountMinor) WHERE status=CONFIRMED AND kind != REFUND` |
| Возвраты | `SUM` по `kind IN (REFUND, REVERSAL)` |
| Чистая выручка | выручка − возвраты |
| Средний чек | `выручка / COUNT(DISTINCT orderId)` |
| Выручка по видам работ | `SUM(OrderWork.amountMinor)` по категориям |
| Маржинальность | `(выручка − SUM(costMinor)) / выручка` (если заполнена себестоимость) |
| Структура оплат | доля наличных / карты / перевода |
| Дебиторка | `SUM(totalAmountMinor − paidAmountMinor)` по незакрытым заказам |

**Разрезы:** период (день/неделя/месяц/год), магазин, вид работ, категория клиента (обычный/гарантийный).
**Важно:** выручка считается **по дате платежа**, а не по дате заказа — иначе отчёт не сойдётся с 1С.

## 5. Предоплаты

**Вопрос бизнеса:** сколько денег клиентов у нас «в работе» и нет ли зависших заказов?

| Метрика | Формула |
|---------|---------|
| Внесено предоплат | `SUM(amountMinor) WHERE kind=PREPAYMENT` |
| Зачтено | предоплаты по заказам, дошедшим до `COMPLETED` |
| Зависло | предоплаты по заказам в `AWAITING_PREPAYMENT`/`ACCEPTED` дольше норматива |
| По магазинам внесения | `GROUP BY Payment.storeId` — важно, т.к. платят не там, где заказали |
| Возвращено | `SUM WHERE kind=REFUND` |
| Средний размер предоплаты | `AVG(amountMinor)` |
| Заказы без предоплаты, где она требовалась | контроль нарушений блокировки |

**Особый контроль:** заказы, где предоплата внесена, но работы не начаты более 14 дней —
потенциальная потеря клиента.

## 6. Единый подход к реализации

### 6.1. Структура эндпоинта
```
GET /reports/{name}?from=2025-09-01&to=2025-09-30&storeId[]=...&groupBy=store&format=json
```

Ответ:
```json
{
  "meta": { "from": "...", "to": "...", "generatedAt": "...", "cached": false, "rowCount": 42 },
  "columns": [
    { "key": "stage", "title": "Этап", "type": "string" },
    { "key": "avgHours", "title": "Среднее, ч", "type": "duration" },
    { "key": "inNormShare", "title": "В норме, %", "type": "percent" }
  ],
  "rows": [ { "stage": "PRODUCTION_SIMPLE", "avgHours": 62.4, "inNormShare": 0.87 } ],
  "totals": { "ordersCount": 412 }
}
```

Единый формат `columns` + `rows` позволяет фронтенду рендерить **любой** отчёт одной
табличной компонентой, а экспорт в XLSX делать универсально — без кода под каждый отчёт.

### 6.2. Кэширование
| Тип отчёта | TTL кэша | Инвалидация |
|------------|----------|-------------|
| Просрочки, дашборд | 5 мин | по событию статуса |
| Загрузка производства | 15 мин | по расписанию |
| Сроки по этапам | 1 час | — |
| Выручка, предоплаты | 15 мин | по событию платежа |
| Годовые срезы | 24 часа | — |

Ключ кэша включает `userId`-scope (набор магазинов), иначе приёмщик увидит чужие данные из кэша.

### 6.3. Производительность
- Агрегаты считаются SQL-запросами с индексами, описанными в `docs/03-data-model.md`.
- Для годовых срезов — материализованные представления `mv_revenue_daily`,
  `mv_stage_durations`, обновляемые ночью и по требованию.
- Тяжёлые отчёты (год, вся сеть) выполняются асинхронно: `POST` создаёт задачу,
  клиент опрашивает статус, готовый файл отдаётся ссылкой. Порог — оценка > 5 с.
- Отчётные запросы по возможности идут на **реплику** БД, чтобы не мешать операционной работе.

### 6.4. Экспорт
XLSX (основной, с форматированием и итогами) и CSV (для выгрузки в другие системы).
Экспорт уважает права: пользователь не может выгрузить то, что не видит на экране.
Каждая выгрузка персональных данных фиксируется в аудите.

### 6.5. Дашборд руководителя
Один экран с ключевыми числами: заказов в работе, просрочено, выручка за месяц,
предоплаты в работе, средний срок ремонта, загрузка цеха, рекламации в работе.
Каждый блок кликабелен и ведёт в соответствующий отчёт или список.

## 7. Сверка с 1С

Отдельный отчёт — **не для бизнеса, а для контроля интеграции**:

| Проверка | Условие расхождения |
|----------|---------------------|
| Суммы за день | `SUM(Payment)` в ИС ≠ `SUM(документов)` в 1С |
| Количество документов | число платежей ИС ≠ число документов 1С |
| Зависшие в outbox | `status=PENDING` дольше 1 часа |
| Отклонённые | `status=DEAD` — требуют вмешательства администратора |

Расхождения → уведомление администратору и руководителю, разбор в тот же день.
Это критично: без сверки ошибка интеграции обнаружится только при инвентаризации.
