Документ фиксирует ответы заказчика и принятые проектные решения. Он имеет приоритет над
`tz.md` в случае расхождений: ТЗ описывает требования, здесь — **как** они реализуются.

## 2. Уточнение ролевой модели (изменение относительно ТЗ п. 2.10)

ТЗ перечисляет 6 ролей, включая «Мастер-ювелир». По результатам двух раундов уточнений:

| Роль в ТЗ | Решение | Обоснование |
|-----------|---------|-------------|
| Приёмщик магазина | Оставляем | Рабочая роль точки приёма |
| Менеджер производства | Переименована в **«Менеджер обработки поступающих ремонтов»** (`PRODUCTION_MANAGER`) | Единственная точка контакта с производством и ювелирами; **ответственный по всем вопросам приёмки** |
| Мастер-ювелир | **Исключена из пользователей** | Доступ в систему не нужен; учитывается как исполнитель в назначении работ |
| Логист / курьер | Оставляем | Партии, акты, статус «в пути» |
| Руководитель | Оставляем | Утверждение прейскуранта, эскалации, отчётность |
| Администратор | Оставляем | Пользователи, права, справочники, аудит |
| — | **Добавлена: «Кассир/бухгалтер точки»** (`CASHIER`) | ТЗ п. 2.5 и 2.8 требуют приём оплаты и работу с ККТ; совмещение с приёмщиком возможно, но право отделяемое |
| — | **Добавлена: «Наблюдатель/аудитор»** (`AUDITOR`) | ТЗ п. 4 требует журнал действий; отдельная read-only роль для контроля без права правки |
| — | **Добавлена: «Главный бухгалтер»** (`CHIEF_ACCOUNTANT`) | Ответ A2: главбух **соутверждает прейскурант**. Имеет право `pricelist:approve` и доступ к финансовой отчётности |

**Итого 8 ролей.** Главный бухгалтер — новая роль по результату уточнения A2. Ему доступны:
утверждение прейскуранта, отчёты «Выручка» и «Предоплаты», реестр платежей, аудит —
но **не** операционная работа с заказами (приём, статусы, калькуляция).

## 3. Технологический стек

| Слой | Выбор | Почему |
|------|-------|--------|
| Язык | TypeScript (strict) | Единый язык фронта и бэка, общие типы домена |
| Frontend | Next.js (App Router) + React + PWA | SSR для быстрой первой отрисовки, PWA из коробки, мобильная адаптация |
| Backend | NestJS | Модульная структура под интеграции (1С, АТС), DI, guards для RBAC, очереди |
| БД | PostgreSQL 16 | Транзакционность платежей, `jsonb` для гибких полей, оконные функции для отчётности |
| ORM | Prisma | Типобезопасность, миграции, единая схема как источник правды |
| Очереди | Redis + BullMQ | Эскалации, синхронизация с 1С, отправка уведомлений, ретраи |
| Хранилище файлов | S3-совместимое (MinIO on-premise) | Фото изделий, записи звонков (1 год хранения) |
| Аутентификация | JWT (access + refresh), Argon2id | Простая ролевая модель, работа из любой точки |
| Мониторинг | Prometheus + Grafana + Loki | On-premise, без внешних зависимостей |
| Пакетный менеджер | npm workspaces (монорепо) | Работает в текущем окружении без установки pnpm; заменяется на pnpm одной строкой |

**Отклонение:** изначально предполагался pnpm, но в целевом окружении он не установлен.
Выбран `npm workspaces` — эквивалентен по возможностям для монорепо, требует только Node.
Если команда предпочитает pnpm — достаточно добавить `pnpm-workspace.yaml` и `packageManager`.

## 4. Инфраструктура и масштаб

### 4.1. Сервер (ответ A1)

| Параметр | Значение |
|----------|----------|
| Виртуализация | **Proxmox VE 7.4** (on-premise) |
| Домен | **remixgold.ru** (корпоративный) |
| TLS | **Внешний nginx-proxy заказчика** — выдаёт сертификаты Let's Encrypt |
| Развёртывание | **Docker Compose в LXC** — вложенный Docker разрешён (ответ A1) |
| Роутинг | Существующий nginx-proxy, настройка **через UI**; проект **не содержит собственного прокси** |
| База данных | **Существующий PostgreSQL 16 предприятия** — свой **не устанавливаем** |

**Практические следствия:**
- **TLS, HSTS и общесетевые правила — зона ответственности прокси заказчика.** Проект
  публикует `web:3000` и `api:4000`, прокси направляет на них трафик. Пошаговая инструкция
  для настройки через UI (поля, сертификат, обязательные заголовки) — `docs/14-deployment.md` §8;
  технические детали — `infra/proxy/README.md`.
  Преимущество: сертификаты настраиваются в одном месте, а не дублируются в каждом сервисе.
- **`client_max_body_size` в прокси нужно поднять до 25 МБ.** По умолчанию (1 МБ в Nginx
  Proxy Manager) загрузка фотографии изделия падает с ошибкой 413.
- **`TRUST_PROXY=1` обязателен.** За прокси `req.ip` без этой настройки был бы адресом
  прокси, и ограничение частоты запросов заблокировало бы вход **всей сети** после
  нескольких неудачных попыток одного сотрудника. Значение `true` использовать нельзя:
  IP подделывается заголовком `X-Forwarded-For`.
- **PostgreSQL внешний — сервер общий с 1С и другими системами.** Отсюда два ограничения:
  пул соединений приложения лимитирован (`DATABASE_POOL_SIZE`), чтобы не занять все
  соединения сервера; резервное копирование БД выполняет администратор БД —
  **система копирования уже организована и настроена** на отдельном сервере PostgreSQL.
  Подготовка базы, расширения, права и бюджет соединений — `infra/db/README.md`;
  проверка готовности перед деплоем — `infra/db/preflight.sh`.
- **Резервное копирование файлов** (фото, записи, PDF) — **наша зона**: выгрузка во внешнее
  хранилище. Копирование БД настроено на отдельном сервере; остаётся подтвердить, охвачен
  ли **PITR** (иначе фактический RPO = интервал между дампами, а не 5 минут) и проводилась
  ли **проверка восстановлением** (`infra/db/README.md` §5.1).
- **Внутренние имена:** серверы 1С и IP-АТС резолвятся во внутренней сети — интеграции
  идут напрямую; доступ LXC к ним **подтверждён** (ответ A1).
- **Docker и LXC:** вложенный Docker разрешён (ответ A1), поэтому выбран Docker в LXC.
  Вариант без Docker сохранён как резервный — `docs/14-deployment.md` §6.

### 4.2. Масштаб

- **Масштаб:** проектируем на рост от «до 10 магазинов / до 500 заказов в месяц» до
  «10–50 магазинов / 1000+ заказов в месяц».
- **Практический вывод:** одной виртуальной машины достаточно для старта, но архитектура
  сразу разделяется на stateless API (масштабируется горизонтально), БД с возможностью
  реплики для отчётности, Redis для очередей и S3 (MinIO) для файлов.
  Преждевременного усложнения (микросервисы, Kafka, шардирование) **не делаем**.

## 5. Границы MVP (1-й этап)

Входит:
- аутентификация, RBAC по 8 ролям, разграничение по магазинам;
- справочники: магазины, цеха, клиенты, исполнители производства;
- заказы: регистрация, карточка, поиск, история статусов;
- прейскурант с версионностью и утверждением руководителем;
- калькуляция (работа + камни) с фиксацией причины корректировки;
- согласования, включая «согласовано устно»;
- предоплата (без 1С — ручная фиксация) и блокировка старта работ;
- аудит действий пользователя;
- адаптивный PWA-интерфейс.

Не входит в MVP (см. `docs/09-roadmap.md`):
- логистика и партии (этап 2);
- интеграция с 1С (этап 3);
- интеграция с IP-АТС (этап 4);
- отчётность и дашборды (этап 5);
- гарантия и рекламации (этап 6);
- SMS-уведомления и личный кабинет клиента.

## 6. Ключевые проектные решения

1. **Заказ — агрегат.** Все дочерние сущности (строки калькуляции, платежи, согласования,
   история статусов) изменяются только вместе с заказом, в одной транзакции, с записью в аудит.
2. **Цена фиксируется в момент приёма.** Прейскурант версионируется; в заказ копируются
   `priceMinor` и ссылка на версию. Пересмотр цен не меняет уже принятые заказы (ТЗ п. 2.2).
3. **Статус — конечный автомат.** Переходы описаны явно и валидируются на сервере;
   фронтенд не может перевести заказ в произвольный статус (см. `docs/04-status-workflow.md`).
4. **Деньги — целые числа.** Все суммы хранятся в минорных единицах (`Int`/`BigInt` в копейках)
   с указанием валюты. Никаких `Float` для денег.
5. **Дедлайны вычисляются, а не вводятся.** При переходе в статус система проставляет
   `dueAt` по нормативу этапа из справочника `StageNorm`. Значения нормативов **редактируются
   без выпуска новой версии приложения** (см. §6.11).
6. **Аудит неизменяем.** Журнал действий — append-only таблица с `actorId`, `entity`,
   `entityId`, `before`/`after` в `jsonb`. Обновление и удаление записей запрещены на уровне
   прав БД.
7. **Интеграции — через адаптеры.** 1С и АТС подключаются через интерфейсы
   `AccountingPort` и `TelephonyPort` с in-memory реализациями для MVP и тестов.
8. **Файлы не хранятся в БД.** БД держит метаданные и ключ объекта в S3.
9. **Идемпотентность приёмки платежей.** Каждый платёж имеет `idempotencyKey` — защита от
   двойного нажатия и от повторной доставки вебхука из 1С.
10. **Все сроки считаются в рабочем календаре.** «10 рабочих дней» для рекламации и
    нормативы этапов учитывают выходные/праздники (`WorkingCalendar`).

### 6.11. Нормативы сроков: стартовые значения (ответ A3)

**Проблема:** ТЗ п. 2.7 требует эскалаций по нормативам, но утверждённых нормативов у
заказчика **нет**. Без нормативов система не сможет сигнализировать о просрочке —
а это одна из главных целей проекта (ТЗ §1.2: «контроль сроков на каждом этапе»).

**Решение:** внедряем **стартовые нормативы** на основе отраслевой практики.
Руководитель корректирует их по фактическим данным **в течение первого месяца пилота**.
Нормативы живут в справочнике `StageNorm` и правятся через интерфейс администратора
**без участия разработчика** — это прямое требование к гибкости настройки.

| Этап | Стартовое значение | Обоснование |
|------|--------------------|-------------|
| Согласование клиента | 3 рабочих дня | Клиенту нужно время подумать |
| Ожидание предоплаты | 5 рабочих дней | После — напоминание приёмщику |
| Очередь на отправку | 24 рабочих часа | Партия формируется ежедневно |
| Доставка в цех | 8 рабочих часов | Один рабочий день |
| Производство: простое | 5 рабочих дней | Пайка, полировка, изменение размера |
| Производство: сложное | 15 рабочих дней | Реставрация, литьё, перезакрепка |
| Доставка в магазин | 8 рабочих часов | Один рабочий день |
| Хранение до выдачи | 30 календарных дней | Прямо указано в ТЗ п. 2.8 |
| Рассмотрение рекламации | 10 рабочих дней | Прямо указано в ТЗ п. 2.9 |

**Важно для приёмки:** стартовые значения — это **экспертная гипотеза, а не требование**.
Отдельным пунктом приёмки фиксируется: руководитель может изменить любое значение
в интерфейсе, и эскалации немедленно начинают работать по новым срокам. Если значения
окажутся неверными — это не дефект системы, а настроечный параметр.

**Что делать с уже принятыми заказами при изменении норматива:** `dueAt` **не**
пересчитывается задним числом — иначе отчётность по срокам станет недостоверной.
Новый норматив применяется только к заказам, которые войдут в этап после изменения.

### 6.12. Формат номера заказа (ответ A4)

Действующего формата нет, поэтому выбираем сами. Формат:

```
{КОД_МАГАЗИНА}-{ГГ}{ММ}-{6 цифр}     пример: MSK1-2509-000142
```

Обоснование выбора:
- **Префикс магазина** — приёмщик и клиент сразу видят точку приёма;
- **Год и месяц** — облегчает сортировку, архивирование и разговор по телефону
  («заказ от сентября»);
- **6 цифр** — запас на 999 999 заказов в месяц на магазин, переполнение невозможно;
- **Только ASCII и дефис** — безопасно для QR-кода, штрих-кода, URL и поиска.

Номер **не связан** с 1С: по ответу A4 в 1С фиксируется только факт оплаты, сквозная
нумерация документов не требуется. В `ЧекККМ` номер заказа передаётся в комментарии —
это обеспечивает трассировку без жёсткой связи.

### 6.13. Интеграция с 1С упрощается до фиксации оплаты (ответ A4)

**Существенное упрощение относительно первоначального плана.** Ответ A4: в 1С достаточно
фиксировать **факт оплаты** созданием документа `ЧекККМ` с услугой «Ремонт».
Не требуется:
- синхронизация заказов, статусов, номенклатуры работ;
- отражение предоплат отдельными документами;
- двусторонний обмен справочниками.

**Что делаем:**

```
ИС → 1С:  POST создания документа ЧекККМ
          { сумма, магазин/касса, услуга «Ремонт», способ оплаты,
            номер заказа (в комментарии), ИдемпотентностьKey }
1С → ИС:  { Ref_Key документа, номер чека, фискальный номер }
```

**Следствия:**
- Этап 3 сокращается **с 2 недель до 1 недели** (оценка в `docs/09-roadmap.md` обновлена);
- риск R1 (недоступность 1С) сохраняется, outbox остаётся — платёж принимается всегда;
- **предоплата и финальная оплата** отражаются в 1С одинаково — обе как `ЧекККМ`
  с услугой «Ремонт», различаясь суммой и комментарием;
- требование к 1С-подрядчику: HTTP-сервис создания `ЧекККМ` с идемпотентностью по ключу.

**Что уточнить при обследовании (этап 0):** через какую кассу создаётся `ЧекККМ`
(привязка магазина к кассе в 1С), нужен ли признак способа оплаты (нал/карта) отдельным
реквизитом, и как 1С возвращает фискальные данные для хранения в карточке заказа.

### 6.14. QR-код на квитанции и сканирование (ответ A4)

**Требование:** считывать номер заказа с печатной квитанции сканером.

**Решение:** QR-код на квитанции (PDF, печать на офисном принтере A4).

```
Содержимое QR:  repair://order/MSK1-2509-000142
```

**Почему именно так:**
- **Сканер USB в режиме эмуляции клавиатуры** — работает без драйверов, интеграции и
  настройки: сканер «печатает» содержимое в активное поле ввода. Приложение перехватывает
  ввод в поле поиска и автоматически находит заказ. Поддерживается **любой** USB-сканер.
- **Префикс `repair://`** отличает наше содержимое от случайного ввода и позволяет в
  будущем использовать тот же QR в мобильном приложении.
- **Сканирование в 3 точках:** поиск заказа, приём платежа (основной сценарий — A4),
  выдача.
- **Запасной вариант:** рядом с QR печатается номер **человекочитаемым текстом** и
  обычным линейным `Code128` дублируется тот же номер — на случай, если сканер читает
  только линейные коды. Печать линейного кода не усложняет реализацию.

**Где печатается:** PDF-квитанция формируется на сервере (этап 1). Драйверы и агенты
печати **не нужны** — печать выполняется браузером.

### 6.15. Ответственность заказчика (ответ A2)

| Область | Ответственный |
|---------|---------------|
| Приёмка этапов, эксплуатация, приоритеты | **Менеджер обработки поступающих ремонтов** |
| Прейскурант: состав и цены | Руководитель + главный бухгалтер |
| Утверждение версии прейскуранта | Руководитель **или** главный бухгалтер (одной подписи достаточно) |
| Нормативы сроков | Менеджер обработки поступающих ремонтов, корректировка по факту |

Это снимает риск R5 (размывание требований): единая точка принятия решений определена.
Менеджер становится и «суперпользователем» первой линии поддержки — ему в первую очередь
адресуются инструкции и обучение.

### 6.16. График и лимит партий: рабочая трактовка (задача 2.1)

ТЗ п. 2.6 требует «формирование партий по графику», но ни график, ни лимиты
нигде не определены: их нет ни в ТЗ, ни в этих решениях, ни в схеме БД
(`Batch` не имеет полей вместимости и расписания, у `Store` нет графика).

Чтобы не блокировать этап 2, принята трактовка, которая **ничего не запрещает
по умолчанию** и подтверждена заказчиком при старте задачи 2.1:

* **График** — плановая дата отправки (`Batch.plannedAt`). Она задаётся при
  создании партии и определяет дату в номере (`П-250916-004` — рейс 16
  сентября). Отдельного расписания по магазинам не вводится: это была бы
  выдуманная сущность, которой нет в ТЗ.
* **Лимит** — настройка `Setting.logistics.batchMaxItems`, по умолчанию
  **отсутствует**, то есть состав не ограничен. Мусорное значение настройки
  лимитом не становится: опечатка администратора не должна останавливать
  логистику.

Если заказчик позже задаст настоящее расписание рейсов и нормы вместимости,
они добавляются как отдельные поля `Batch`/`Store` и новая настройка — текущая
трактовка этому не противоречит.

## 7. Логистическая схема «магазин ⇄ производство» (согласовано заказчиком)

Раздел фиксирует порядок работы, согласованный заказчиком при разборе вопроса
«как происходит привязка заказа к партии для отправки». Он **имеет приоритет**
над прежними трактовками этапа 2 там, где они расходятся, и служит основанием
для доработки (см. `docs/16-logistics-completion.md`).

### 7.1. Магазин → Производство

1. Сотрудник магазина (в терминах системы — пользователь с ролью приёмщика,
   которому **дополнительно назначена роль логиста**) создаёт партию в
   интерфейсе и добавляет в неё принятые заказы.
2. Формируется и печатается **реестр отправляемых документов** — это акт
   приёма-передачи (`BatchAct`, PDF, подпись обеих сторон). Реализовано.
3. Отправка партии переводит заказы в «В пути в цех».
4. Менеджер обработки поступающих ремонтов принимает партию — цех принял
   изделия.
5. Менеджер назначает исполнителя; статус меняется на **«Выдано в работу»**, и
   факт «какой ювелир выполнял работу» виден **в истории заказа**.
6. Работы выполнены; менеджер принимает работу — статус **«Работы завершены»**.

### 7.2. Производство → Магазин

7. Менеджер создаёт партию на магазин **приёма** заказа («где приняли, там и
   выдаём»), по одной партии на магазин, и добавляет в неё заказы.
8. Формируется и печатается реестр; отправка переводит заказы в «В пути в
   магазин».
9. Магазин принимает партию — статус **«Готов к выдаче»**, клиент уведомляется.
   Реализовано.
10. Выдача: при необходимости принимается оплата, фиксируется подпись клиента,
    заказ закрывается. Реализовано.

### 7.3. Отказ клиента

Отказ возможен **до начала работ**. Изделие возвращается в магазин **обычной
партией** — для этого введены переходы «вернуть в магазин без работ» из
«Принят цехом» (26) и из «Выдано в работу» (27), оба с обязательной причиной.
Заказ при этом помечается отметкой `returnedWithoutWorkAt`, и при приёмке
обратной партии магазин закрывает его статусом **«Отказ до начала работ»**
(`REFUSED_BEFORE_WORK`, переход 29).

**Решение изменено 2026-09-20 (дефект 67).** Первоначально было принято, что
отдельный статус отказа **не вводится**, а отказ оформляется в магазине
существующим статусом «Отменён» (`CANCELLED`). На проде выяснилось, что это
решение неработоспособно: заказ, возвращённый в магазин, принимался статусом
**«Готов к выдаче»** (`READY_FOR_PICKUP`), а отмена разрешена только из
`ACCEPTED` (переход 10). Закрыть отказ клиента было **нечем**: заказ нельзя было
ни выдать (работы не выполнены, оплаты нет), ни отменить — в магазине висело
изделие, которое никто не заберёт.

Заказчик выбрал **ввести отдельный статус** вместо повторного использования
`CANCELLED`. Причина: отмена — это действие магазина по своей инициативе, а отказ
— инициатива клиента, и изделие уже съездило в цех и вернулось. Отдельный статус
делает отказ видимым в отчётах и в истории заказа, а «Отменён» остаётся за
действиями сотрудника.

### 7.4. Принятые решения по ролям и контролю

| Вопрос | Решение |
|--------|---------|
| Кто создаёт партии отправки | Приёмщик, которому дополнительно назначена роль **логиста**. Матрица прав `RECEIVER` не расширяется |
| Контроль «где приняли, там и выдаём» | Зона ответственности **менеджера**. Жёсткая проверка в коде не вводится; интерфейс подбора заказов **предупреждает** о несовпадении магазина партии и магазина приёма, но не блокирует |
| Производственные статусы | Вводятся **«Принят цехом»** и **«Выдано в работу»** (плюс **«Работы завершены»**); `IN_PRODUCTION` сохраняется как этап «в производстве» |

### 7.5. Почему это доработка, а не готовая функция

Серверная логика партий, акт и PDF, отправка/приём с переходами пачкой в одной
транзакции — работают. **Отсутствовало** три вещи, без которых описанный
процесс физически не выполнялся:

* интерфейса партий в веб-приложении нет вовсе — процесс выполним только через API;
* назначение исполнителя не сохраняется (`OrderAssignment` только читается), из-за
  чего переход «работы завершены» был недостижим и заказ не мог уехать из цеха;
* отказ от оплаты недостижим: акт отказа (`RefusalAct`) никто не создаёт.

Разбор — в `docs/15-known-issues.md` (дефекты 58–63) и
`docs/16-logistics-completion.md`.
