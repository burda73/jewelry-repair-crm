# 08. Интерфейс и UX

## 1. Принципы

1. **Одно главное действие на экране.** Приёмщик работает с клиентом «в руках» — ему некогда
   искать кнопку. Ключевое действие всегда крупное и справа.
2. **Мобильный приоритет.** Курьер и приёмщик работают с телефона; вёрстка проектируется
   от 360 px вверх, а не «сжимается» из десктопа.
3. **Скорость важнее красоты.** Никаких тяжёлых анимаций и больших таблиц без виртуализации.
   Целевой вес страницы карточки заказа — ≤ 250 КБ JS.
4. **Сервер — источник правды по правам.** Кнопка скрыта, если сервер не вернул действие
   в `available-transitions` / `permissions`. Фронтенд не дублирует матрицу прав.
5. **Ничего не теряется молча.** Все деструктивные действия (отмена, сторно, корректировка)
   требуют причины и показывают последствие.
6. **Понятные статусы.** Внутренние коды не показываются пользователю — только русские
   названия с цветовой кодировкой.

### 2.0. Публичная страница «Проверить статус заказа» (задача 5.11)

Маршрут `/status` — **вне входа**. Самый частый звонок в магазин — «готов ли
заказ»; страница снимает его без учётной записи и без участия приёмщика.

**Два поля:** номер заказа и телефон, названный при приёме изделия. Затем код из
SMS — четвёртое поле. Одного номера недостаточно: он угадываем по формату
(`МСК1-2609-000001`), и перебором можно было бы собрать статусы чужих заказов
(docs/05 §5.1).

**Ничего не подставляется из адреса.** Ни номер заказа, ни телефон не берутся из
параметров ссылки: такая ссылка с подставленным номером попала бы в историю
браузера и в чужой телефон при пересылке.

**Страница не различает причину отказа.** Текст один и тот же для «нет такого
заказа», «телефон не тот» и «лимит»: сервер намеренно отвечает неотличимо, и
интерфейс не добавляет того, что сервер скрывает. Поэтому фраза-подтверждение
сформулирована условно: «если заказ есть и телефон совпадает, код отправлен».

**Что показывается после проверки:** номер, статус словами для клиента,
плановая дата, стоимость, оплачено, к доплате, маска телефона. Фамилия, описание
работ, адрес и полный телефон не показываются — состав ответа задан на сервере и
проверяется тестом, интерфейс не добавляет своих сведений о заказе.

### 2.1. Экран «Сотрудники» (задача 1.2.4)

Реализован (`apps/web/src/app/(app)/users/page.tsx`). Пункт меню виден только тем,
у кого есть право `user:manage`, — по матрице ролей это только ADMIN.

**Список.** Поиск по ФИО, почте и телефону (без учёта регистра, работает с
кириллицей), фильтры «только активные» / «только отключённые» и по роли. В
строке видны: ФИО, бейдж активности, пометки «требуется смена пароля» и
«заблокирована», роли с магазинами, дата последнего входа и **число активных
сессий** — по нему администратор понимает, работает ли сотрудник прямо сейчас.

**Создание.** Отдельное модальное окно. Пароль генерируется на клиенте из
доменного генератора (`@app/shared`, `utils/password.ts`) и **показывается один
раз** — с отдельной плашкой и просьбой передать его лично. Посмотреть пароль
потом нельзя: сервер хранит только хеш Argon2id и не отдаёт его ни в одном
ответе. Кнопка «Сгенерировать» рядом с полем избавляет от соблазна задать
простой пароль, который легко набрать вручную.

**Карточка.** Роли перечислены с магазинами, потому что одну роль можно
назначить в нескольких магазинах и снимать нужно конкретное назначение.
Действия: назначить роль (уже назначенные в списке не показываются — повторное
назначение сервер отклонит как `ROLE_ALREADY_ASSIGNED`), снять роль, сбросить
пароль, включить или отключить учётную запись. Показаны вычисленные права —
объединение прав всех ролей, ровно то же, что вернёт `GET /auth/me`, поэтому
экран администратора не может показать права, которых сотрудник не получит.

**Предупреждения.** Операции, завершающие сессии сотрудника (отключение,
снятие роли, сброс пароля), подтверждаются и объясняют последствие: без этого
администратор воспринимал бы «отключить» как безобидную пометку. Отключение
собственной учётной записи блокируется в интерфейсе до запроса — сервер
отклонит его и так, но объяснение до нажатия понятнее отказа после.

**Чего экран не показывает.** Пароли — нигде и никогда, включая журнал аудита.
Права роли берутся из справочника `GET /users/roles-catalog`, который отдаёт
матрицу из доменного пакета: интерфейс не дублирует матрицу доступа, поэтому
не может разойтись с сервером.

### 2.2. Экран «Справочники» (задача 1.3.1)

Реализован (`apps/web/src/app/(app)/dictionaries/page.tsx`). Пункт меню виден
тем, у кого есть `settings:manage` (ADMIN) или `performer:manage`
(PRODUCTION_MANAGER) — по матрице прав исполнителей производства ведёт менеджер
производства, поэтому раздел не может быть администраторским целиком.

**Вкладки.** Магазины, цеха, исполнители, категории работ, типы камней. Вкладка
«Исполнители» показывается только при праве `performer:manage`; остальные четыре
требуют `settings:manage`. Права проверяются и на сервере — клиентская проверка
лишь не показывает недоступный интерфейс.

**Удаления нет.** Кнопки «Удалить» на экране нет намеренно: на магазины, цеха и
исполнителей ссылаются заказы, на категории — позиции прейскуранта, на типы
камней — строки камней в заказах. Вместо удаления — переключатель «Активна» в
карточке: запись исчезает из выбора при оформлении заказа, но остаётся в
справочнике и во всех уже созданных документах.

**Отключённые записи.** По умолчанию список показывает только активные;
флажок «Показывать отключённые» добавляет остальные. Так администратор не
разыскивает отключённое по всему списку и при этом не теряет его совсем.

**Код.** Ввод кода автоматически приводится к верхнему регистру и проверяется по
формату (заглавные латинские буквы, цифры, дефис). Подсказка объясняет, что код
неизменяем после начала использования: у магазина код входит в номера заказов,
поэтому сервер отклонит его смену при наличии заказов — администратор увидит
причину, а не «ошибка 409».

**Цена камня.** Вводится в рублях, в API уходит целым числом копеек. Перевод
делается на клиенте, чтобы администратор вводил привычную сумму, а сервер
принимал единый формат минорных единиц; дробное значение отклоняется.

**Зависимости между справочниками.** Исполнителя нельзя завести, пока нет ни
одного активного цеха (кнопка «Добавить» заблокирована), а перевод в закрытый
цех отклоняется сервером с `WORKSHOP_INACTIVE`. Причина в том, что такой
исполнитель сразу оказался бы недоступен для назначения.

**Ошибки.** Экран показывает сообщение сервера, а не общую формулировку: отказы
осмысленны («Нельзя изменить код: у магазина 1 заказ(ов)…», «В цехе незавершённые
заказы: 4…»), и администратор понимает, что именно нужно исправить.

### 2.3. Экран «Рабочий календарь» (задача 1.3.3)

Реализован (`apps/web/src/app/(app)/calendar/page.tsx`). Пункт меню виден только
при праве `settings:manage` (ADMIN): календарь определяет сроки всех заказов,
поэтому его изменение влияет на обещания клиентам, а не на работу одного
подразделения.

**Главное отличие от справочников: здесь нет списка дней.** Таблица хранит
только исключения — праздник, объявленный рабочим днём, перенос, особые часы.
Обычные рабочие дни и государственные праздники РФ система знает сама. Это не
упрощение ради экономии места, а исправление: прежде календарь заполнялся
строкой на каждый день, среди этих строк праздники среди недели были помечены
рабочими, и срок «5 рабочих дней от 25 декабря» попадал на 1 января. Сетка
месяца с флажками на каждый день снова подталкивала бы к таким записям, поэтому
её нет.

**Экран показывает четыре вещи:**

| Блок | Смысл |
|------|-------|
| Пояснение сверху | Праздники ТК РФ учтены автоматически; здесь вносятся только переносы |
| Сводка по месяцам | Сколько рабочих и нерабочих дней — чтобы администратор видел, что праздники уже учтены, и не заводил записи зря |
| Исключения | Действующие отметки: дата, рабочий/нерабочий, часы, примечание |
| «Ничего не меняет» | Отдельным блоком с предупреждением: исторические записи, совпадающие с обычным правилом |

**Список праздников** показывается отдельным блоком, чтобы администратор видел,
что 1–8 января нерабочие и отмечать их не нужно. Без этого он заводит запись,
которая уже ничего не меняет.

**Часы вводятся только для рабочего дня.** «Выходной 8 часов» и «рабочий день
0 часов» — состояния, которых быть не должно; сервер их отклоняет, а поле просто
не показывается, когда день отмечен нерабочим. Понятнее, чем показать поле и
объяснять запрет.

**Снятие отметки.** Единственная кнопка удаления в интерфейсе администратора.
Подтверждение объясняет последствие: день вернётся к обычному правилу, прежнее
значение останется в журнале действий. Удаление здесь допустимо, потому что на
строку календаря не ссылается ни одна таблица, а «отключить дату» смысла не
имеет.

**Период обязателен.** По умолчанию — текущий год. Запрос без периода или
длиннее года отклоняется: календарь за 10 лет превратил бы экран в выгрузку
всей таблицы.

### 2.4. Экран «Нормативы этапов» (задача 1.3.4)

Экран задаёт срок, который система обещает клиенту на каждом этапе, — по нему считаются дата
готовности, просрочка и эскалации (ТЗ п. 2.7). Две идеи определяют его вид:

**Правка — это новая версия, а не изменение строки.** У нормативов нет «карандаша» у
отдельной записи: набор редактируется целиком, а сохранение создаёт версию и сразу её
применяет. Прежняя версия остаётся в истории — по ней объясняют, почему у заказа,
принятого месяц назад, был именно такой срок. Поэтому рядом с набором есть кнопка
«История версий», а поле «Причина изменения» обязательно: норматив меняет сроки всех новых
заказов, и причина попадает в журнал действий.

**Единица измерения выбирается явно и показывается рядом со значением.** «24 рабочих часа»
и «3 рабочих дня» — разные сроки: рабочие часы считаются внутри окна 10:00–19:00 МСК, а
рабочие дни — целыми днями по производственному календарю. Единица, скрытая в настройке,
приводила бы к сроку, который администратор не имел в виду.

```
┌── Нормативы этапов ──────────────────────────── [История версий] [Изменить] ──┐
│ Версия 1 · действует с 20.09.2026                                             │
├──────────────────────────┬────────────┬──────────────┬────────────┬──────────┤
│ Этап                     │ Сложность  │ Срок         │ Единица    │          │
├──────────────────────────┼────────────┼──────────────┼────────────┼──────────┤
│ Согласование клиента     │ любая      │ 3            │ раб. дн    │          │
│ Ожидание предоплаты      │ любая      │ 5            │ раб. дн    │          │
│ Очередь на отправку      │ любая      │ 24           │ раб. ч     │          │
│ Доставка в цех           │ любая      │ 8            │ раб. ч     │          │
│ Производство             │ сложный    │ 15           │ раб. дн    │          │
│ Производство             │ типовой    │ 5            │ раб. дн    │          │
│ Производство             │ любая      │ 15           │ раб. дн    │          │
│ Доставка в магазин       │ любая      │ 8            │ раб. ч     │          │
│ Хранение до выдачи       │ любая      │ 30           │ кал. дн    │          │
│ Рассмотрение рекламации  │ любая      │ 10           │ раб. дн    │          │
└──────────────────────────┴────────────┴──────────────┴────────────┴──────────┘
```

**Строка «Производство · любая» объясняется в интерфейсе.** `Order.complexity` по умолчанию
`ANY`, а задать его пока негде — калькуляция ещё не реализована. Без общего норматива такой
заказ остался бы вообще без срока. Значение равно сроку сложного ремонта намеренно
консервативно; конкретные «типовой»/«сложный» приоритетнее.

**Состояние «нормативы не заданы» показывается явно.** Если действующей версии нет, экран
сообщает, что срок по этапам **не рассчитывается**, и предлагает задать набор. Молчаливая
подстановка значений по умолчанию скрыла бы это состояние — именно так дефект с
нерассчитанным сроком и оставался незамеченным (docs/15, «Дефект 26»).

**Этапы перечислены в порядке прохождения заказа**, а не по алфавиту: набор читают как
маршрут изделия, а не как список кодов.

## 3. Карточка заказа — центральный экран

Единый экран, где собрано всё о заказе. Вкладки, а не отдельные страницы — сотрудник
не теряет контекст.

```

│ Кольцо золото 585 · Иванов И.И. · +7 916 123-45-67                       │
│ [Перевести статус ▾]  [Принять оплату]  [Печать квитанции]               │
├──────────────────────────────────────────────────────────────────────────┤
│ Обзор │ Калькуляция │ Платежи │ Согласования │ Звонки │ История │ Фото   │
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  ИЗДЕЛИЕ                          ДЕНЬГИ                                  │
│  Кольцо, Au585, 4.2 г, р.17        Итого:            12 500 ₽             │
│  Дефект: трещина у шинки           Оплачено:          3 000 ₽             │
│  Комплектность: без вставки        Осталось:          9 500 ₽             │
│                                    Предоплата: ✓ внесена                  │
│  ПРОИЗВОДСТВО                                                             │
│  Цех: Центральный                  СРОКИ                                  │

│  Назначено: 15.09                  Норматив этапа: 5 раб. дней            │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

**Вкладка «История»** — единая лента: статусы, платежи, согласования, корректировки,
изменения — с указанием автора и времени. Это прямой ответ на ТЗ п. 2.1 («история статусов»)
и п. 4 («журнал действий»), но в удобном для сотрудника виде.

**Вкладка «Согласования»** — карточки согласований, устные помечены бейджем
«Согласовано устно» и рядом кнопка прослушать запись.

**Вкладка «Звонки»** — плеер, дата/время, длительность, направление, кнопка «отвязать».

## 4. Мастер создания заказа

5 шагов, прогресс виден, можно вернуться назад. Черновик сохраняется автоматически —
приёмщика может отвлечь клиент.

| Шаг | Содержание | Валидация |
|-----|-----------|-----------|
| 1. Клиент | Поиск по телефону/ФИО, выбор существующего или создание | Телефон обязателен и нормализуется |
| 2. Согласие | **Обязательная отметка о согласии на запись разговоров** (ТЗ п. 2.4) | Без отметки «Далее» заблокировано |
| 3. Изделие | Название, металл, вес, размер, дефекты, комплектность, фото с камеры | Минимум 1 изделие, ≥ 1 фото |
| 4. Работы и камни | Выбор из прейскуранта с поиском, добавление камней, нетиповые работы | Калькуляция непуста |
| 5. Итог | Сумма, срок, предоплата, подтверждение, **печать квитанции с QR-кодом** | Сумма > 0 |

**Предоплата на шаге 5:** система показывает, требуется ли она и сколько; если да —
заказ сразу уходит в `AWAITING_PREPAYMENT`, и приёмщик видит подсказку «работы не начнутся
до подтверждения предоплаты» (ТЗ п. 2.5).

### 4.1. Автосохранение черновика (задача 1.7.3)

Приёмщика может отвлечь клиент посреди оформления: он уходит за изделием, отвечает на
звонок, закрывает ноутбук. Черновик сохраняется автоматически, а рядом с номером шага
появляется подпись «черновик сохранён 14:32» — без неё непонятно, сохранился ли ввод.

**Черновик не подставляется автоматически.** При открытии формы показывается отдельное
предложение: *«Найден незавершённый черновик от 18.09.2026, 14:32. Восстановить введённые
данные?»* с кнопками «Восстановить» и «Начать заново». Молчаливая подстановка означала бы,
что приёмщик, начавший новый заказ, видит в полях данные прошлого клиента, — и может принять
новый заказ на чужое изделие. Потеря черновика здесь безопаснее ошибки.

**Черновик привязан к сотруднику.** Он хранится в браузере под ключом с идентификатором
пользователя: на точке часто один общий компьютер, и черновик одного приёмщика с ФИО и
телефоном клиента не должен открываться у другого (152-ФЗ). При выходе из системы черновики
сотрудника удаляются; после успешного создания заказа — тоже, потому что черновик стал
заказом.

**Срок годности — неделя.** Более старый черновик не восстанавливается: клиент уже приходил
или отказался, и подстановка недельного ввода только запутала бы. Черновик другой версии
схемы формы также не применяется вслед за обновлением приложения.

**Чего в черновике нет.** Цены работ: они выводятся из металла и действующего прейскуранта,
а сохранённая копия цены «застряла» бы после изменения прейскуранта — ровно тот дефект, ради
которого цены сделаны производными. Фотографии изделий тоже не сохраняются: файлы не место
в браузерном хранилище.

**На сервере черновик не хранится намеренно.** Незавершённый ввод не должен становиться
сущностью БД: иначе брошенные формы порождали бы мусорные `DRAFT`-заказы, которые пришлось
бы отслеживать и чистить.

**Пустая форма черновика не создаёт.** Признак «есть что сохранять» проверяется по полям,
которые заполняет человек; шаг, магазин по умолчанию и приоритет по умолчанию данными не
считаются. Иначе приёмщик, открывший и закрывший мастер, оставил бы черновик, и при
следующем входе система предлагала бы восстановить пустоту. Восстановленный черновик
продолжает сохраняться: приёмщик может продолжить заполнение и снова отвлечься.

### 4.2. Сохранённые представления списка заказов (задача 1.7.4)

Приёмщик, руководитель и мастер смотрят на одни и те же заказы разными срезами: приёмщик —
«новые за сегодня», руководитель — «просроченные», мастер — «в работе». Кнопка
**«Представления»** над списком открывает панель: сохранённые срезы с отметкой текущего и
поле «Название представления» для сохранения того, что выставлено сейчас.

**Срез целиком лежит в адресе страницы** (`/orders?status=DRAFT,READY_FOR_PICKUP&overdue=true`).
Это не деталь реализации, а причина хранить представления как набор фильтров: ссылку на
подборку можно передать коллеге — «посмотри просроченные по первому магазину». Хранить
представление как «идентификатор сохранённого поиска» и передавать ссылку значило бы, что у
коллеги этот идентификатор не найдётся.

**Представления привязаны к сотруднику** и хранятся в браузере: фильтр может содержать
телефон клиента или номер заказа, а компьютер на точке часто общий (152-ФЗ). При выходе из
системы они удаляются вместе с черновиками. На сервере представления намеренно не хранятся:
состав фильтров — вопрос удобства, а не бизнес-правило, и таблица ради него не оправдана.

**Пустой срез сохранить нельзя** — это и есть исходный экран; место в списке он бы занимал
без пользы. Дубли по содержимому не создаются: два представления с одинаковыми фильтрами
различались бы только именем и путали бы выбор. Состав фильтров из хранилища проверяется так
же, как данные из адреса: неизвестное поле отбрасывается, а не уходит в запрос к API, иначе
выборка оказалась бы непредсказуемой.

### 4.1. Квитанция и QR-код (ответ A4)

После создания заказа квитанция формируется **в PDF на сервере** и печатается из браузера
(`window.print()`) на обычном офисном принтере A4. Драйверы, агенты печати и настройка
рабочего места **не требуются** — достаточно открыть карточку заказа и нажать «Печать».

**Состав квитанции:**

```
┌──────────────────────────────────────────────┐
│  РЕМИКС ГОЛД · Магазин МСК1                  │
│  ┌─────────┐                                 │
│  │ ▄▄▄ ▄ ▄ │   Заказ: МСК1-2509-000142       │
│  │ ▄ ▄▄▄ ▄ │   ─────────────────────────     │
│  │ ▄▄▄ ▄▄▄ │   Изделие: кольцо золото 585     │
│  └─────────┘   Работа: пайка разрыва шинки   │
│   (QR-код)     Сумма: 2 500,00 ₽             │
│                Предоплата: 1 000,00 ₽        │
│  ‖‖│‖│‖‖│‖‖    Срок: 23.09.2025              │
│  (Code128)     Телефон: +7 916 123-45-67     │
└──────────────────────────────────────────────┘
```

**Три способа ввода номера — от самого удобного:**

| Способ | Как работает | Зачем |
|--------|--------------|-------|
| **QR-код** | Сканер USB «печатает» `repair://order/МСК1-2509-000142` в поле поиска; система сама открывает заказ | Основной способ: не нужно набирать вручную |
| **Code128** | Резерв, если сканер читает только линейные коды | Совместимость с любым оборудованием |
| **Текстом** | Номер крупным шрифтом, приёмщик набирает вручную | Если сканера нет или он неисправен |

**Поведение поля поиска.** Приёмщик ставит курсор в поле поиска и сканирует. Система
принимает и полный URI, и просто номер, игнорирует лишние пробелы и перевод строки, который
добавляет сканер. Если распознать не удалось — поле ведёт себя как обычный текстовый поиск,
ошибка не показывается: пользователь может просто продолжать печатать.

**Учёт перепечаток.** Каждая печать увеличивает счётчик, дата последней печати сохраняется.
Это защищает от ситуации «клиент принёс квитанцию, а по ней уже выдали другое изделие»:
перепечатки видны в истории заказа.

**Как это сделано.** Сервер отдаёт PDF (`GET /orders/:id/receipt`, docs/07 §6.1),
браузер открывает его в новой вкладке встроенным просмотрщиком. Кнопка не блокируется
после первой печати: сотрудник вправе напечатать копию, и она останется в истории.

**Шрифт встроен в PDF.** На сервере нет ни одного системного шрифта
(`/usr/share/fonts` отсутствует — проверено), поэтому шрифт DejaVu Sans приезжает
вместе с зависимостями. Полагаться на системный шрифт нельзя: кириллица вышла бы
пустыми квадратами, то есть квитанция была бы нечитаемой.

**Фон кодов задан белым явно.** `bwip-js` по умолчанию рисует код на прозрачном фоне;
такой QR не декодируется ни на одном масштабе — сканирование квитанции не работало бы.
Проверено декодированием QR, извлечённого из готовой страницы PDF.

**Сканирование в трёх местах:** поиск заказа (общий), **приём оплаты** (основной сценарий,
ТЗ п. 2.5 — оплата в любой точке по номеру) и **выдача** (ТЗ п. 2.8).

## 5. Мобильные сценарии (PWA)

| Роль | Сценарий | Особенности экрана |
|------|----------|--------------------|
| Приёмщик | Приём заказа, фото изделия | Камера вызывается напрямую (`capture`), крупные кнопки, автосохранение черновика |
| Приёмщик | Выдача | Проверка оплаты крупным индикатором, подпись клиента пальцем на canvas (загрузка файла — дефект 66) |
| Курьер | Мои доставки | Список партий, сканирование номера заказа, фото партии, отметка «в пути»/«доставлено» с геометкой (опционально) |
| Менеджер производства | Очередь, назначение | Список с фильтром, назначение исполнителя в 2 тапа |
| Руководитель | Просмотр показателей | Дашборд и отчёты, read-only |

**PWA-требования:** манифест, Service Worker с кэшем оболочки, работа при кратком пропадании
сети с очередью мутаций (фото загружаются в фоне), установка на домашний экран,
push-уведомления — опционально на этапе 5.

### 5.1. Service Worker: что кэшируется, а что нет (задача 1.7.5)

Реализован Service Worker (`apps/web/public/sw.js`) и страница-заглушка
(`apps/web/public/offline.html`). Манифест и иконки дополняют установку на домашний экран.

**Кэшируется только оболочка** — статика сборки (`/_next/static/*`, имя содержит хэш
содержимого, поэтому устаревание невозможно) и иконки. Это позволяет приложению открыться
при кратком пропадании сети: на торговой точке это обычная ситуация.

**Ответы API не кэшируются никогда.** Это главное решение, и оно принято против удобства:
устаревший статус заказа или неподтверждённая оплата, показанные как актуальные, ведут к
выдаче изделия без денег. При недоступной сети приложение честно сообщает об ошибке загрузки.

**HTML страниц приложения не кэшируется.** Разметка отрисована с данными конкретного
пользователя — ФИО клиента, суммы. Кэш страницы на общем компьютере означал бы, что после
выхода из системы следующий сотрудник увидит чужой экран (152-ФЗ). При переходе без сети
отдаётся заглушка «Нет подключения», а не страница из кэша.

**Выход из системы очищает кэш.** Правило «выход очищает устройство» выполняется целиком:
вместе с черновиками и представлениями (задачи 1.7.3, 1.7.4) страница просит воркер удалить
кэши, а тот при активации удаляет всё, кроме текущей версии оболочки.

**Версия кэша входит в его имя.** Новая сборка получает новый кэш, старый удаляется при
активации: иначе на планшете годами лежала бы статика первой версии.

**Очередь мутаций и фоновая загрузка фото** (из требований выше) не реализованы: это
существенно больший объём — нужна синхронизация с разрешением конфликтов и повторной
отправкой. Офлайн-режим сейчас ограничен открытием оболочки; приём заказа требует сети.
Решение зафиксировано в `docs/15-known-issues.md`.

## 6. Дизайн-система

- **Компоненты:** shadcn/ui + Radix (доступность из коробки) + Tailwind CSS.
- **Токены темы:** цвета статусов — единый словарь `statusColor(status)` в `packages/shared`,
  чтобы бейдж в списке и в карточке выглядели одинаково.

| Статус | Цвет | Смысл для сотрудника |
|--------|------|----------------------|
| Черновик | серый | Ещё не принят |
| Ожидает согласования / предоплату | янтарный | Ждём клиента |
| Принят / В очереди | синий | В работе у нас |
| В пути | фиолетовый | Перемещение |
| В производстве | голубой | У ювелиров |
| Готов к выдаче | зелёный | Можно звонить клиенту |
| Невостребовано | оранжевый | Требует внимания |
| Выдан | тёмно-зелёный | Закрыт успешно |
| Отменён / Отказ / Отказ до начала работ | красный | Закрыт без ремонта |

- **Типографика:** Inter, базовая 16 px (важно для планшетов и читаемости возрастными
  сотрудниками).
- **Плотность:** два режима — «комфортный» (по умолчанию, мобильные) и «компактный»
  (для списков на десктопе).
- **Обратная связь:** каждая мутация — оптимистичное обновление + тост с откатом при ошибке.
  Денежные операции — **без** оптимистичного обновления, только после ответа сервера.

## 7. Доступность и локализация

- Контраст ≥ 4.5:1, управление с клавиатуры, фокус-ловушки в модальных окнах.
- Все формы работают с автозаполнением; телефон и карта — `inputmode="tel"`/`"numeric"`.
- Локаль — только `ru-RU`, но тексты выносятся в словарь (задел на будущее).
- Даты: `дд.мм.гггг`, суммы: `12 500 ₽` (неразрывный пробел как разделитель разрядов).

## 9. Что проверяем юзабилити-тестами до разработки

1. Приёмщик оформляет типовой заказ с нуля — целевое время **≤ 3 минуты**.
2. Приём предоплаты в чужом магазине по номеру заказа — **≤ 1 минута**.
3. Курьер отмечает получение партии — **≤ 2 минут** на партию из 20 заказов.
4. Менеджер производства распределяет 30 заказов на исполнителей — **≤ 5 минут**.
5. Руководитель находит просроченные заказы — **≤ 30 секунд** от входа.

Тесты проводятся на прототипе Figma до начала кодирования экранов (см. `docs/09-roadmap.md`,
этап 0) — это дешевле, чем переделывать реализованный интерфейс.
