# 05. Интеграции

Все внешние системы подключаются через **порты** (интерфейсы) и **адаптеры**: доменный код
зависит от интерфейса, а не от конкретной 1С или АТС, поэтому в тестах и в MVP используются
in-memory реализации.

## 0. Состояние на сегодня

**Реализация 1С и IP-АТС отложена заказчиком** (этапы 3 и 4, `docs/09-roadmap.md` §6–7).
Этот документ — их подготовленная документация: контракты, требования к подрядчикам и план
приёмки. Разделы ниже описывают **проектируемое** поведение; чтобы не выдавать план за
готовое, состояние каждой части указано явно.

| Часть | Состояние |
|-------|-----------|
| Таблицы `IntegrationOutbox`, `IntegrationLog`, `CallRecording`, `Notification` | **есть в схеме** (`packages/db/prisma/schema.prisma`) |
| Идемпотентность платежей (`Payment.idempotencyKey`, `externalId`, `syncStatus`, `receiptNo`, `kktShiftNo`, `fiscalDocNo`) | **есть в схеме** |
| `AccountingPort`, `TelephonyPort`, `NotificationPort`, `StoragePort` | **не созданы** — контракты в §7 |
| Воркер `integration-outbox`, HTTP-клиент 1С, воркер `recording-retention` | **не реализованы** |
| Эндпоинты `/integrations/1c/*`, `/notifications`, `/public/order-status` | **не реализованы** |
| Хранилище файлов | **реализовано локально** (`StorageService`, каталог на диске); S3 — при переходе в прод |
| Внешний HTTP для интеграций | недоступен: **у продакшн-контура нет выхода в интернет**, поэтому 1С и АТС должны быть во внутренней сети |

Что это значит практически: **схема данных и правила идемпотентности уже готовы**, и
построение адаптера не потребует миграций. Заказчику нужно предоставить доступы и
подтвердить требования из §1.3.1 (1С) и §2.7 (АТС).

### Порты (планируемая структура)

```
packages/shared/src/ports/          ← каталога пока НЕТ; создаётся на этапе 3
  accounting.port.ts   AccountingPort   — 1С        (этап 3)
  telephony.port.ts    TelephonyPort    — IP-АТС    (этап 4)

```

Контракты портов приведены в §7 — их можно передавать подрядчикам как спецификацию.

## 1. Интеграция с 1С (ТЗ п. 2.5, 2.8 — оплаты, ККТ)

> **Область интеграции существенно сокращена по ответу A4** (`docs/00-decisions.md` §6.13):
> в 1С достаточно **фиксировать факт оплаты** созданием документа `ЧекККМ` с услугой «Ремонт».
> Синхронизация заказов, статусов, номенклатуры работ и справочников **не требуется** —
> это снимает значительную часть первоначального объёма работ.

### 1.1. Что передаётся

| # | Направление | Событие | Данные |
|---|-------------|---------|--------|
| 1 | ИС → 1С | Приём предоплаты | Сумма, магазин/касса, услуга «Ремонт», способ оплаты, номер заказа (в комментарии), `idempotencyKey` |
| 2 | ИС → 1С | Приём финальной оплаты | То же (отличается суммой и комментарием) |
| 3 | ИС → 1С | Сторно/возврат | Ссылка на исходный документ, причина |
| 4 | 1С → ИС | Подтверждение | `Ref_Key` документа, номер чека, фискальный номер |
| 5 | 1С → ИС | Отмена/сторно со стороны 1С | Причина, ссылка |

**Предоплата и финальная оплата отражаются в 1С одинаково** — обе как `ЧекККМ` с услугой
«Ремонт», различаясь суммой и комментарием. Отдельные документы для предоплаты не нужны.

**Разделение копий документов по магазинам.** `ЧекККМ` создаётся в базе магазина, где принята
оплата, — это позволяет принимать предоплату в любой точке сети (ТЗ п. 2.5).

### 1.2. Механизм: transactional outbox

Механизм остаётся **без изменений** (ADR 0002). Упрощение области интеграции не отменяет
главного требования: **1С может быть недоступна, но приём оплаты обязан работать.**

```
Приём платежа (одна транзакция БД):
  1. INSERT Payment (status = CONFIRMED, syncStatus = PENDING)
  2. UPDATE Order.paidAmountMinor
  3. INSERT IntegrationOutbox (eventType = PAYMENT_CREATED, status = PENDING, idempotencyKey)
  4. INSERT AuditLog
  ── COMMIT ──  ← клиент получает ответ, деньги приняты

Воркер integration-outbox (каждые 30 сек):
  1. SELECT ... WHERE status = 'PENDING' AND nextRetryAt <= now() FOR UPDATE SKIP LOCKED
  2. POST в 1С с idempotencyKey
  3. Успех  → status = SENT, Payment.syncStatus = SYNCED, externalId
     Ошибка → attempts++, экспоненциальная задержка 30с → 5м → 30м → 2ч → 12ч
     attempts > 10 → status = DEAD, алерт администратору
```

`FOR UPDATE SKIP LOCKED` позволяет запускать несколько воркеров без дублирования отправок.

### 1.2.1. Почему outbox сохраняется при упрощённой интеграции

Возможен вопрос: если интеграция сводится к одному документу, не проще ли вызывать 1С
напрямую? **Нет**, и причины те же, что и раньше:

1. **Магазин не должен ждать 1С.** Если 1С обновляется или недоступна, кассир всё равно
   принимает деньги — иначе останавливается работа точки.
2. **Чек ККТ обязан быть пробит.** Факт оплаты и фискальный документ не должны теряться
   при сбое передачи данных в учётную систему.
3. **Расхождение должно быть видно.** Outbox даёт очередь с ошибками и алертами, а не
   «тихо не улетевший» запрос.

### 1.3. Транспорт

**Ответ A4/A1.2:** у заказчика **есть 1С-подрядчик**, который сделает HTTP-сервис;
тестовая база будет предоставлена.

| Вариант | Решение |
|---------|---------|
| **HTTP-сервис 1С** | **Выбран.** JSON-обмен, идемпотентность по ключу |
| OData | Не используется — требуется своя логика создания `ЧекККМ` |
| Обмен через файлы | Резерв, только если публикация веб-сервиса окажется невозможной |
| Прямая запись в БД 1С | **Не применяем** — обход бизнес-логики 1С, риск порчи данных |

### 1.3.1. Требования к 1С-подрядчику

HTTP-сервис должен:

1. Принимать `POST` с JSON: сумма, магазин, услуга «Ремонт», способ оплаты, комментарий
   (номер заказа), `idempotencyKey`.
2. **Быть идемпотентным:** повторный вызов с тем же ключом не создаёт второй `ЧекККМ`,
   а возвращает ранее созданный документ. Это критично: при таймауте наша система повторит
   запрос, и без идемпотентности в 1С появится дубль чека.
3. Возвращать `Ref_Key` документа, номер чека и фискальный номер.
4. Быть доступным во внутренней сети по адресу, резолвящемуся с сервера приложения
   (`remixgold.ru`, Proxmox).

**Что уточнить при обследовании (этап 0):** через какую кассу создаётся `ЧекККМ`
(привязка магазина к кассе в 1С), нужен ли признак способа оплаты отдельным реквизитом,
и как 1С возвращает фискальные данные для хранения в карточке заказа.

### 1.4. Сверка

Ежедневная сверка сумм платежей между ИС и 1С (см. `docs/06-reporting.md` §7).
Расхождения — отчёт администратору и главному бухгалтеру с указанием заказов и сумм.

### 1.4. Надёжность

- **Идемпотентность с обеих сторон:** `idempotencyKey` передаётся в 1С, при повторе 1С
  возвращает существующий документ, а не создаёт дубль.
- **Сверка (reconciliation):** ежедневный job сверяет суммы платежей ИС и 1С за прошлый день.
  Расхождения → отчёт администратору и руководителю.
- **Интерфейс контроля:** страница `/admin/integrations/1c` со списком очереди, ошибок,
  кнопкой «повторить» для отдельных записей.
- **ККТ:** фискализация выполняется 1С; в ИС хранятся `receiptNo`, `fiscalDocNo`, `kktShiftNo`
  как справочная информация. Если у заказчика ККТ с прямой интеграцией — добавляется второй
  адаптер, интерфейс не меняется.

### 1.5. Ключевые поля соответствия

| ИС | 1С | Примечание |
|----|----|-----------|
| `Order.orderNo` | Номер заказа | Соответствие задаётся в справочнике |
| `Payment.amountMinor` | Сумма документа | Копейки ↔ рубли, деление на 100 |
| `Payment.receiptNo` | Номер чека ККТ | |
| `Payment.externalId` | `Ref_Key` документа | Заполняется 1С при подтверждении |
| `Store.code` | Код склада/подразделения | Настраивается администратором |

## 2. Интеграция с IP-АТС (ТЗ п. 2.4 — записи звонков)

### 2.1. Задача

Автоматически привязывать запись разговора к карточке заказа, чтобы подтвердить устное
согласие клиента. Требование ТЗ прямо указывает на «интеграцию с IP-АТС».

### 2.2. Сценарии получения данных

| Способ | Описание | Приоритет |
|--------|----------|-----------|
| **REST API АТС** (Mango Office, Битрикс24, Asterisk ARI) | Периодический опрос журнала звонков | Основной |
| **CDR-файлы** (`Master.csv` Asterisk) | Парсинг файла по расписанию | Резервный для Asterisk |
| **AMI-события** (Asterisk Manager Interface) | Real-time подписка на `Cdr` | Если требуется мгновенная привязка |
| **Вебхук от АТС** | АТС сама вызывает наш эндпоинт | Если поддерживается |

### 2.3. Алгоритм сопоставления звонка с заказом

```
Вход: CallRecording { phoneFrom/phoneTo, startedAt, extension }

1. Нормализация телефона → E.164 (Customer.phoneNormalized)
2. Кандидаты: заказы, у которых клиент с этим телефоном,
   и (startedAt - 7 дней) <= Order.createdAt <= (startedAt + 90 дней)
   ИЛИ есть Approval за ±7 дней от звонка
3. Оценка совпадения (matchScore):
     +50  телефон точно совпадает с Customer.phoneNormalized
     +20  внутренний номер сотрудника привязан к магазину заказа
     +20  звонок в течение 30 минут после изменения статуса/создания согласования
     +10  заказ активен (не терминальный) на момент звонка
4. Если ровно один кандидат с score >= 70 → автопривязка (matchedBy = PHONE_TIME)
   Если несколько или score < 70    → в очередь «Неразобранные звонки» (ручная привязка)
   Если ни одного                    → сохраняем без привязки (история звонка клиента)
```

**Автопривязка никогда не удаляет данные.** Ручная перепривязка сотрудником фиксируется
(`linkedById`, `linkedAt`) и записывается в аудит.

### 2.4. UI «Неразобранные звонки»

Страница для приёмщика и менеджера производства: список звонков без заказа с фильтром по
телефону/дате, поиск заказа и кнопка «Привязать». Показывается и в карточке заказа —
вкладка «Звонки» с плеером.

### 2.5. Хранение записей — 1 год (ТЗ п. 2.4)

- Запись скачивается из АТС и кладётся в S3 (`CallRecording.fileId`), `retainUntil = startedAt + 1 год`.
- Если АТС сама хранит запись — допускается хранить только метаданные и ссылку
  (`fileId = null`, `externalUrl`), но **только если** это согласовано и срок хранения в АТС
  покрывает год.
- Воркер `recording-retention` ежедневно в 03:00 удаляет истёкшие: объект S3 → `FileObject` →
  `CallRecording` (мягко: сначала `retainUntil < now`, затем удаление).
- Удаление фиксируется в аудите (кто/когда/что удалено, без содержимого).

### 2.6. Правовые требования

- Согласие клиента на запись разговора — обязательный пункт заявки (`Customer.consentCallRecording`).
- Без согласия заказ не создаётся; при отзыве согласия записи по клиенту удаляются.
- Доступ к прослушиванию — только роли с правом `recording:listen`; каждое прослушивание
  логируется в аудите.

### 2.7. Требования к заказчику (АТС)

Чтобы начать этап 4, нужны:

1. **Модель АТС и способ доступа** — определяет адаптер (§2.2). От этого зависит, будет ли
   это REST, CDR-файлы или AMI.
2. **Доступ к журналу звонков и к аудиозаписям** с сервера приложения. Напоминание: у
   продакшн-контура **нет выхода в интернет**, поэтому АТС должна быть доступна во внутренней
   сети (или через прокси заказчика).
3. **Согласованная длительность хранения записей в АТС.** Если сама АТС хранит запись год,
   допускается держать у нас только метаданные и ссылку — но это требует письменного
   подтверждения: по ТЗ п. 2.4 запись обязана быть доступна **год**, и ответственность за
   срок в этом случае несёт АТС.
4. **Правовое подтверждение** порядка получения согласия на запись разговоров (§2.6).
5. **Привязка внутренних номеров к магазинам** — повышает точность автопривязки звонка к
   заказу (§2.3, +20 баллов).

## 3. SMS / мессенджеры (ТЗ п. 3, ответ заказчика — опционально с 5-го этапа)

Подключается через `NotificationPort`. Архитектура готова с 1-го этапа, реальная отправка
включается настройкой `notifications.sms.enabled`.

**События для уведомлений клиенту:**

| Событие | Шаблон | Канал по умолчанию |
|---------|--------|--------------------|
| Заказ принят | `ORDER_ACCEPTED` | SMS / мессенджер |
| Согласование требуется | `APPROVAL_REQUEST` | SMS / звонок |
| Предоплата получена | `PREPAYMENT_RECEIVED` | SMS |
| Заказ готов к выдаче | `READY_FOR_PICKUP` | SMS / мессенджер |
| Заказ невостребован | `UNCLAIMED_REMINDER` | SMS / звонок |
| Гарантия оформлена | `WARRANTY_ISSUED` | SMS |

**События для сотрудников:** `ORDER_OVERDUE`, `ESCALATION_MANAGER`, `PREPAYMENT_REQUIRED`,
`CLAIM_DEADLINE`. Канал по умолчанию — `IN_APP` + `EMAIL`, чтобы не зависеть от SMS-шлюза.

Каждое уведомление пишется в `Notification` со статусом; при отключённом канале остаётся
`IN_APP`-запись, то есть история уведомлений не теряется.

## 4. Хранилище файлов (S3 / MinIO)

`StoragePort`: `put(key, stream, mime)`, `getSignedUrl(key, ttl)`, `delete(key)`.

| Тип | Бакет | Доступ | Retention |
|-----|-------|--------|-----------|
| Фото изделий | `repair-photos` | Только через подписанные URL (TTL 15 мин) | Бессрочно |
| Записи звонков | `repair-calls` | Подписанные URL, только роль с правом | 1 год |
| Документы (акты, квитанции) | `repair-docs` | Подписанные URL | Бессрочно |
| Бэкапы | `repair-backups` | Только сервисный доступ | 90 дней |

Прямой публичный доступ к бакетам **закрыт**. Клиент получает временную ссылку.
Загрузка фото с телефона — прямая в S3 по presigned URL (не через API), чтобы не грузить
сервер бинарями.

## 5. Публичный API для будущего личного кабинета клиента

Заложено с 1-го этапа (ответ на вопрос 2 ТЗ), реализуется пост-MVP:

```
GET  /api/v1/public/order-status?orderNo=MSK1-2509-000142&code=1234
POST /api/v1/public/order-status/request-code  { orderNo, phone }
```

Код подтверждения — 4 цифры, отправляется SMS на телефон из заказа, живёт 10 минут,
rate limit 3 запроса в час на номер. Публичный эндпоинт возвращает **минимум данных**:
статус, плановую дату, сумму к оплате. Никаких ФИО, адресов и истории.

## 6. Контракты портов

Раздел предназначен для передачи подрядчикам: это спецификация того, что система ожидает от
внешней стороны, и одновременно граница, за которую доменный код не выходит.

### 6.1. `AccountingPort` (1С)

```ts
export interface AccountingPort {
  /** Создать чек ККМ. Идемпотентно по ключу. */
  createReceipt(input: ReceiptInput): Promise<ReceiptResult>;
  /** Сторнировать ранее созданный чек. */
  reverseReceipt(input: ReverseInput): Promise<ReverseResult>;
}

export interface ReceiptInput {
  /** Ключ идемпотентности: повторный вызов не создаёт второй чек. */
  idempotencyKey: string;
  /** Сумма в КОПЕЙКАХ — деньги в системе хранятся целыми минорными единицами (ADR 0004). */
  amountMinor: number;
  currency: 'RUB';
  kind: 'PREPAYMENT' | 'FINAL' | 'ADDITIONAL' | 'REFUND' | 'REVERSAL';
  method: 'CASH' | 'CARD' | 'BANK_TRANSFER' | 'ONLINE';
  /** Код магазина: чек создаётся в базе того магазина, где принята оплата. */
  storeCode: string;
  orderNo: string;
  comment?: string;
}

export interface ReceiptResult {
  /** `Ref_Key` документа 1С. */
  externalId: string;
  receiptNo: string | null;
  fiscalDocNo: string | null;
  kktShiftNo: string | null;
}
```

**Требования к реализации.** Адаптер обязан:

1. **Не бросать исключение при недоступности 1С в момент оплаты.** Приём денег и передача в
   1С разведены транзакционно (outbox, §1.2): оплата фиксируется в нашей БД, а передача
   выполняется воркером. Адаптер вызывается только воркером.
2. **Различать постоянную и временную ошибку.** `4xx` (кроме `429`) — постоянная: повтор не
   поможет, запись уходит в `DEAD` с алертом. `5xx`, таймаут, `429` — временная: retry с
   экспоненциальной задержкой.
3. **Не выполнять ретраи самостоятельно** — политика повторов принадлежит воркеру, иначе
   задержки перемножаются.
4. **Переводить минорные единицы в рубли** ровно один раз, на границе: внутри системы деньги
   целые (§1.5).

### 6.2. `TelephonyPort` (IP-АТС)

```ts
export interface TelephonyPort {
  /** Забрать записи о звонках за период (инкрементально). */
  listCalls(params: { from: Date; to: Date }): Promise<CallDto[]>;
  /** Получить аудиозапись звонка. */
  fetchRecording(externalId: string): Promise<{ stream: Readable; mime: string } | null>;
}

export interface CallDto {
  /** Идентификатор звонка в АТС. Уникален — защищает импорт от дублей. */
  externalId: string;
  direction: 'IN' | 'OUT';
  phoneFrom: string | null;
  phoneTo: string | null;
  /** Внутренний номер сотрудника — повышает точность сопоставления (§2.3). */
  extension: string | null;
  startedAt: Date;
  durationSec: number;
}
```

**Требования к реализации.** Адаптер обязан:

1. Возвращать звонки **идемпотентно**: повторный импорт того же периода не создаёт дублей
   (`CallRecording.externalId` уникален, импорт идёт upsert).
2. Нормализовать телефоны **до** передачи: сопоставление идёт по
   `Customer.phoneNormalized`, и номер в произвольном формате его не найдёт.
3. Не тянуть аудио при `listCalls` — запись скачивается отдельно
   (`fetchRecording`) и только для тех звонков, что решено хранить: трафик и место.
4. Возвращать `null` из `fetchRecording`, если запись недоступна (истёк срок в АТС): это
   штатная ситуация, а не ошибка импорта.

### 6.3. Общее правило для всех портов

**Порт не знает о Prisma и о транзакциях.** Он получает простые структуры и возвращает
простые структуры; запись в БД выполняет вызывающий код в своей транзакции. Это позволяет
подменять адаптер в тестах in-memory реализацией и не тащить внешнюю систему в транзакцию.

## 7. Тестирование интеграций

| Уровень | Что проверяем |
|---------|---------------|
| Unit | Нормализация телефонов, скоринг сопоставления, расчёт retry-задержек |
| Contract | Схемы запросов/ответов 1С и АТС против записанных фикстур (Pact-подобно) |
| Integration | Очередь outbox на реальном Redis: ретраи, DEAD-статус, SKIP LOCKED при 3 воркерах |
| Fault injection | 1С недоступна 2 часа → платежи приняты, очередь выросла, после восстановления всё ушло |
| E2E | Приём оплаты → подтверждение → отражение в карточке и отчёте |

Для приёмки с заказчиком готовится **стенд интеграции** с тестовой базой 1С и тестовой АТС.
