# Утверждённые справочные документы заказчика

Здесь лежат документы, присланные заказчиком как **утверждённые**, и их машинные
представления. Это источник данных, а не иллюстрация: цены и формулировки из этих
файлов попадают в квитанции клиентам.

## Прейскурант

| Файл | Что это |
|------|---------|
| `Прейскурант-Ремонт-утверждённый.docx` | исходный документ заказчика, 24 позиции |
| `price-list-baseline.json` | те же данные, извлечённые из `.docx` машинно |

`price-list-baseline.json` — **не резервная копия и не второй источник правды.**
Это базис для автоматической сверки: тест `packages/db/prisma/price-list-spec.spec.ts`
сравнивает с ним описание прейскуранта в коде (`packages/db/prisma/price-list-spec.ts`).

### Зачем нужен отдельный базис

Цены переносятся из документа в код вручную, и ошибка на порядок (900 вместо 9000)
не ломает ни сборку, ни типы, ни интерфейс — она просто выставляет клиенту неверную
сумму. В 24 строках с двумя колонками такую ошибку глазами не найти.

Тест ловит три класса ошибок, каждый проверен намеренным внесением дефекта:

| Ошибка | Ловится |
|--------|---------|
| Цена завышена/занижена (900 → 9000) | «цены по золоту и серебру совпадают с документом» |
| Признак «от» взят из названия, а не из колонки цены | «признак „от“ определяется по колонке цены, а не по названию» |
| Золото и серебро перепутаны местами | «цены совпадают с документом» + «золото не ниже серебра» |

### Как перепроверить, что базис не подогнан под код

Базис извлекается из самого `.docx`, поэтому проверку можно повторить с нуля:

```bash
python3 - <<'PY'
import xml.etree.ElementTree as ET, re, json, zipfile
W='{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'
with zipfile.ZipFile('docs/reference/Прейскурант-Ремонт-утверждённый.docx') as z:
    root=ET.fromstring(z.read('word/document.xml'))
body=root.find(W+'body')
tx=lambda el: ''.join(t.text or '' for t in el.iter(W+'t'))
rows=[[tx(c).strip() for c in r.findall(W+'tc')] for r in body.findall(W+'tbl')[0].findall(W+'tr')]
for r in rows:
    if r and r[0].isdigit():
        print(f"{r[0]:>3}  золото={r[2]:<10} серебро={r[3]:<10} {r[1]}")
PY
```

Сравните вывод с `price-list-baseline.json`. Совпадение означает, что базис
соответствует документу и тест проверяет именно то, что нужно.

### Особенности документа, учтённые в модели

Их легко потерять при переносе, поэтому они зафиксированы и в коде, и в тестах:

1. **Две цены на каждую услугу** — «Золото» и «Серебро». Металл сданного изделия
   выбирает ставку (ADR 0009).
2. **5 позиций с ценой «от»** — № 10, 18, 19, 20, 24.
3. **3 позиции со стоимостью металла отдельно** — № 15, 17, 24. Позиция 24 имеет
   оба признака одновременно.
4. **3 позиции тарифицируются за грамм** — № 21, 22, 23 (родирование, золочение).
5. **Ловушка:** в позиции 6 («...кольца **от 0,5 размера**...») слово «от» относится
   к размеру, а цена фиксированная (1425/825). Признак «от» определяется по ячейке
   цены, а не по названию.

### Загрузка прейскуранта в развёрнутую базу

`npm run db:seed` заполняет только **пустую** базу и пропускает уже созданные
сущности, поэтому для действующей системы есть отдельный идемпотентный скрипт:

```bash
npx tsx packages/db/prisma/apply-price-list.ts
```

Он приводит версию 1 в `APPROVED`, заменяет позиции и ставки, удаляет пустые
категории и восстанавливает ссылки работ демонстрационного заказа. Повторный
запуск безопасен.
