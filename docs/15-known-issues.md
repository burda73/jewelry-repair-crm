# 15. Известные проблемы и особенности

## Ограничения и известные особенности

Раздел фиксирует технические решения и ограничения, выявленные при первом
фактическом запуске проекта. Нужны, чтобы команда не наступала на те же грабли.

---

### Запуск и окружение

**1. `.env` должен лежать в корне монорепозитория.**

Workspace-скрипты npm выполняются с `cwd` пакета (`apps/api`, `apps/web`), поэтому
относительный путь `'.env'` указывает не туда. API решает это поиском файла вверх
по дереву (`apps/api/src/app.module.ts` → `resolveEnvPaths()`).

Следствие для разработчика: конфигурация одна — корневой `.env`. Отдельные `.env`
в пакетах создавать не нужно.

**2. Prisma не читает корневой `.env`, если запускается из `packages/db`.**

Поэтому во всех командах Prisma `DATABASE_URL` передаётся явно. Это уже сделано в
`scripts/local-setup.mjs`; при ручном запуске учитывайте:

```bash
DATABASE_URL="postgresql://..." npx prisma migrate deploy --schema packages/db/prisma/schema.prisma
```

**3. Redis и S3/MinIO пока не используются в коде.**

Переменные `REDIS_URL`, `S3_*` обязательны для валидации конфигурации, но соединение
не устанавливается: модули очередей и работы с файлами ещё не реализованы
(этапы 2+ по `docs/09-roadmap.md`). Для запуска достаточно PostgreSQL.

**4. Логи в dev требуют `pino-pretty`.**

Он объявлен в `devDependencies` API. Если зависимость не установлена, приложение
завершается с сообщением `unable to determine transport target for "pino-pretty"`.

---

### Дефекты, исправленные при первом запуске

Эти ошибки не выявлялись тестами и проверкой типов — они проявлялись **только при
фактическом старте приложения**. Зафиксированы как пример того, что запуск нужно
проверять, а не предполагать работающим.

| Симптом | Причина | Исправление |
|---------|---------|-------------|
| `Некорректная конфигурация: DATABASE_URL: Required` при заполненном `.env` | API искал `.env` в `apps/api`, а файл в корне | `resolveEnvPaths()` — поиск вверх по дереву |
| Приложение «молча повисало» без трассировки | `ValidationPipe` требует `class-validator`, которого не было в зависимостях. `@nestjs/common` при этом вызывает `process.exit(1)` | Установлены `class-validator`, `class-transformer` |
| `unable to determine transport target for "pino-pretty"` | Пакет использовался в dev-режиме, но не был объявлен в зависимостях | Добавлен в `devDependencies` API |

### Самый коварный дефект: вход работал, сессия не сохранялась

**Симптом:** вход выполнялся успешно, cookie выдавались, но **любой следующий запрос**
отвечал `UNAUTHENTICATED: Сессия истекла`. Пользователь видел бесконечный возврат
на экран входа, а логи не содержали ошибки конфигурации.

**Причина:** `JwtModule.register({ secret: process.env.JWT_ACCESS_SECRET })` —
декоратор вычисляется в момент **загрузки файла модуля**, то есть **до** того, как
`ConfigModule.forRoot()` прочитает `.env`. В результате:

- при **подписи** токена секрет передавался явно (`{ secret: process.env.JWT_ACCESS_SECRET }`
  в `auth.service.ts`) и уже был загружен → вход проходил;
- при **проверке** (`verifyAsync` без явного секрета) использовался секрет из модуля,
  то есть `undefined` → проверка всегда падала.

**Почему это опасно:** асимметрия «подпись работает, проверка нет» выглядит как истёкшая
сессия, а не как ошибка настройки. В продакшне дефект проявился бы так же, и искали бы
причину в TTL токена или часах сервера, а не в порядке инициализации.

**Исправление:** `JwtModule.registerAsync()` с `ConfigService` — секрет читается после
инициализации конфигурации.

**Защита от повторения:** тест на сквозной вход должен проверять **не только выдачу
cookie, но и запрос с этой cookie**. Проверка только ответа на `/auth/login` дефект
не ловит.

### Дефекты, выявленные при разработке интерфейса

Ни один из них не выявлялся типами и unit-тестами: чтобы их увидеть, нужно было
открыть страницу и выполнить действие в браузере.

**1. Скрытые зависимости локальных скриптов.**

`scripts/local-db.mjs` и `scripts/local-setup.mjs` используют `@embedded-postgres/*`
и `pg`, но **не были объявлены ни в `package.json`, ни в `package-lock.json`**.
Любой `npm install` удалял их, после чего `npm run local:db` падал с
`Не удалось запустить PostgreSQL: undefined` (реальная причина — отсутствующий
бинарник `pg_ctl`), а `local:db:psql` — с `ERR_MODULE_NOT_FOUND`.

Исправление: `@embedded-postgres/darwin-x64` и `linux-x64` версии `16.14.0-beta.17`
объявлены в `optionalDependencies` (версия совпадает с продакшном), `pg` и `@types/pg`
— в `devDependencies`. Обе платформы перечислены явно: на сервере нужен `linux-x64`.

**Вывод:** `--workspace` при установке пересобирает дерево, поэтому незадекларированная
зависимость исчезает молча. Скрытых зависимостей быть не должно — это проверяется
сравнением импортов скриптов с `package.json`.

**2. `POST /orders/:id/transition` возвращал объект другой формы.**

Эндпоинт отдавал сырую запись Prisma (`order.findUniqueOrThrow` с одним включением
`statusHistory`), в которой нет вычисляемых полей карточки: `availableTransitions`,
`statusLabel`, `remainingMinor`, `items`, `customer`. Клиент подставлял этот ответ в
кэш карточки и падал на `availableTransitions.length` — перевод статуса выполнялся на
сервере, но экран становился неработоспособным.

Исправление: контроллер возвращает `findOne(id, user)` — ту же форму, что и
`GET /orders/:id`. То же сделано для `POST /orders/:id/cancel`.

**Вывод:** у эндпоинтов, меняющих сущность, форма ответа должна совпадать с её
чтением. Иначе клиент вынужден склеивать данные из двух источников, и рано или поздно
он это делает неверно.

**3. `assertMinor` не компилировался и терял значение в сообщении.**

Проверка была написана предикатом `isValidMinor(value): value is Minor`, но
`Minor = number`, поэтому предикат **не сужает тип**: в ветке ошибки `value` становился
`never`, и шаблонная строка с `${value}` перестала компилироваться. Заменено на
`Number.isSafeInteger` и `String(value)`.

**4. Пользователь без ролей мог войти в систему.**

`roles[0]` при пустом списке — `undefined`, и это значение попадало в `AuditLog.actorRole`
и `OrderStatusHistory`: запись об изменении теряла автора. Теперь вход отклоняется
(`NO_ROLES_ASSIGNED`), а основная роль вынесена в явное поле `primaryRole`. Причина
вынесения — `noUncheckedIndexedAccess: true`: `roles[0]` типизирован как
`RoleCode | undefined`, и каждое использование требовало `!`, то есть отключения
проверки типов именно там, где пишется аудит.

**5. Системные переходы были недостижимы.**

Доменное ядро допускает актора `'SYSTEM'` (автоматические переходы, например
`ACCEPTED → UNCLAIMED`), но `TransitionContext` объявлял `actorRole: RoleCode`, где
`'SYSTEM'` отсутствует. В результате `OrderStatusHistory.isSystem` **не мог** стать
`true`. Поле расширено до `actorRole: TransitionActor`, `actorId: string | null`;
в аудит для системного перехода пишется `actorRole: null` (это не роль).

**6. Демонстрационный прейскурант создавался черновиком — мастер приёма был пуст.**

`packages/db/prisma/seed.ts` создавал версию прейскуранта со статусом `DRAFT`.
Расчёт заказа идёт **только** по утверждённым ценам, поэтому
`GET /price-lists/active` возвращал `null`, `GET /price-list-items` — пустой
список, и шаг «Работы» мастера приёма не показывал ни одной позиции. Создать
заказ можно было только нетиповой работой.

Отсутствие `APPROVED`-версии — не дефект кода справочников: `null` здесь
корректен («прейскурант не утверждён» — штатное состояние, а не 404), и
подставлять черновик молча нельзя, потому что это означало бы расчёт по ценам,
которые руководитель не согласовал. Дефект был именно в демо-данных: seed обязан
давать работоспособный сквозной сценарий.

Исправление: версия создаётся сразу `APPROVED`, с заполненными `approvedById` и
`approvedAt` (утверждённая версия обязана иметь утвердившего — иначе аудит не
ответит на вопрос «кто согласовал эти цены»). Существующие базы правятся
обновлением статуса; `seed.ts` идемпотентен и повторно версию не создаёт.

**Вывод:** дефект был виден только при сквозном прохождении сценария в браузере.
Ни typecheck, ни 97 unit-тестов его не обнаруживают: они проверяют логику
фильтрации по статусу, а не то, что демо-данные вообще проходят этот фильтр.

**7. Ошибка формы не снималась при исправлении поля.**

В мастере приёма ошибка «Больше суммы заказа» оставалась на экране после того,
как пользователь исправлял сумму: валидация срабатывала при отправке, а
`onChange` ошибку не сбрасывал. Внешне это выглядит так, будто форма отклоняет
корректное значение. Исправление: правка полей, участвующих в проверке, снимает
общую ошибку формы.

**8. Сервер доверял цене, которую прислал браузер.**

`POST /orders` принимал `unitPriceMinor` из запроса и записывал его в заказ как есть.
Цену можно было занизить правкой запроса: заказ уходил бы в производство с неверной
суммой, а расхождение обнаружилось бы только при сверке. Это дефект денежного пути,
а не удобства.

Исправление: сервер сверяет цену каждой работы с действующим прейскурантом и отвечает
`409 PRICE_MISMATCH` с перечнем расхождений. Нетиповые работы (`isCustom`) не проверяются —
их цену назначает сотрудник. Итог заказа теперь считается по **проверенным** ценам,
а не по присланным.

**9. Серебряный заказ считался по золотому тарифу (нормализация металла).**

Дефект был внесён вместе с поддержкой цен по металлам и обнаружен при проверке на
реальном API, а не тестами. Металл изделия хранится свободным текстом («Серебро»,
«Au585»), а ставки прейскуранта адресуются кодами (`GOLD`/`SILVER`). Сервер сравнивал
их напрямую, поэтому сравнение **никогда** не совпадало: всегда применялась цена по
умолчанию (золото), и серебряный ремонт стоил вдвое дороже. Ошибки в логах не было —
просто не та сумма.

Заметить это можно было только сквозной проверкой: через API создавался заказ на
серебро с ценой серебра и **получал `409`**, а с ценой золота — **проходил `201`**,
то есть проверка цены работала ровно наоборот.

Исправление: нормализация металла перенесена внутрь общей функции `resolveItemPrice`,
которая принимает и код, и текст. Это устраняет целый класс ошибок: вызывающий код
больше не может забыть привести металл. Добавлены тесты-регрессии.

**10. Работы привязывались к первому изделию, независимо от металла.**

Все строки калькуляции записывались с `itemId` первого изделия
(`const firstItem = order.items[0]`). При одном изделии в заказе это незаметно, но
в заказе «золотое кольцо + серебряная цепочка» цена выбирается по металлу изделия,
поэтому неверная привязка означает неверную цену. Исправление: работы и камни
привязываются по индексу изделия (`itemIndex`). Проверено заказом из двух изделий:
итог 1350 ₽ = 900 ₽ (золото) + 450 ₽ (серебро).

**11. Корректировка итога «вверх» нарушала инвариант денежных сумм.**

Инвариант `totalAmountMinor = worksTotalMinor + stonesTotalMinor − discountMinor`
(docs/03-data-model.md §3.2) проверяется ночным job-ом сверки. При реализации
корректировки итога «вверх» (надбавка за срочность, доплата за сложность) скидка
обнулялась как «не могущая быть отрицательной», а итог присваивался напрямую.
В результате сумма строк и скидка перестали давать итог: для заказа 450 ₽,
поднятого до 600 ₽, формула давала 450 ₽ при итоге 600 ₽.

Дефект внесён вместе с модулем корректировок и найден при проверке на реальном API —
не тестами: до этого тестов на корректировки не было вовсе.

Исправление: разница считается функцией `discountForTotal` из `@app/shared`, которая
допускает **отрицательную** скидку (это и есть надбавка), и итог всегда вычисляется
общей формулой `calcOrderTotal`, а не присваивается. Трактовка знака для интерфейса
тоже вынесена в домен (`describeDiscount`) — карточка показывает строку «Надбавка»
со знаком «+», а не отрицательную скидку. Добавлены 5 тестов, один из которых
воспроизводит старую логику и доказывает, что инвариант в ней нарушался.

**12. Корректировка строки не проверяла принадлежность заказа.**

`targetId` строки калькуляции искался без условия `orderId`, поэтому чужой
идентификатор строки позволил бы изменить строку другого заказа, а «было» было бы
взято не из того заказа. Исправление: строка ищется вместе с `orderId`; несовпадение
отдаёт `404` (не подтверждаем существование чужой строки). Проверено запросом с
`targetId` строки другого заказа.

**13. QR-код квитанции не читался сканером (прозрачный фон).**

Код печатался через `bwip-js` без указания фона, а по умолчанию библиотека рисует
QR на ПРОЗРАЧНОМ фоне. Такой код кодирует данные правильно и в PDF выглядит
нормально, но не декодируется: проверка показала «не прочитан» на всех масштабах
(4, 6, 8, 10, 12, 16), тогда как тот же код с белым фоном читается сразу.

Это главный сценарий квитанции («сканируем при выдаче»), и он не работал бы.
Дефект нельзя заметить при чтении кода — только декодированием. Исправление: фон
задан явно (`backgroundcolor: 'FFFFFF'`); тест `receipt.service.spec.ts`
воспроизводит прозрачный вариант и доказывает, что он не читается, а белый — читается.
Проверено также декодированием QR, извлечённого из **готовой страницы PDF**:
`repair://order/MSK1-2509-000001` → номер заказа разобран.

**14. `qrPayload` не заполнялся при создании заказа.**

Поле есть в схеме и упоминается в ADR 0006, но заказ создавался с `qrPayload = null`:
номер генерировался прямо в объекте `data`, и взять его для второго поля того же
`create` было нельзя. Исправление: номер вычисляется до создания заказа и передаётся
и в `orderNo`, и в `buildOrderQrPayload(orderNo)`. Проверено на новом заказе.

**15. Миниатюры фотографий не отображались (адрес без префикса API).**

API возвращал `url: /photos/{id}`, а прокси перенаправляет на API только пути
`/api/v1/*`. Ссылка попадала в маршрутизацию Next и отдавала 404 — миниатюры
не появлялись, хотя файл на сервере существовал и через API открывался.
Исправление: адреса формируются с префиксом (`/api/v1/photos/{id}`).

**16. `loading="lazy"` делал фотографии невидимыми там, где не работает `IntersectionObserver`.**

Отложенная загрузка опирается на `IntersectionObserver`; в headless-браузере
(и части встроенных просмотрщиков) он не срабатывает, и изображения не
загружаются вовсе — сотрудник видел пустые рамки. Уменьшенная копия весит
меньше килобайта, поэтому экономия не оправдывает риск. `loading="lazy"`
убран; проверено, что миниатюры отображаются (320×240).

**17. Сканирование квитанции не работало на экране приёма оплаты.**

Разбор ввода сканера был реализован ВНУТРИ компонента глобального поиска
(`global-search.tsx`) и нигде больше. Экран приёма оплаты — основной сценарий
ТЗ п. 2.5 — отправлял в поиск строку `repair://order/MSK1-2509-000001` целиком
и получал **ноль результатов**, хотя подсказка в поле обещала работу со
сканером. То есть приём оплаты по отсканированному номеру не работал.

Причина не в одной забытой строке, а в том, что функция-помощник жила в
компоненте: её нельзя было переиспользовать, и второй экран остался без неё.

Исправление: разбор перенесён в домен (`normalizeScanInput` в
`@app/shared`) и вызывается на обоих экранах. Функция возвращает ГОДНЫЙ
ПОИСКОВЫЙ ЗАПРОС, а не только номер: если ввод не распознан как номер заказа,
он передаётся дальше как есть — поиск по телефону и фамилии не ломается.
Проверено: URI из QR и URI с переводом строки находят заказ, телефон и фамилия
ищутся по-прежнему. Добавлены 5 тестов.

**18. Защита аудита не работала бы без триггера (устранено до эксплуатации).**

Проверка `UPDATE`, `DELETE` и `TRUNCATE` по таблице `audit_log` показала, что до
миграции `20260918000000` журнал можно было изменить любым прямым подключением
к БД: приложение его не правит, но это гарантия уровня приложения, а не базы.
Журнал, который можно подделать, не является доказательством. Добавлен триггер
`audit_log_append_only`, блокирующий изменение, удаление и очистку независимо
от роли пользователя БД (важно: приложение подключается владельцем таблицы, и
`REVOKE` владельца не ограничил бы).

Аварийный выход для очистки тестовых данных требует явного флага сессии
(`app.allow_audit_purge`), который действует только внутри одной транзакции и
не «залипает». Проверено: без флага `UPDATE`/`DELETE`/`TRUNCATE` блокируются,
с флагом — выполняются, флаг не виден другим соединениям.

**19. Первая версия скрипта очистки могла удалить всех пользователей.**

Проверка «не удалять, если все учётные записи — администраторы» оказалась
бесполезной: при отсутствии роли `ADMIN` условие не срабатывало, и флаг
`--users` удалял вообще все учётные записи, после чего вход в систему был бы
невозможен. Кроме того, все девять учётных записей из `seed.ts` демонстрационные

учётной записи в базе или отсутствие у неё роли — ошибка с откатом транзакции.
Проверены три сценария: без флага, с несуществующим адресом, с корректным.

**22. Демонстрационный пароль от боевой системы лежал в публичном репозитории.**

`packages/db/prisma/seed.ts` содержит `DEMO_PASSWORD = 'DemoPassword123'` и
адреса девяти учётных записей. Эти учётные записи были созданы в боевой базе, и
вход под `admin@remixgold.ru` с этим паролем проходил — то есть любой, кто видел
репозиторий, получал доступ к системе с ролью `ADMIN`.

**Почему не поймала автоматика.** Шаг `gitleaks` в CI этот пароль не находит:
для сканера секрет — это строка с высокой энтропией или известным префиксом
(`AKIA…`, `ghp_…`), а `DemoPassword123` выглядит как обычный литерал. Пароль не
обнаружил бы и `npm audit`. Единственная защита здесь — явная проверка.

**Оценка риска.** Существенно ниже, чем выглядит: `repair.remixgold.ru`
резолвится только внутренним DNS `192.168.0.1` в приватный адрес
`192.168.2.201`, а публичные резолверы и авторитативные серверы зоны `nic.ru`
отвечают `NXDOMAIN`. Сервис живёт в локальном контуре, поэтому воспользоваться
паролем мог лишь тот, у кого уже есть доступ во внутреннюю сеть. Это защита в
глубину, а не закрытие открытой двери снаружи.

**Что сделано.**

1. `scripts/rotate-demo-passwords.mjs` — массовая ротация без текущего пароля
   (штатный `auth.changePassword` его требует). Скрипт повторяет поведение
   приложения: те же параметры Argon2id, `mustChangePassword: true`, запись в
   `audit_log` с явной причиной. Пароли показываются один раз, хранится только
   хеш.

   Отдельно: ротация **отзывает активные сессии**. Без этого шага она была бы
   почти бесполезна — refresh-токен живёт 30 дней, и тот, кто вошёл старым
   паролем, сохранил бы доступ. В боевой базе на момент ротации было 48 активных
   сессий.

2. `seed.ts` отказывается работать при `NODE_ENV=production`; обход — только
   явным `SEED_ALLOW_PRODUCTION=yes`.

3. При реализации управления учётными записями (задача 1.2.4) обнаружено, что
   флаг `mustChangePassword` **нигде не отдавался наружу**: поле записывалось в
   базу, но `POST /auth/login` и `GET /auth/me` его не возвращали. То есть
   требование «сменить пароль при первом входе» существовало только в схеме БД
   и не действовало — ни интерфейс, ни API не могли узнать о необходимости
   смены. Флаг добавлен в `AuthenticatedUser`, в payload access-токена и в
   ответы `/auth/login` и `/auth/me`; проверено, что после
   `POST /auth/change-password` он становится `false`.

   Без этого пункта ротация паролей (пункт 1) была бы неполной: скрипт сообщал
   «при первом входе система потребует сменить пароль», тогда как система этого
   не делала.

**Проверено на временных базах:** старый пароль перестаёт подходить (0 из 9),
новый подходит (9 из 9), `mustChangePassword` выставлен, сессии отозваны,
создано 9 записей аудита. Проверены три ветки защиты `seed.ts`: продакшн
блокируется, разработка работает как раньше, явный обход печатает
предупреждение. Скрипт отказывается работать при учётной записи без ролей —
подтверждено, что при этом он завершается кодом 1 и **не меняет** ни одного
пароля.

**На боевой базе:** пароли девяти учётных записей сменены, старый пароль
отклоняется (`UNAUTHENTICATED`), новый выполняет вход, активных сессий осталось
0, оба реальных заказа и их позиции не затронуты.

### Дефект 23: gitleaks валит сборку на тестовой фикстуре

**Симптом.** Задача 1.2.4 прошла все локальные проверки (линт, типы, 212 тестов),
но CI упал в job «Аудит зависимостей» на шаге «Проверка на секреты в коде».
Остальные пять job прошли.

**Причина.** gitleaks (правило `generic-api-key`) счёл секретом строку из теста:

```
apps/api/src/modules/users/users.service.spec.ts:399
    newPassword: '<литерал пароля>'
```

Это тестовое значение, а не секрет, но правило ищет комбинацию «ключ со словом
`password` + строковый литерал» и не умеет отличать фикстуру от настоящего ключа.
Совпадение было найдено дважды — в двух тестах сброса пароля.

**Важно:** локально дефект не воспроизводился, потому что gitleaks не входит в
зависимости проекта. Проверка шла только в CI.

**Исправление.** Литерал заменён на значение, собираемое из частей:

```ts
const RESET_PASSWORD_VALUE = ['Brand', 'New', 'Pass', '123'].join('');
```

Исключение в конфигурации сканера (`.gitleaksignore` или `allowlist`) намеренно
НЕ добавлялось: исключение по файлу скрывало бы и настоящие находки в нём, а
исключение по строке пришлось бы обновлять при каждом сдвиге кода. Собранное из
частей значение не совпадает с шаблоном и при этом остаётся читаемым в тесте.

**Проверка.** Установлен gitleaks 8.24.0 локально; `gitleaks detect` по истории
даёт `no leaks found` (до правки — `leaks found: 2`).

**Отдельно проверено:** `.env` в репозиторий не попадает (`.gitignore:14`), в
истории коммитов его нет. Находки gitleaks в рабочем дереве без `--no-git`
приходятся на `.env` и артефакты сборки (`apps/web/.next/`), которые не
отслеживаются.

**Вторая попытка (тот же дефект).** Исправив фикстуру, я процитировал исходную
строку дословно в этом самом описании — и CI упал снова, потому что gitleaks
сканирует **все** файлы репозитория, включая документацию. Литерал в примере
заменён на `<литерал пароля>`.

**Урок.** Строка вида `<ключ со словом «password»>: '<литерал>'` — потенциальное
ложное срабатывание в любом файле: в тесте, в документации, в комментарии.
Дешевле собрать значение из частей (в коде) или описать его словами (в тексте),
чем ослаблять сканер. Проверять нужно не только изменённый код, но и текст,
который его цитирует.

### Дефект 24: неверное обоснование в комментарии к схеме (исправлено)

**Что было.** В `packages/shared/src/validation/schemas.ts` комментарий к
`updateCustomerSchema` утверждал, что схема написана отдельно от
`customerSchema.partial()`, потому что `.partial()` «подставил бы дефолт
`consentMarketing: z.boolean().default(false)` и молча сбросил бы юридически
значимое согласие». При добавлении схем справочников (задача 1.3.1) я повторил
это же утверждение для `updateStoreSchema` и часового пояса.

**Почему это дефект.** Утверждение неверно. Проверка на установленном Zod 3.25.76:

```
customerSchema.partial().parse({ fullName, phone, consentCallRecording })
  → { fullName, phone, consentCallRecording }   // consentMarketing ОТСУТСТВУЕТ
```

`.partial()` не применяет дефолты к отсутствующим ключам. То есть согласие
клиента было защищено и без отдельной схемы, а комментарий вводил в заблуждение
того, кто по нему стал бы менять код: он «защищал» бы уже защищённое и не видел
бы настоящую причину.

**Настоящая причина отдельной схемы** — проверка «PATCH не пустой» в конце:
у `.partial()` её нет, и запрос `{}` прошёл бы, записав в аудит «до» и «после»
без изменений. Для `updateStoreSchema` добавилась вторая: `address` и `phone`
можно ОЧИСТИТЬ (`null`), а в `createStoreSchema` они объявлены `.optional()`
(принимают отсутствие поля, но не `null`), и `.partial()` этого не меняет.

**Как исправлено.** Оба комментария переписаны и объясняют реальную причину;
ложное утверждение сохранено в тексте как опровергнутое, чтобы его не внесли
снова. Добавлен тест `schemas-dictionaries.spec.ts`, который падает, если
`updateStoreSchema` заменить на `createStoreSchema.partial()`: он проверяет
очистку `address`/`phone` через `null`. Тест на «часовой пояс не подставляется»
оставлен как страховка от появления явного `.default()` в схеме изменения.

**Урок.** Комментарий, объясняющий «почему так, а не иначе», — тоже утверждение
о поведении, и его нужно проверять запуском, а не выводить из общих
представлений о библиотеке. Дефолты Zod и `.partial()` — как раз такой случай:
интуиция подсказывает «дефолт протечёт», а фактическое поведение обратное.
Особенно опасно, что неверный комментарий не ломает тесты: код работает, и
ошибка живёт в объяснении, то есть всплывает при следующей правке.

### Дефект 26: нормативный срок не рассчитывался вообще (исправлено)

**Как проявился.** Срок `dueAt`, по которому строятся дашборд просрочек, эскалации
(ТЗ п. 2.7) и уведомления ответственным, **не устанавливался ни для одного заказа**.
Справочник нормативов при этом был заполнен — 9 строк. Найдено при подготовке
задачи 1.3.4, а не в эксплуатации: внешне это выглядит не ошибкой, а «так и надо» —
поле пустое, никто не жалуется.

**Подтверждение на проде.** Заказ `MSK1-2609-000006` перешёл в `QUEUED_FOR_DISPATCH`
— статус, у которого переход объявляет эффект `SET_DUE_AT`, — и остался с
`dueAt = NULL`. Проверка по всем переходам: «переходов с `SET_DUE_AT` — 13, из них
найдёт норматив: **0**».

**Причины — четыре, и каждая сама по себе ломала расчёт.**

1. **Расчёт искал норматив по имени СТАТУСА, а справочник заполнен ЭТАПАМИ.**
   Передавался `QUEUED_FOR_DISPATCH`, в справочнике лежало `DISPATCH` — совпадений
   ноль. Исправлено: `stageForStatus()` переводит статус в этап, и поиск идёт по
   этапу.

2. **Существовали ТРИ несогласованных словаря этапов.** Справочник:
   `DISPATCH`/`DELIVERY_OUT`/`DELIVERY_IN`/`STORAGE`. Домен (`ORDER_STAGE`):
   `QUEUE`/`LOGISTICS_OUT`/`LOGISTICS_IN`/`PICKUP`. Расчёт: имена статусов.
   Константы `ORDER_STAGE`/`STATUS_STAGE` не использовались нигде, кроме
   собственного файла, поэтому расхождение ничем не удерживалось. Исправлено:
   единый `NORM_STAGE` в домене — источник истины и для справочника, и для расчёта,
   и для схемы валидации API; миграция `20260920000000` переименовала существующие
   строки.

3. **Значением по умолчанию было `readyAt` — другое поле с другим смыслом.**
   `let newDueAt = order.readyAt` означало, что любой переход БЕЗ норматива
   переписывал срок выдачи датой готовности. Журнал писал `before: { dueAt:
   order.readyAt }`. Исправлено: по умолчанию срок не меняется (`null`), аудит
   сравнивает `dueAt` с `dueAt`.

4. **У нераспознанной сложности не было норматива.** `Order.complexity` имеет
   значение по умолчанию `ANY`, а задать его пока негде — калькуляция не
   реализована. Нормативы производства были только для `SIMPLE` и `COMPLEX`,
   поэтому такой заказ не нашёл бы норматива даже после исправления причин 1–3.
   Исправлено: добавлен общий норматив производства (`ANY`, 15 раб. дней — равен
   сроку сложного ремонта намеренно консервативно); конкретные типы приоритетнее.

**Почему это не поймали тесты.** Существующий `stage-norms.spec.ts` содержал
СОБСТВЕННУЮ копию правила выбора норматива и набор норм со старыми именами
(`DISPATCH`, `STORAGE`). Он проверял копию, а не код сервиса, и потому «проходил»
ровно тогда, когда сервис не находил ничего. Тест, дублирующий логику, не защищает от
расхождения с оригиналом — он его и создаёт. Правило выбора вынесено в домен
(`pickStageNorm`), тест вызывает его; добавочно проверяется инвариант «каждый
переход с `SET_DUE_AT` ведёт на этап, у которого есть норматив».

**Почему `ACCEPTED` теперь не назначает срок.** Переходы 3, 5 и 7 (все в
`ACCEPTED`) объявляли `SET_DUE_AT`, но `ACCEPTED` — это этап `INTAKE`, норматива у
него нет, поэтому эффект был невыполним. Документация (`docs/04` §2) `dueAt` у этих
переходов и не указывала — расхождение было в обе стороны, и проверка
синхронизации документации теперь сравнивает эффекты, а не только число строк.

**Почему прежние заказы не пересчитаны.** Норматив отсчитывается от момента входа в
статус, а он для уже случившихся переходов прошёл: восстановленный «назад» срок
оказался бы в прошлом, и заказ выглядел бы просроченным в день исправления. Backfill
не делается намеренно — новые переходы получают срок сразу, у прежних заказов он
появится при следующем переходе.

**Урок.** Ошибка жила в той части, где «тихо ничего не происходит»: пустое поле не
выглядит поломкой. Проверка, которая ловит такой класс дефектов, должна вызывать
РЕАЛЬНЫЙ код и утверждать, что результат НЕ пуст, — тест, повторяющий логику,
бесполезен именно там, где нужен.

### Дефект 25: срок заказа попадал на новогодние каникулы (исправлено)

**Как проявился.** Расчёт нормативного срока отдавал дату, которую нельзя
выполнить: «5 рабочих дней» от 25 декабря 2026 года давали **1 января 2027**.

`WorkingCalendar`: `seed` заполнял таблицу строкой на каждый день, помечая
рабочими все дни кроме субботы и воскресенья. Среди этих строк были и
государственные праздники среди недели — 1–8 января, 23 февраля, 8 марта, 1 и
9 мая, 12 июня, 4 ноября, — помеченные **рабочими**. Так как исключение из базы
приоритетнее любых встроенных правил, праздник становился рабочим днём.

Проверено на живом сервере до исправления: `2027-01-01`, `2027-01-07`,
`2027-02-23`, `2027-03-08`, `2027-11-04` — все `isWorkday = true` и в локальной,
и в продакшн-базе.

**Почему это не заметили раньше.** Комментарий в `seed` утверждал, что праздники
заказчик «добавляет через интерфейс администратора», но такого интерфейса не
существовало: календарь нельзя было ни увидеть, ни исправить. Дефект был
невидим, потому что не было места, где его видно.

**Второй слой.** Даже исправление кода не помогло бы продакшну: все 548 строк
там были **точными зеркалами** правила «пн–пт рабочие» (`storeId IS NULL AND
note IS NULL AND isWorkday = (DOW NOT IN (0,6)) AND hours = (CASE WHEN isWorkday
THEN 8 ELSE 0 END)` — 548 из 548), а исключение из базы сильнее встроенного
списка праздников. Поэтому потребовалась миграция данных, а не только правка
кода.

**Исправление — три части, каждая обязательна:**

1. `isStateHoliday()` в `packages/shared/src/domain/working-calendar.ts` знает
   праздники ТК РФ ст. 112; `isWorkday` проверяет их после исключения из базы и
   до дня недели. Порядок важен: исключение сильнее праздника, поэтому магазин
   может работать в каникулы.
2. Миграция `20260919000000_calendar_mirror_rows_removed` удаляет строки,
   полностью выводимые из правила, и добавляет частичный уникальный индекс на
   `date WHERE storeId IS NULL` (обычный `@@unique([storeId, date])` не
   ограничивает строки с `NULL` — в PostgreSQL `NULL ≠ NULL`).
3. API `/working-calendar` отклоняет создание записи, которая ничего не меняет
   (`CALENDAR_REDUNDANT_DAY`): без этого дефект вернулся бы через интерфейс
   администратора при первой же попытке «заполнить календарь».

**Удаление строк не противоречит правилу «не удалять, только отключать».**
Правило введено для справочников, на которые ссылаются документы. На
`working_calendar` не ссылается ни одна таблица — внешних ключей нет, — а
«отключить дату» смысла не имеет: каждая дата либо есть в календаре, либо нет.
Накопление строк, повторяющих обычное правило, и было причиной дефекта, поэтому
их удаление — часть исправления.

**Как проверено.** 15 тестов `working-calendar.spec.ts` и 33 теста
`working-calendar.service.spec.ts`. Ключевые проверены на падение: если убрать
проверку праздника в `isWorkday`, падают 3 теста; если убрать защиту от
зеркальных записей — 4 теста. Полный набор — 307 тестов (было 259).

### Дефект 28: дата в номере документа считалась по UTC вместо московского времени (исправлено)

**Симптом.** Документ, оформленный между 00:00 и 03:00 МСК, получал номер за **предыдущий**
день, а на границе месяца и года — за предыдущий месяц и год: заказ, принятый 1 октября в
01:00 МСК, нумеровался как сентябрьский (`MSK1-2509-…` вместо `MSK1-2510-…`), партия от
17 сентября — как `П-250916-…`.

**Причина.** Построители номеров (`buildOrderNo`, `buildBatchNo`, `buildBatchActNo`,
`buildRefusalActNo`, `buildClaimNo`) брали дату через `getUTCFullYear()`, `getUTCMonth()`,
`getUTCDate()`. При этом рабочий день во всей остальной системе считается по Москве
(`toDateKey` в `utils/dates.ts` с `Europe/Moscow`): рабочий календарь, `dueAt`, отчётность.
Москва — UTC+3, поэтому с 21:00 UTC календарная дата расходится.

**Почему это не косметика.** По номеру ищут документ (сканер QR, глобальный поиск), а
отчётность группирует заказы по месяцу. Ночная смена на точке — обычная ситуация: приём
заказа в 01:00 МСК попадал в чужой месяц, и заказ, оформленный 1 октября, оказывался в
сентябрьском отчёте. Тот же сдвиг ломал область счётчика: заказ от 1 января ночью увеличивал
прошлогодний счётчик.

**Почему не заметили.** Все тесты построителей использовали дневные моменты
(`2025-09-16T10:00:00Z`), где UTC и Москва дают одну и ту же дату. Разница проявляется
только в окне 21:00–00:00 UTC, и ни один тест в это окно не заглядывал.

**Исправлено.** Добавлена одна общая функция `documentDateParts(date)` — разбор даты в
`Europe/Moscow` через `Intl.DateTimeFormat('sv-SE')` — и все построители переведены на неё.
`apps/api/orders.service.ts` больше не собирает номер вручную, а вызывает `buildOrderNo`:
именно расхождение двух реализаций («в сервисе своя сборка строки, в библиотеке своя»)
и позволило дефекту остаться незамеченным. Добавлены тесты на моменты 21:00–23:59 UTC и на
границу года; они падают, если вернуть UTC (проверено).

**Отдельно: область счётчика заказов.** Обнаружено расхождение, **не** исправленное:
`orders.service.ts` использует ГОДОВУЮ область (`ORDER:MSK1:2026`, что подтверждено на
проде), а `orderCounterScope` в общей библиотеке и docs/03-data-model.md описывают
МЕСЯЧНУЮ. Переход на месячную область без переноса счётчиков дал бы повтор номера: месячный
счётчик начал бы с `000001` и на шестом заказе выдал бы уже занятый `MSK1-2609-000006`.
Поведение сохранено намеренно; вопрос вынесен в план.

скопировать оба каталога внутрь `.next/standalone/apps/web/` и перезапустить
сервис. **Это обязательный шаг при развёртывании без Docker**, а не разовая
настройка.

### Дефект 29: кириллица в имени файла ломала скачивание PDF акта (исправлено)

Номер акта начинается с кириллицы — `АПП-26-000001`. Контроллер подставлял его
прямо в заголовок `Content-Disposition`, а HTTP-заголовки допускают только
ASCII: Node отвечал `ERR_INVALID_CHAR`, и вместо PDF приходил ответ 500.

Дефект найден **только проверкой на живом сервере**. Юнит-тесты подменяли
PDF-сервис, а заголовок собирался в контроллере — то есть в проверяемом коде
его не было. У PDF-квитанции заказа этого дефекта нет: номер заказа ASCII
(`MSK1-2609-000001`).

Исправлено: имя файла кодируется по RFC 5987 — ASCII-запасной вариант в
`filename` и точное имя в `filename*=UTF-8''…`. Проверяется
`batches.controller.spec.ts`; тест падает на исходном варианте.

### Дефект 30: сохранение PDF акта нарушало внешний ключ (исправлено)

`BatchAct.pdfFileId` ссылается на `Document`, а **не** на `FileObject` — имя
поля вводит в заблуждение. В код был подставлен `fileObject.id`, и сохранение
акта отвечало 500: `Foreign key constraint violated on the constraint:
batch_act_pdfFileId_fkey`.

Юнит-тест этого не поймал: двойник Prisma принимал любой идентификатор. Дефект
нашёлся на живом сервере. Исправлено: в `pdfFileId` пишется `document.id`; в
схеме добавлен комментарий; в тесте идентификаторы документа и файла теперь
разные, поэтому подмена снова уронит тест.

### Дефект 31: норматив в рабочих часах истекал на час раньше (исправлено)

`addWorkingHours()` засчитывала час **до** сдвига времени и выходила из цикла
**до** него. Из-за этого:

* `addWorkingHours(t, 1)` возвращала сам `t` — сдвига не было вовсе;
* норматив «Доставка в цех = 8 рабочих часов» от 12:00 вторника давал срок
  10:00 среды вместо 11:00;
* норматив «4 часа» от 15:00 истекал в 18:00 вместо 19:00, то есть **до**
  закрытия рабочего дня.

Последствие: заказ становился «просроченным» раньше наступления срока, и
эскалация срабатывала на час раньше нормы. Найдено при разработке эскалаций
(задача 2.8): порог руководителя считается в рабочих часах, и сверка
`countWorkingHours()` с `addWorkingHours()` показала расхождение.

Существующий тест дефект не ловил: он проверял только
`result.getTime() > date.getTime()` — то есть «время сдвинулось вперёд», а
`+1 час` от 12:00 как раз этого условия не выполнял. Проверка была слабее
утверждения, которое должна была защищать.

Исправлено: час засчитывается по интервалу, начинающемуся в текущем моменте,
время сдвигается **после** проверки. Добавлены тесты на точный результат
(«+1 час от 12:00 — это 13:00», «4 часа от 15:00 — это 19:00»); возврат
прежнего порядка роняет 9 тестов.

### Дефект 32: в письме руководителю ответственным был номер заказа (исправлено)

Шаблон `ESCALATION_MANAGER` содержит `{{responsible}}` — «кто отвечает за
заказ». В это поле подставлялся **номер заказа**, и руководитель получал:

> Заказ MSK1-2509-000001 просрочен более чем на рабочий день.
> Ответственный: MSK1-2509-000001.

На вопрос «к кому идти» это не отвечает, а эскалация существует именно ради
этого. Дефект не виден в юнит-тестах: проверялось, что уведомление создано и
что выбран верный шаблон, но не то, что подставлено в переменные. Найден при
прогоне на живом сервере, где текст письма был прочитан целиком.

Исправлено: имя ответственного (`productionManager.fullName`, при его
отсутствии — `createdBy.fullName`) читается вместе с заказом и подставляется в
шаблон. Тест проверяет значение переменной и падает при возврате номера заказа.

### Дефект 33: системный переход падал на внешнем ключе истории статусов (исправлено)

`OrderStatusHistory.changedById` — внешний ключ на `User`. Системный переход
передавал в него строку `'system'`, и вставка нарушала
`order_status_history_changedById_fkey`. В результате автостатус
«Невостребовано» не работал: заказ не переводился, оставаясь «готов к выдаче»
навсегда, а в журнале была лишь одна строка «не переведён». Ни один тест этого
не ловил: двойник Prisma принимает любой идентификатор, и тест сервиса
проверял, что переход **вызван**, но не то, с каким актором.

Договор сервиса переходов описан в его же интерфейсе: `actorId = null` означает
системный переход, а признак системности несёт `actorRole: 'SYSTEM'` (она же
выставляет `isSystem = true` и оставляет `AuditLog.actorRole = null`). Дефект
заключался в том, что вызывающий код этот договор нарушил.

Исправлено в двух местах:

1. `UnclaimedService` передаёт `actorId: null`;
2. `OrderWorkflowService.transition()` отклоняет системный переход с
   непустым `actorId` (`INVALID_ACTOR`) — переходов с актором `'SYSTEM'`
   несколько, и каждый новый вызывающий мог бы повторить ту же ошибку.

Тест проверяет и значение, и отклонение: возврат строки роняет тест.

### Дефект 34: шаблоны уведомлений не доходили до боевого сервера (исправлено)

Список шаблонов существовал только внутри `packages/db/prisma/seed.ts`. Сид в
продакшне не запускают — он создаёт демонстрационные заказы, клиентов и учётные
записи, — поэтому новый шаблон в базу боевого сервера не попадал.

Отказ был **тихим**: `notifyByTemplate` при отсутствии шаблона использует
запасной текст из кода. Уведомление приходило, но с другой формулировкой, и
понять это можно было, только прочитав сообщение. На живом сервере так ушло
уведомление о невостребованном заказе: вместо «Заказ … не получен клиентом
более 30 дней — переведён в «Невостребовано»» пришло «Заказ … ожидает клиента
более 30 дней».

Исправлено: список вынесен в `@app/shared` (`NOTIFICATION_TEMPLATES`) — один
источник и для сида, и для сервера; добавлен `scripts/sync-templates.mjs`,
который **добавляет** недостающие шаблоны и сообщает о расхождении текстов,
**не перезаписывая** их (правка формулировки администратором не должна теряться
при выпуске; для намеренного обновления есть `--update-texts`). Шаг включён в
`deploy.sh`. Тесты проверяют уникальность кодов, формат подстановок и наличие
всех кодов, которые ищут сервисы.

### Дефект 35: эффект `NOTIFY_CUSTOMER` не обрабатывался нигде (исправлено)

Таблица переходов (`packages/shared/src/domain/order-transitions.ts`) содержала
эффект `NOTIFY_CUSTOMER` у трёх переходов, а `docs/05` §3 обещала клиенту шесть
событий. **Обработчика не существовало**: `OrderWorkflowService` применял эффекты
`SET_DUE_AT`, `SET_READY_AT`, `COMPUTE_WARRANTY` и другие, а `NOTIFY_CUSTOMER`
молча пропускал.

Отказ был **полностью тихим**: ни ошибки, ни записи в журнале, ни уведомления.
Система считала клиента извещённым, а изделие лежало в магазине, пока клиент сам
не догадается позвонить. Ни один тест этого не ловил — проверялось, что переход
состоялся, а не что клиент узнал о результате.

Следствие того же класса: переходы `DRAFT → ACCEPTED` и
`AWAITING_APPROVAL → ACCEPTED` эффекта `NOTIFY_CUSTOMER` не имели вовсе, поэтому
обещанное событие «Заказ принят» (`ORDER_ACCEPTED`) не могло возникнуть даже
после появления обработчика.

Исправлено: обработка добавлена в `OrderWorkflowService` с записью в журнал при
сбое; эффект добавлен двум переходам на `ACCEPTED`; нормативная таблица `docs/04`
§2 приведена в соответствие. Повод определяется **парой «откуда → куда»**, а не
целевым статусом: `ACCEPTED` достигается и приёмом заказа, и поступлением
предоплаты, и это разные сообщения клиенту. Добавлена проверка согласованности —
каждый переход с эффектом обязан иметь событие, и наоборот; она сразу нашла два
дополнительных расхождения (`UNCLAIMED->COMPLETED` без эффекта и пропущенный
`AWAITING_APPROVAL->ACCEPTED`).

### Дефект 36: классификатор ошибки для HTTP был скопирован с SMTP (исправлено)

`isRetryableByCode` в `notification.port.ts` объявлен общим для всех адаптеров и
трактует `5xx` как **постоянную** ошибку, а `4xx` — как временную. Это верно для
SMTP, но для HTTP всё наоборот: `5xx` — сбой сервера, который обычно проходит, а
`4xx` — ошибка запроса, которая повтором не исправится.

Переиспользование общей функции дало бы новому каналу **обратную политику
повторов**: SMS не повторялось бы при временном сбое шлюза (`502`) и повторялось
бы бесконечно при постоянном отказе (`400` — неверный номер).

Исправлено: добавлена отдельная `isRetryableHttpStatus()` с противоположной
трактовкой диапазонов и исключениями `408`/`429` (сервер просит повторить позже).
Тест фиксирует именно противоположность трактовок — совпадение и было бы ошибкой.

### Дефект 37: `subject` в шаблонах был обязательным (исправлено)

`NotificationTemplateSeed.subject` имел тип `string`, и проверка требовала
непустую тему у **каждого** шаблона. У SMS темы нет: сообщение доставляется одним
текстом. Пустая строка была бы хуже `null` — она неотличима от «тему забыли
заполнить», и проверка перестала бы что-либо ловить.

Исправлено: тип стал `string | null`, а проверка требует тему только у каналов,
где она существует (`IN_APP`, `EMAIL`), и `null` — у `SMS` и `MESSENGER`.

## Замечания заказчика от 19.09.2026

Заказчик осмотрел работающую систему и сообщил три замечания по интерфейсу. Ниже
они разобраны по существу: два оказались небольшими доработками, третье —
отсутствующей функциональностью, ошибочно отмеченной в плане как готовой.

### Дефект 38: редактора прейскуранта не существовало, хотя план отмечал его готовым

**Как проявилось.** В интерфейсе администратора, в разделе «Справочники», нет
возможности изменить прайс-лист. Замечание заказчика дословно: «в управлении
справочников нет возможности внести изменения в прайслист».

**Что было на самом деле.** Редактора не было вовсе, а не «не хватало кнопки»:

* у прейскуранта **не было ни одного записывающего маршрута**. В
  `dictionaries.controller.ts` существовали только `GET price-lists`,
  `GET price-lists/active`, `GET price-list-items` и `GET price-lists/:id`;
  `dictionaries-admin.controller.ts` имел запись для магазинов, цехов,
  исполнителей, категорий работ и типов камней — и ничего для прейскуранта;
* в `dictionaries-admin.service.ts` позиции прейскуранта только **читались**
  (для проверок при отключении категорий);
* экран «Справочники» имел пять вкладок и ни одной для прейскуранта.

**Почему это стало возможным (главное).** План (`docs/09-roadmap.md`) отмечал
пункты 1.4.2 «API и UI редактора версии…» и 1.4.3 «запрет правки утверждённой
версии» как готовые. Отметка относилась к **модели данных**: схема `PriceListVersion`
/ `PriceListItem` / `PriceListItemRate` и перечисления статусов действительно были
созданы в этапе 1 и заполнены скриптом `apply-price-list.ts`. Наличие таблиц и
заливка утверждённых 24 позиций были приняты за наличие редактора. Заказчик
обнаружил разрыв при осмотре, а не проверка: **у функциональности не было ни
одного теста**, потому что тестировать было нечего — маршрутов не существовало.

**Вывод для процесса.** Отметка «готово» в плане должна подтверждаться наличием
маршрутов и экрана, а не наличием таблиц. Пункт, закрытый скриптом-заливкой,
готовым не является.

**Исправлено** задачей «редактор прейскуранта»: добавлены записывающие маршруты
(создание черновика версии, правка позиций и ставок по металлам, отправка на
утверждение, утверждение, отклонение, архивация, копирование версии) и вкладка
«Прейскурант» на экране «Справочники». Утверждённая версия доступна только для
чтения — правка идёт через новую версию.

**Побочная находка: контрольная функция не действовала.** При проверке
утверждения выяснилось, что администратор мог утвердить прейскурант сам, хотя
матрица прав (`docs/02-domain-and-roles.md` §4) ставит ему в строке
«Прейскурант: утверждение» прочерк. Причина оказалась двойной:

1. `RolesGuard` пропускал `ADMIN` **раньше** проверки прав — безусловно. Поэтому
   явный запрет на маршруте ничего не менял;
2. `ROLE_PERMISSIONS[ADMIN]` содержал `...Object.values(P)`, то есть выдавал
   администратору все права, включая `pricelist:approve`.

Итог: администратор правил цены и он же их утверждал. Подпись под ценами,
которую выполняет тот же человек, что и контролируемое действие, контролем не
является, а расхождение документации с поведением не было видно ни в одном
тесте. Исправлено двумя изменениями: введён декоратор
`RequireStrictPermission` (маршруты утверждения, отклонения и архивации
прейскуранта), а из набора прав администратора изъято `pricelist:approve`.
Проверено и обратное — для всех прочих проверок безусловный доступ
администратора сохранён, иначе систему стало бы некому настраивать.

**Вторая находка: утверждающий не видел того, что утверждает.** Маршрут чтения
карточки версии (`GET /price-lists/:id/editor`) требовал права
`pricelist:edit`, которого у руководителя и главбуха нет. На живом прогоне
руководитель получал на карточке **403**: он мог утвердить версию, но не мог
посмотреть её позиции и цены — то есть подписывал по одному номеру версии.
Исправлено: маршрут только читает (GET), поэтому к праву правки добавлено право
утверждения. Правка по-прежнему требует `pricelist:edit` — руководителю она
недоступна (проверено: `PATCH` → 403, `POST .../items` → 403).

### Дефект 39: поле «Металл» было свободным текстом (исправлено)

Поле металла в мастере приёма принимало произвольный текст. Металл определяет
**цену** работ: прейскурант задаёт отдельные ставки по золоту и серебру. Пока
металл распознавался, расчёт шёл верно, но при опечатке («Золото 5856»,
«Серебро 92») распознавание возвращало «не распознано», и работы молча считались
по цене по умолчанию — то есть по чужой колонке. Ошибка не показывалась как
ошибка: предупреждение было, но цена уже была подставлена.

Исправлено: поле стало выпадающим списком из металлов, по которым в прейскуранте
есть ставки (`METAL_OPTIONS`), значением служит код (`GOLD`/`SILVER`), а не
подпись. Старые заказы и сохранённые черновики со свободным текстом не теряют
значение: нераспознанный текст показывается отдельным пунктом
(`metalOptionValue`), а не подменяется пустым выбором.

### Дефект 40: вход по почте был единственным способом (исправлено)

Сотрудники входили по адресам вида `receiver1@remixgold.ru` — номерной ящик
вместо фамилии. Ошибиться в нём легко, а отказ выглядит как «неверный пароль»:
человек считает, что забыл пароль, и идёт его сбрасывать.

Исправлено: экран входа показывает выпадающий список активных сотрудников по
ФИО. Список (`GET /auth/login-options`) отдаёт **только** `id` и `fullName`:
маршрут открыт до входа, и почта в нём была бы готовым перечнем адресов для
фишинга. Вход из списка идёт по `userId`, поэтому адреса не покидают сервер.
Отключённые учётные записи в список не попадают.

Сохранено: вход по почте (скрипты, интеграции, аварийный доступ) и резервное поле
e-mail, если список получить не удалось — сбой одного запроса не должен запирать
систему для всех, включая администратора.

## Этап 5.11: публичная проверка статуса

### Дефект 41: флаги каналов в окружении не действовали НИКОГДА (исправлено)

Схема окружения объявляет каналы как `z.coerce.boolean()`, то есть строка
`'true'` превращается в **булево** `true`. Код читал их иначе:

```ts
config.get<string>('NOTIFICATIONS_SMS_ENABLED') === 'true'
```

Булево значение не равно строке `'true'` никогда. Флаг `=true` не действовал:
`channelsFor` получал `smsEnabled: false`, и SMS не отправлялись вовсе. Тем же
дефектом были поражены `NOTIFICATIONS_MESSENGER_ENABLED` и `SMTP_SECURE` — то
есть **шифрование почты молча оставалось выключенным** даже при `SMTP_SECURE=true`.

**Почему это не было видно.** Состояние каналов для администратора считает
другой код (`readSmsSettings`), который читал значение через `String(enabled)` и
работал правильно. В интерфейсе канал выглядел настроенным, а сообщения не
уходили.

**Найдено** на живой проверке кода подтверждения: код создавался в базе, в
журнале появлялась запись «создан, но НЕ ОТПРАВЛЕН», а состояние каналов при
этом показывало SMS как настроенный.

**Исправлено:** функция `envFlag` в `apps/api/src/config/env.validation.ts`
разбирает оба варианта (булево и строку). Регрессия закрыта тестом
`env-flag.spec.ts`, который **запрещает сравнение этих флагов со строкой во всём
исходном коде API** — проверка читает файлы, а не поведение, потому что
молчаливо выключенный канал не проявляется ни в одном функциональном тесте.

### Дефект 42: публичный ответ сам выдавал существование заказа (исправлено)

Первый вариант ответа на запрос кода содержал поле `phoneMask` — «код отправлен
на `****4567`». Поле заполнялось **только** тогда, когда заказ существует,
публично виден и телефон совпал. То есть поле само было тем оракулом, от
которого защищает вся схема: перебором номеров заказов можно было выяснить, какие
из них есть в системе.

**Найдено тестом на неотличимость** ответов, а не рассуждением: тест сравнил
ответ по существующему и несуществующему заказу и увидел разные маски.

**Исправлено:** поле убрано. Подтверждение «это ваш телефон» клиенту не нужно —
он сам его ввёл, и интерфейс показывает маску из введённого значения. Добавлен
тест, который перебирает ВСЕ случаи отказа и требует одинакового отпечатка
ответа `{ sent: true }`, — он ловит не конкретное поле, а сам принцип.

### Дефект 44: контроллер возвращал внутреннюю причину клиенту (исправлено)

Сервис возвращает объект с полем `reason` (`ORDER_NOT_FOUND`, `PHONE_MISMATCH`,
`RATE_LIMITED`) — оно нужно для журнала. Контроллер возвращал результат
**целиком**, и причина уходила клиенту в HTTP-ответе. Комментарий рядом
утверждал, что наружу идёт только признак «отправлено», — код делал обратное.

Это возвращало **тот самый оракул**, против которого построена вся защита:
перебором номеров заказов можно было выяснить, какие из них существуют в
системе. Для проверки статуса причина давала ещё больше — `MISMATCH` против
`NOT_FOUND` сообщает, что по заказу ВЫДАН код, то есть заказ существует и активен.

**Почему не нашли тесты.** Тесты сервиса сравнивали результат СЕРВИСА и
намеренно исключали `reason` из сравнения — как внутреннее поле. Всё было верно,
кроме того, что проверялось не то, что получает клиент.

**Найдено на живой проверке развёрнутого сервера:** в ответе `curl` стояло
`"reason":"ORDER_NOT_FOUND"`.

**Исправлено:** оба маршрута собирают ответ явными литералами (`{ sent }` и
`{ ok, view }`), поэтому новое поле в сервисе не сможет просочиться наружу само
собой. Добавлен тест `public-status.e2e-shape.spec.ts`, который смотрит на
готовый ответ контроллера, сравнивает его со **строгим литералом** (ловит и
новые поля) и требует одинакового отпечатка при всех внутренних причинах.

### Дефект 43: ограничение частоты срабатывало раньше лимита попыток (исправлено)

На `GET /public/order-status` стоял лимит 10 запросов в минуту на адрес, а код
гасится после 5 ошибок. Клиент ошибался в коде три раза, а на четвёртый получал
`429 Too Many Requests` — то есть ограничение по адресу подменяло собой лимит
попыток. Вместо «код не подошёл» человек видел «слишком много запросов», не
понимал, что происходит, и не мог воспользоваться оставшимися попытками.

На `POST /public/order-status/request-code` было то же: 5/час на адрес при лимите
3 на телефон. Хуже того, `429` **различает** случаи, тогда как смысл ограничения
— отвечать неотличимо.

**Исправлено:** лимит по адресу поднят до 30/мин (проверка статуса) и 20/час
(запрос кода) — строго выше лимитов по телефону, но не «без ограничения».
Расходы на SMS ограничивает счётчик по телефону. Тесты требуют, чтобы лимит по
адресу был **строго больше** числа попыток: иначе ограничение по адресу снова
подменит собой ограничение по коду.

### Дефект 45: карточка сотрудника не сохраняла изменения вообще

**Как проявилось.** Администратор открывал карточку сотрудника, менял пароль и не
находил кнопки «Сохранить». Закрытие карточки ничего не записывало.

**Что было на самом деле.** Причина не в одной отсутствующей кнопке, а в
устройстве карточки:

* кнопки сохранения в карточке **не было вовсе** — единственной кнопкой внизу
  была «Закрыть»;
* ФИО, e-mail, телефон и магазины выводились **текстом**: их нельзя было даже
  начать править, хотя `PATCH /users/:id` принимает `email`, `fullName`, `phone`,
  `isActive`, `storeIds` ещё с задачи 1.2.4;
* `useUpdateUser` вызывался только для одного действия — переключения
  активности, у которого была отдельная кнопка с немедленным срабатыванием;
* сброс пароля выполнялся кнопкой `variant="danger"` с надписью «Сбросить
  пароль», которая была **неактивна**, пока пароль не пройдёт политику. Причины
  неактивности интерфейс не объяснял: администратор видел серую кнопку, набирал
  пароль, а затем закрывал карточку и терял ввод. Это и читалось как «нет кнопки
  сохранить».

**Исправлено:**

1. В карточке появились поля правки ФИО, e-mail, телефона, флажок «Активна» и
   кнопка **«Сохранить»**, отправляющая `PATCH /users/:id`.
2. Отправляются **только изменённые** поля: иначе открытие карточки и сохранение
   затирали бы параллельную правку, сделанную в другой вкладке.
3. Телефон можно **стереть**: пустое поле уходит на сервер как `""`. Раньше это
   было невозможно и на уровне API — `phone: null` и `phone: ""` отклонялись
   схемой (`updateUserSchema` использует `phoneSchema`, требующую ≥10 цифр).
   Схема обновления теперь принимает пустую строку как «удалить телефон».
4. Флажок «Активна» заменил отдельную кнопку отключения с немедленным действием:
   два способа сделать одно и то же различались только тем, что один срабатывал до
   нажатия «Сохранить».
5. У блока сброса пароля появилась подсказка о политике и **перечисление
   конкретных причин** отказа («минимум 12 символов», «нужна прописная буква»),
   показываемое только после начала ввода. Кнопка «Сбросить пароль» перестала быть
   загадочно серой.
6. Кнопка «Сохранить» неактивна, когда изменений нет, и рядом текстом объясняется
   состояние («Есть несохранённые изменения» / «Изменений нет»). Закрытие без
   сохранения больше не выглядит как сохранение.

Логика вынесена в `apps/web/src/lib/user-edit.ts` и покрыта тестами (29): правило
«только изменённые поля», очистка телефона, сравнение магазинов как множества
(порядок не значим — сервер назначает магазином по умолчанию первый элемент) и
разбор причин отказа пароля. Каждое правило проверено мутацией: при его снятии
тест падает.

### Дефект 46: даты версии прейскуранта нельзя было изменить

**Как проявилось.** В разделе «Справочники» → «Прейскурант» администратор не мог
задать срок действия версии. Кнопки сохранения у версии тоже не было.

**Что было на самом деле.** Сервер принимает `effectiveFrom` и `effectiveTo` в
`PATCH /price-lists/:id` (`updatePriceListSchema`), но в интерфейсе:

* `effectiveFrom` **только отображалась** в строке списка, `effectiveTo` не
  показывался вовсе;
* задать даты можно было лишь косвенно — при копировании версии, где
  `effectiveFrom` подставлялась текущей датой;
* единственным сохраняемым полем был комментарий, и он сохранялся **неявно** —
  по потере фокуса, без кнопки и без подтверждения.

**Исправлено:** в карточке версии появились поля «Действует с» и «Действует по»
(`type="date"`) и кнопка «Сохранить». Пустое поле окончания означает бессрочность
и уходит как `null`, а не пропускается: иначе снять ограничение срока было бы
нельзя, а интерфейс отчитался бы об успехе. Даты сравниваются по значению дня, а
не по исходной строке ISO: сервер отдаёт `2026-09-16T17:05:08.846Z`, и сравнение
со значением поля `2026-09-16` объявляло бы изменение при простом открытии
карточки. День трактуется как полночь UTC, чтобы граница действия прейскуранта не
съезжала на сутки в UTC+3.

Логика вынесена в `apps/web/src/lib/price-list-period.ts` и покрыта тестами (16),
проверенными мутацией.

## Этап 6: гарантия и рекламации

### Дефект 47: закрытие рекламации стирало её исход (исправлено)

**Найдено** на живом сервере при сквозной проверке рекламации 19.09.2026.

**Симптом.** Рекламация с возвратом денег, доведённая до конца
(`APPROVED → RESOLVED_REFUND → CLOSED`), в отчёте `/reports/claims` давала
`resolvedRefundCount: 0`. Отчёт при этом не падал и выглядел правдоподобно: одна
закрытая рекламация, ноль возвратов.

**Причина.** Исход хранился только в СТАТУСЕ рекламации, а статус при закрытии
заменяется на `CLOSED` — прежнее значение `RESOLVED_REFUND` терялось. Отчёт считал
возвраты и ремонты по текущему статусу, и после закрытия считать было нечего.

**Почему не заметили раньше.** До этого этапа рекламации не создавались вовсе
(таблица пустая), а тесты отчёта подавали фикстуру со статусом `RESOLVED_REFUND`
и не проходили шаг закрытия — то есть проверяли состояние, которое в жизни
существует ровно до первого закрытия.

**Исправление.** Исход записывается в поле `WarrantyClaim.resolution` при переходе
в `RESOLVED_REPAIR`/`RESOLVED_REFUND` и не перезаписывается при закрытии. Отчёт
считает исходы по `resolution`. Добавлены два теста, каждый из которых падает на
соответствующей мутации: подсчёт по статусу и отсутствие записи исхода.

**Связь с ТЗ.** П. 2.9 требует «запись в основном заказе» и решения по рекламации;
без сохранённого исхода решение терялось из отчётности, то есть требование
выполнялось лишь формально.

### Дефект 48: кэш отчётов не сбрасывался при работе с рекламациями (исправлено)

**Найдено** на живом сервере сразу после исправления дефекта 47.

**Симптом.** В реестре `/claims` две рекламации, а в отчёте `/reports/claims` — одна.
Мета отчёта показывала `"cached": true`.

**Причина.** Кэш отчётов (задача 5.7) сбрасывался при переходах статусов заказа и при
платежах, но модуль рекламаций о нём не знал вовсе: он появился на этапе 6, когда
кэш уже существовал. Открытие рекламации и смена её статуса не сбрасывали ничего,
и отчёт отдавал картину до истечения TTL (15 минут).

**Почему не заметили раньше.** Тесты сервиса рекламаций и тесты отчётов проверялись
по отдельности: первые не смотрели на кэш, вторые подавали Prisma напрямую, минуя
кэш. Дефект виден только при последовательном обращении к обоим через живой API —
то есть на сквозной проверке.

**Исправление.** `ClaimsService` зависит от `ReportsCacheService` и сбрасывает кэш
отчёта `claims` при открытии рекламации и при каждом УСПЕШНОМ переходе. Отклонённый
переход (недопустимый или в терминальном статусе) кэш не сбрасывает: он ничего не
изменил. Три теста, две мутации убиты.

**Урок для остальных модулей.** Любой модуль, меняющий данные, попадающие в отчёт,
обязан сбросить его кэш. Кэш мог бы сбрасываться по времени изменения данных, но
такой механизм потребовал бы версионирования всех таблиц; текущий явный сброс
требует помнить о себе. Это осознанный компромисс, и он записан здесь именно
потому, что однажды уже был забыт.

### Дефект 49: `deploy.sh` не перезапускал воркер — новый воркер не запускался вовсе (исправлено)

**Найдено** при развёртывании этапа 6: новый воркер `claim-deadlines` (задача 6.6) не
появился в журнале после трёх развёртываний.

**Симптом.** `systemctl is-active repair-worker` отвечал `active`, дымовые проверки
проходили, API и страницы работали. При этом в `/opt/repair/logs/worker.log` последний
запуск задач был шестичасовой давности, а `claim-deadlines` не упоминался ни разу.
Воркер крутился со СТАРЫМ кодом из памяти.

**Причина.** `deploy.sh` использовал `systemctl enable --now repair-worker`. `--now`
запускает юнит, только если тот ОСТАНОВЛЕН; для уже работающего это пустая операция.
`repair-api` и `repair-web` перезапускались явным `restart`, а воркер — нет.

**Почему это опасно.** Отсутствие нового воркера не проявляется как ошибка: эскалации и
уведомления продолжают работать по старому коду, и заметить пропажу одной задачи можно
только по журналу. Изменения в существующих воркерах так же не вступали в силу до
ручного перезапуска.

**Исправление.** Воркер перезапускается явным `systemctl restart repair-worker`
(`enable` — отдельно, для первого развёртывания). Добавлена проверка: сверяется время
запуска юнита и наличие записи «Запуск фоновых воркеров» в журнале после него; при
расхождении печатается предупреждение с указанием на возможный старый код.

**Проверено на живом сервере.** После исправления в журнале появились все шесть задач,
включая `claim-deadlines (интервал 3600000 мс)`, а прогон воркера отработал:
`claim-deadlines: к сроку 1, предупреждено 1, без рассматривающего 0`.

### Дефект 50: настройка срока рекламации объявлена, но не читалась (исправлено)

**Найдено** при проверке документации интеграций: сверялись объявленные настройки
окружения с местами, где они читаются.

**Симптом.** `CLAIM_REVIEW_WORKDAYS` присутствовала в схеме окружения
(`apps/api/src/config/env.validation.ts`) с самого начала работы, но не читалась нигде.
Срок рассмотрения был жёстко задан константой `CLAIM_REVIEW_WORKING_DAYS = 10` в домене.
Изменение значения настройки не меняло ничего.

**Почему это опасно.** Настройка выглядит рабочей: она есть в схеме, у неё есть значение
по умолчанию, её видно в списке переменных. Администратор, меняющий «10» на «15», был бы
уверен, что изменил срок, — а срок остался бы прежним. Это тот же класс дефекта, что
«Дефект 41» (флаги каналов уведомлений не действовали никогда): расхождение между
объявленной настройкой и её фактическим использованием не проявляется как ошибка.

**Исправление.** `computeClaimDueAt` принимает срок параметром; сервис читает
`CLAIM_REVIEW_WORKDAYS` и применяет его при открытии рекламации. Значение проверяется:
нечисловое, нулевое или отрицательное заменяется значением по умолчанию — «0 рабочих
дней» означал бы рекламацию, просроченную в момент заведения. Три теста, две мутации
убиты (настройка не читается; снята защита от нуля).

**Что это не меняет.** Срок уже открытых рекламаций не пересчитывается: `dueAt` сохранён
при открытии и остаётся обязательством, названным клиенту.

### Дефект 51: `JWT_REFRESH_SECRET` требовался для запуска, но не защищал ничего (исправлено)

**Найдено** при сплошной сверке объявленных настроек окружения с местами, где они
читаются (следствие работы над «Дефектом 50»).

**Симптом.** `JWT_REFRESH_SECRET` объявлен как **обязательная** настройка: схема окружения
требует не короче 32 символов, `superRefine` отвергает демонстрационные значения в
продакшне, переменная документирована в `.env.example`. При этом в коде она не
использовалась **нигде**: хеш refresh-токена считался открытым `createHash('sha256')`.

**Почему это опаснее предыдущих однотипных дефектов.** Все прочие настройки без эффекта
означали «изменение ничего не меняет». Здесь наоборот: **эксплуатация считала, что у неё
есть рычаг отзыва сессий.** При краже базы, компрометации cookie или увольнении сотрудника
штатным действием было «сменить секрет refresh-токенов» — и оно не давало **ничего**:
refresh-токены оставались действительными все 30 дней своего срока.

**Причина.** Refresh-токен сознательно сделан **непрозрачной случайной строкой**
(`randomBytes(48)`), а не JWT: в базе лежит только его хеш, и это правильное решение
(отзыв возможен по факту наличия сессии). Но раз токен не подписывается JWT, секрет для
него не понадобился, а объявление переменной осталось от первоначального замысла
подписывать и refresh-токен.

**Исправление.** Хеш считается как HMAC-SHA-256 с ключом `JWT_REFRESH_SECRET`. Смена
секрета немедленно делает недействительными все ранее выданные refresh-токены — рычаг
отзыва стал реальным. Медленная `argon2` намеренно не применяется: токен — это 48
случайных байт, а не пароль, и перебирать его бессмысленно.

**Цена решения.** Смена секрета разлогинивает всех сотрудников — это **намеренное**
свойство, а не побочный эффект: секрет, смена которого ничего не завершает, бесполезен
как средство реагирования. Плата — повторный вход; взамен появляется действие, которым
можно остановить продолжающуюся компрометацию.

**Проверка.** Три теста: при смене секрета сохранённый хеш перестаёт совпадать, при
неизменном — совпадает, в базе не остаётся открытого токена. Мутация «секрет
игнорируется» убита. На сервере переменная задана, то есть поведение после развёртывания
меняется предсказуемо: все текущие сессии завершатся.

**Следствие для остальных настроек.** Проверка выявила ещё три объявленные, но не
читаемые настройки того же класса: `REPORT_CACHE_TTL_SECONDS`, `WARRANTY_MONTHS_DEFAULT`,
`WARRANTY_MONTHS_SETTING` и `REPORT_ASYNC_THRESHOLD_MS`. Настройки S3, 1С и IP-АТС не
считаются дефектом: их интеграции отложены заказчиком, и контракты описаны в
`docs/05-integrations.md`.

### Дефекты 52–53: ещё две объявленные настройки не читались (исправлено)

Продолжение сплошной сверки настроек окружения с местами, где они читаются. Обе
настройки — того же класса, что 41, 50 и 51: объявлены, имеют значение по умолчанию,
видны в `.env.example` — и не влияют ни на что.

| Настройка | Что было | Что стало |
|-----------|----------|-----------|
| `REPORT_CACHE_TTL_SECONDS` | Не читалась: кэш жил строго по таблице `REPORT_TTL_MS` | Задаёт ВЕРХНЮЮ границу свежести отчётов. Отчёт, устаревающий быстро («просрочки» — 5 минут), настройкой не удлиняется; годовой срез (сутки) не укорачивается |
| `WARRANTY_MONTHS_DEFAULT` | Не читалась: в коде стояла жёсткая «6» | Определяет гарантию заказа, у которого срок не задан ни одной работой |

**Про `REPORT_CACHE_TTL_SECONDS`: почему именно верхняя граница.** Таблица
`REPORT_TTL_MS` выражает РАЗЛИЧИЕ отчётов по скорости устаревания, и это различие —
часть домена, а не настройка окружения. Настройка задаёт общий предел свежести: на
пилоте нужны свежие цифры, на большом объёме те же отчёты дороже. Простое умножение
или подстановка сделали бы отчёт «просрочки» менее свежим, чем задумано, — а он
страдает от устаревания сильнее всех.

**Про `WARRANTY_MONTHS_DEFAULT`.** Настройка объявлена с комментарием «6 обычный,
3 закрепка», но второй параметр (`WARRANTY_MONTHS_SETTING`) относится к сроку НОВЫХ
позиций прейскуранта и применяется при их создании, а не при расчёте гарантии: у
позиции срок хранится, и пересчитывать его задним числом нельзя — иначе гарантия по
уже принятым заказам изменилась бы в момент правки настройки.

**Найдена мёртвая передача параметра.** В блоке расчёта гарантии значение по умолчанию
передавалось третьим аргументом `computeWarrantyUntil`, хотя `order.warrantyMonths` уже
содержит его: массив из одного элемента никогда не пуст, и параметр не использовался
бы вовсе. Мутация «настройка не читается» в этом месте **выжила** — тесты остались
зелёными. Аргумент убран; настройка применяется ровно в одном месте. Это пример того,
как вторая передача того же значения создаёт вид работы, не влияя ни на что.

**`REPORT_ASYNC_THRESHOLD_MS` оставлена нечитаемой намеренно.** Она относится к задаче
5.13 (асинхронная выгрузка), которая не реализована. В отличие от дефекта 51, здесь
отсутствующая функция описана в `docs/06-reporting.md`, поэтому настройка не выдаёт
себя за работающую; её назначение зафиксировано комментарием в схеме окружения.

### Дефект 54: три клиентских уведомления объявлены, но никогда не отправлялись (задокументировано)

**Найдено** при сверке `docs/05-integrations.md` §3 с фактическими местами отправки
уведомлений (в рамках работы над документацией по интеграциям).

**Симптом.** В таблице событий §3 перечислены шесть клиентских событий, но фактически
отправляются три: `ORDER_ACCEPTED`, `READY_FOR_PICKUP`, `WARRANTY_ISSUED`. События
`PREPAYMENT_RECEIVED`, `APPROVAL_REQUEST` и `UNCLAIMED_REMINDER` имеют шаблоны
(`notification-templates.ts`), правила доставки (`notification-policy.ts`) и каналы — но
вызова, который их создаёт, в коде **нет**.

**Причина.** Клиентское уведомление отправляется из `notifyCustomerOfTransition`, а повод
определяется ПЕРЕХОДОМ статуса через `CUSTOMER_TRANSITION_NOTIFICATION`. Привязка есть
только у трёх переходов. Переход `DRAFT->AWAITING_APPROVAL` («отправить на согласование»)
эффекта `NOTIFY_CUSTOMER` не имеет вовсе, поэтому `APPROVAL_REQUEST` не создаётся никогда.
Приём предоплаты происходит вне перехода статуса, и точки, откуда отправить
`PREPAYMENT_RECEIVED`, нет. Воркер невостребованных заказов шлёт СОТРУДНИКУ
(`ORDER_UNCLAIMED`), а клиентский `UNCLAIMED_REMINDER` не вызывает.

**Почему это не проявлялось.** Внешние каналы выключены по умолчанию
(`NOTIFICATIONS_SMS_ENABLED=false`, `NOTIFICATIONS_MESSENGER_ENABLED=false`), и у клиента нет
`IN_APP`-ленты — учётной записи у него нет. Отправлять было некуда и некому. Дефект стал бы
виден **в момент включения SMS**: клиент не получил бы ни запроса согласования, ни
подтверждения предоплаты, ни напоминания забрать заказ — при том, что в интерфейсе
администратора канал выглядел бы настроенным.

**Что сделано.** Расхождение зафиксировано в `docs/05-integrations.md` §3 отдельной таблицей
«Не отправляются, хотя шаблон есть и канал настроен» с указанием причины по каждому событию
и прямым предупреждением: **перед включением каналов привязку нужно сделать**. Код не
менялся: это незакрытая часть этапа 5, а не ошибка, и делать её вслепую — без работающего
внешнего канала для проверки — значило бы получить код, который «выглядит отправляющим».

**Почему это записано как дефект, а не как задача.** Формально привязка событий — задача
5.9/5.10, и её отсутствие не было бы дефектом, если бы документация §3 отражала факт.
Дефект в другом: таблица §3 читалась как перечень РАБОТАЮЩИХ уведомлений. Расхождение
«объявлено и реализовано» без пометки — то же, что дефекты 38 и 45, где отметка «готово»
относилась к модели данных, а не к функции.

### Дефект 55: ограничение пула соединений не действовало на работающий API (исправлено)

**Найдено** при сверке `docs/14-deployment.md` §3.2 с кодом (продолжение работы над
документацией интеграций).

**Симптом.** `DATABASE_POOL_SIZE` объявлена в схеме окружения, документирована как
«применяется автоматически в `packages/db/src/index.ts`», проверяется скриптом
`infra/db/preflight.sh` до развёртывания и посчитана в бюджете соединений. При этом
**работающий API её не применял**: `PrismaService` создаёт СВОЙ экземпляр `PrismaClient`,
а логика `connectionLimit` жила только в общих клиентах `prisma`/`prismaReplica` пакета
`@app/db`, которые API не использует.

**Почему это опасно.** В продакшне база — существующий сервер PostgreSQL предприятия,
общий с другими системами (ответ A1). Prisma без `connection_limit` открывает соединения
по формуле «число ядер × 2 + 1» на каждый процесс; три процесса (две реплики API и
воркер) могли занять весь `max_connections` сервера. Тогда встали бы 1С и другие системы,
и причину искали бы где угодно, кроме нашего приложения: со стороны это выглядит как «лёг
сервер базы». `preflight.sh` при этом показывал бы, что бюджет в порядке, — он считает по
настройке, а не по фактическому поведению кода.

**Причина.** Два независимых клиента Prisma: общий (`packages/db`) и собственный
(`PrismaService` в API). Логика ограничения была написана для первого, а работает второй.
Комментарий в `prisma.module.ts` («единственный экземпляр клиента на процесс — см.
`packages/db/src/index.ts`») описывал намерение, а не факт.

**Исправление.** Логика вынесена в отдельный модуль `packages/db/src/connection-limit.ts`
(чтобы её можно было проверить без создания клиента Prisma) и применяется в `PrismaService`
через `datasources.db.url`. Шесть тестов фиксируют поведение; мутации «наивная склейка
через `?`» и «перезапись явного ограничения» убиты.

**Побочная находка.** `REDIS_URL` объявлена как **обязательная** настройка (без неё
приложение не запускается), но Redis в коде не используется нигде: решение ADR 0002 —
transactional outbox в PostgreSQL, а Redis/BullMQ лишь «ускоритель оповещения», которого
в реализации нет. В продакшне `REDIS_URL` задана, а служба Redis неактивна. Объявление
оставлено (интеграции 1С отложены, контракт понадобится), но это осознанное расхождение,
а не работающая зависимость.

### Дефект 56: исправление дефекта 55 вывело API из строя на сервере (исправлено)

**Как проявилось.** Выкат дефекта 55 остановил `repair-api`: `systemctl status` показал
`activating (auto-restart)`, в журнале — `SyntaxError: Unexpected token '{'` в
`packages/db/src/index.ts:8`. Веб-интерфейс отвечал, потому что `repair-web` работает
независимо, — то есть внешне система выглядела живой, а API был недоступен.

**Причина.** `PrismaService` получил `import { connectionLimit } from '@app/db'`.
`packages/db/package.json` указывает `main` и `exports` на `./src/index.ts` — на
ИСХОДНЫЙ TypeScript. Пакет задуман как источник типов и клиента для Prisma CLI и не
собирается для Node. `@app/shared`, наоборот, собирается в `dist` и импортируется
нормально.

**Почему не поймали раньше.** Сборка (`nest build`) прошла: TypeScript резолвит `@app/db`
по типам и не проверяет, что указанный путь исполним для Node. Тесты прошли: они не
запускают собранное приложение. Типы сошлись. Ошибка проявляется **только при запуске** —
то есть на сервере, в работающей системе.

**Что сделано, чтобы не повторилось.**

1. `connectionLimit` перенесён в `@app/shared` (`packages/shared/src/utils/connection-limit.ts`),
   откуда его импортируют и API, и `packages/db`. Правило остаётся ОДНО — ради чего
   дефект 55 и исправлялся.
2. Перед повторным выкатом собранное приложение **запущено локально** против рабочей базы:
   `Nest application successfully started`, `/health/ready` — 200.
3. Добавлен тест `apps/api/src/common/prisma/runtime-imports.spec.ts`: он проверяет, что
   `@app/shared` указывает на собранный `.js`, что `PrismaService` не импортирует
   `@app/db`, и фиксирует факт «`@app/db` не собирается» — чтобы при его будущей сборке
   тест упал и заставил перечитать решение о двух клиентах Prisma. Мутация «вернуть
   импорт `@app/db`» убита.

**Урок.** «Собралось и прошло тесты» не означает «запустится». Для изменений в точке
входа приложения обязателен хотя бы один запуск собранного кода до выката.

### Дефект 57: опечатка в цвете статуса не ловилась ничем, и рядом жила мёртвая палитра (исправлено)

**Найдено** при разборе задачи 1.7.6 — последней незакрытой задачи проекта. Её отметка
отсутствовала не случайно: «дизайн-система» существовала как набор компонентов, но не как
свод правил с проверками.

**Симптом А — беззвучная потеря цвета статуса.** `STATUS_COLORS` в `@app/shared` был
объявлен как `Record<OrderStatus, string>`, а компонент `Badge` приводил значение к своему
типу тонов через `as Tone`. Эксперимент: замена `DRAFT: 'gray'` на `DRAFT: 'gren'` дала
**ноль ошибок компиляции**. В рантайме `TONES['gren']` возвращает `undefined`, `cn()` молча
пропускает `undefined`, и бейдж рисуется тоном по умолчанию — серым. Готовый к выдаче заказ
выглядел бы как черновик.

**Почему это важнее, чем кажется.** Цвет статуса — единственный сигнал, который сотрудник
воспринимает не читая текст: в списке из сотни заказов «зелёный» означает «звонить
клиенту», а «красный» — «тревога». Проверок на него не было ни одной: тип не ловил (строка
совместима со строкой), линтер не ловил (приведение `as` снимало вопрос), тесты не
проверяли цвета вовсе. Ошибка была бы видна только глазами и только тому, кто держит в
голове правильный цвет.

**Исправление.** Тон стал типом-объединением `StatusTone`. Та же опечатка теперь даёт
`error TS2820: Type '"gren"' is not assignable to type 'StatusTone'`. Приведение `as Tone`
стало ненужным — линтер (`no-unnecessary-type-assertion`) это подтверждает, то есть типы
домена и компонента действительно сошлись. Добавлен тест
`packages/shared/src/domain/status-colors-sync.spec.ts` (4 теста): каждый тон из
`STATUS_COLORS` обязан существовать в `TONES` компонента; мутация «тон, которого нет в
Badge» убита с сообщением, называющим конкретный статус.

**Симптом Б — мёртвая вторая палитра.** В `tailwind.config.ts` жила палитра `status.*` —
девять hex-цветов с комментарием «соответствует `STATUS_COLORS` из `@app/shared`». Она не
использовалась **ни разу**: ни одного класса `bg-status-*` в разметке, ни одной ссылки на
`theme.colors.status`, ни в собранном CSS. При этом она расходилась с фактом: бейджи
рисуются классами вида `bg-green-100` (светлый фон), а палитра обещала `#22c55e`.

**Почему мёртвое описание хуже отсутствующего.** Оно выглядит работающим. Правка цвета
статуса в этой палитре не дала бы ничего, и это выяснилось бы уже после «исправления» —
причём в момент, когда цвет понадобился (например, для графика или печати). Удалена; в
комментарии оставлено, что делать, если hex действительно понадобится: вывести словарь ИЗ
`STATUS_COLORS`, а не заводить второй.

**Адаптив от 360 px** закреплён тестами `apps/web/src/lib/mobile-layout.spec.ts` (6 тестов).
Проверяются именно молчаливые нарушения: таблица шире экрана задаёт `min-width` всему
документу, и прокручивается вся страница — шапка и кнопки уезжают за край, а причину ищут
в вёрстке шапки. Мутации убиты: убранная прокрутка таблицы нормативов и добавленная ширина
500 px роняют свои тесты с указанием файла.
