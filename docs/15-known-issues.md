# 15. Известные проблемы и особенности

## Ограничения и известные особенности

Раздел фиксирует технические решения и ограничения, выявленные при первом
фактическом запуске проекта. Нужны, чтобы команда не наступала на те же грабли.

---

### Запуск и окружение

**1. `.env` должен лежать в корне монорепозитория.**

Workspace-скрипты npm выполняются с `cwd` пакета (`apps/api`, `apps/web`), поэтому
относительный путь `'.env'` указывает не туда. API решает это поиском файла вверх
по дереву (`apps/api/src/app.module.ts` → `resolveEnvPaths()`).

Следствие для разработчика: конфигурация одна — корневой `.env`. Отдельные `.env`
в пакетах создавать не нужно.

**2. Prisma не читает корневой `.env`, если запускается из `packages/db`.**

Поэтому во всех командах Prisma `DATABASE_URL` передаётся явно. Это уже сделано в
`scripts/local-setup.mjs`; при ручном запуске учитывайте:

```bash
DATABASE_URL="postgresql://..." npx prisma migrate deploy --schema packages/db/prisma/schema.prisma
```

**3. Redis и S3/MinIO пока не используются в коде.**

Переменные `REDIS_URL`, `S3_*` обязательны для валидации конфигурации, но соединение
не устанавливается: модули очередей и работы с файлами ещё не реализованы
(этапы 2+ по `docs/09-roadmap.md`). Для запуска достаточно PostgreSQL.

**4. Логи в dev требуют `pino-pretty`.**

Он объявлен в `devDependencies` API. Если зависимость не установлена, приложение
завершается с сообщением `unable to determine transport target for "pino-pretty"`.

---

### Дефекты, исправленные при первом запуске

Эти ошибки не выявлялись тестами и проверкой типов — они проявлялись **только при
фактическом старте приложения**. Зафиксированы как пример того, что запуск нужно
проверять, а не предполагать работающим.

| Симптом | Причина | Исправление |
|---------|---------|-------------|
| `Некорректная конфигурация: DATABASE_URL: Required` при заполненном `.env` | API искал `.env` в `apps/api`, а файл в корне | `resolveEnvPaths()` — поиск вверх по дереву |
| Приложение «молча повисало» без трассировки | `ValidationPipe` требует `class-validator`, которого не было в зависимостях. `@nestjs/common` при этом вызывает `process.exit(1)` | Установлены `class-validator`, `class-transformer` |
| `unable to determine transport target for "pino-pretty"` | Пакет использовался в dev-режиме, но не был объявлен в зависимостях | Добавлен в `devDependencies` API |

### Самый коварный дефект: вход работал, сессия не сохранялась

**Симптом:** вход выполнялся успешно, cookie выдавались, но **любой следующий запрос**
отвечал `UNAUTHENTICATED: Сессия истекла`. Пользователь видел бесконечный возврат
на экран входа, а логи не содержали ошибки конфигурации.

**Причина:** `JwtModule.register({ secret: process.env.JWT_ACCESS_SECRET })` —
декоратор вычисляется в момент **загрузки файла модуля**, то есть **до** того, как
`ConfigModule.forRoot()` прочитает `.env`. В результате:

- при **подписи** токена секрет передавался явно (`{ secret: process.env.JWT_ACCESS_SECRET }`
  в `auth.service.ts`) и уже был загружен → вход проходил;
- при **проверке** (`verifyAsync` без явного секрета) использовался секрет из модуля,
  то есть `undefined` → проверка всегда падала.

**Почему это опасно:** асимметрия «подпись работает, проверка нет» выглядит как истёкшая
сессия, а не как ошибка настройки. В продакшне дефект проявился бы так же, и искали бы
причину в TTL токена или часах сервера, а не в порядке инициализации.

**Исправление:** `JwtModule.registerAsync()` с `ConfigService` — секрет читается после
инициализации конфигурации.

**Защита от повторения:** тест на сквозной вход должен проверять **не только выдачу
cookie, но и запрос с этой cookie**. Проверка только ответа на `/auth/login` дефект
не ловит.

### Дефекты, выявленные при разработке интерфейса

Ни один из них не выявлялся типами и unit-тестами: чтобы их увидеть, нужно было
открыть страницу и выполнить действие в браузере.

**1. Скрытые зависимости локальных скриптов.**

`scripts/local-db.mjs` и `scripts/local-setup.mjs` используют `@embedded-postgres/*`
и `pg`, но **не были объявлены ни в `package.json`, ни в `package-lock.json`**.
Любой `npm install` удалял их, после чего `npm run local:db` падал с
`Не удалось запустить PostgreSQL: undefined` (реальная причина — отсутствующий
бинарник `pg_ctl`), а `local:db:psql` — с `ERR_MODULE_NOT_FOUND`.

Исправление: `@embedded-postgres/darwin-x64` и `linux-x64` версии `16.14.0-beta.17`
объявлены в `optionalDependencies` (версия совпадает с продакшном), `pg` и `@types/pg`
— в `devDependencies`. Обе платформы перечислены явно: на сервере нужен `linux-x64`.

**Вывод:** `--workspace` при установке пересобирает дерево, поэтому незадекларированная
зависимость исчезает молча. Скрытых зависимостей быть не должно — это проверяется
сравнением импортов скриптов с `package.json`.

**2. `POST /orders/:id/transition` возвращал объект другой формы.**

Эндпоинт отдавал сырую запись Prisma (`order.findUniqueOrThrow` с одним включением
`statusHistory`), в которой нет вычисляемых полей карточки: `availableTransitions`,
`statusLabel`, `remainingMinor`, `items`, `customer`. Клиент подставлял этот ответ в
кэш карточки и падал на `availableTransitions.length` — перевод статуса выполнялся на
сервере, но экран становился неработоспособным.

Исправление: контроллер возвращает `findOne(id, user)` — ту же форму, что и
`GET /orders/:id`. То же сделано для `POST /orders/:id/cancel`.

**Вывод:** у эндпоинтов, меняющих сущность, форма ответа должна совпадать с её
чтением. Иначе клиент вынужден склеивать данные из двух источников, и рано или поздно
он это делает неверно.

**3. `assertMinor` не компилировался и терял значение в сообщении.**

Проверка была написана предикатом `isValidMinor(value): value is Minor`, но
`Minor = number`, поэтому предикат **не сужает тип**: в ветке ошибки `value` становился
`never`, и шаблонная строка с `${value}` перестала компилироваться. Заменено на
`Number.isSafeInteger` и `String(value)`.

**4. Пользователь без ролей мог войти в систему.**

`roles[0]` при пустом списке — `undefined`, и это значение попадало в `AuditLog.actorRole`
и `OrderStatusHistory`: запись об изменении теряла автора. Теперь вход отклоняется
(`NO_ROLES_ASSIGNED`), а основная роль вынесена в явное поле `primaryRole`. Причина
вынесения — `noUncheckedIndexedAccess: true`: `roles[0]` типизирован как
`RoleCode | undefined`, и каждое использование требовало `!`, то есть отключения
проверки типов именно там, где пишется аудит.

**5. Системные переходы были недостижимы.**

Доменное ядро допускает актора `'SYSTEM'` (автоматические переходы, например
`ACCEPTED → UNCLAIMED`), но `TransitionContext` объявлял `actorRole: RoleCode`, где
`'SYSTEM'` отсутствует. В результате `OrderStatusHistory.isSystem` **не мог** стать
`true`. Поле расширено до `actorRole: TransitionActor`, `actorId: string | null`;
в аудит для системного перехода пишется `actorRole: null` (это не роль).

**6. Демонстрационный прейскурант создавался черновиком — мастер приёма был пуст.**

`packages/db/prisma/seed.ts` создавал версию прейскуранта со статусом `DRAFT`.
Расчёт заказа идёт **только** по утверждённым ценам, поэтому
`GET /price-lists/active` возвращал `null`, `GET /price-list-items` — пустой
список, и шаг «Работы» мастера приёма не показывал ни одной позиции. Создать
заказ можно было только нетиповой работой.

Отсутствие `APPROVED`-версии — не дефект кода справочников: `null` здесь
корректен («прейскурант не утверждён» — штатное состояние, а не 404), и
подставлять черновик молча нельзя, потому что это означало бы расчёт по ценам,
которые руководитель не согласовал. Дефект был именно в демо-данных: seed обязан
давать работоспособный сквозной сценарий.

Исправление: версия создаётся сразу `APPROVED`, с заполненными `approvedById` и
`approvedAt` (утверждённая версия обязана иметь утвердившего — иначе аудит не
ответит на вопрос «кто согласовал эти цены»). Существующие базы правятся
обновлением статуса; `seed.ts` идемпотентен и повторно версию не создаёт.

**Вывод:** дефект был виден только при сквозном прохождении сценария в браузере.
Ни typecheck, ни 97 unit-тестов его не обнаруживают: они проверяют логику
фильтрации по статусу, а не то, что демо-данные вообще проходят этот фильтр.

**7. Ошибка формы не снималась при исправлении поля.**

В мастере приёма ошибка «Больше суммы заказа» оставалась на экране после того,
как пользователь исправлял сумму: валидация срабатывала при отправке, а
`onChange` ошибку не сбрасывал. Внешне это выглядит так, будто форма отклоняет
корректное значение. Исправление: правка полей, участвующих в проверке, снимает
общую ошибку формы.

**8. Сервер доверял цене, которую прислал браузер.**

`POST /orders` принимал `unitPriceMinor` из запроса и записывал его в заказ как есть.
Цену можно было занизить правкой запроса: заказ уходил бы в производство с неверной
суммой, а расхождение обнаружилось бы только при сверке. Это дефект денежного пути,
а не удобства.

Исправление: сервер сверяет цену каждой работы с действующим прейскурантом и отвечает
`409 PRICE_MISMATCH` с перечнем расхождений. Нетиповые работы (`isCustom`) не проверяются —
их цену назначает сотрудник. Итог заказа теперь считается по **проверенным** ценам,
а не по присланным.

**9. Серебряный заказ считался по золотому тарифу (нормализация металла).**

Дефект был внесён вместе с поддержкой цен по металлам и обнаружен при проверке на
реальном API, а не тестами. Металл изделия хранится свободным текстом («Серебро»,
«Au585»), а ставки прейскуранта адресуются кодами (`GOLD`/`SILVER`). Сервер сравнивал
их напрямую, поэтому сравнение **никогда** не совпадало: всегда применялась цена по
умолчанию (золото), и серебряный ремонт стоил вдвое дороже. Ошибки в логах не было —
просто не та сумма.

Заметить это можно было только сквозной проверкой: через API создавался заказ на
серебро с ценой серебра и **получал `409`**, а с ценой золота — **проходил `201`**,
то есть проверка цены работала ровно наоборот.

Исправление: нормализация металла перенесена внутрь общей функции `resolveItemPrice`,
которая принимает и код, и текст. Это устраняет целый класс ошибок: вызывающий код
больше не может забыть привести металл. Добавлены тесты-регрессии.

**10. Работы привязывались к первому изделию, независимо от металла.**

Все строки калькуляции записывались с `itemId` первого изделия
(`const firstItem = order.items[0]`). При одном изделии в заказе это незаметно, но
в заказе «золотое кольцо + серебряная цепочка» цена выбирается по металлу изделия,
поэтому неверная привязка означает неверную цену. Исправление: работы и камни
привязываются по индексу изделия (`itemIndex`). Проверено заказом из двух изделий:
итог 1350 ₽ = 900 ₽ (золото) + 450 ₽ (серебро).

**11. Корректировка итога «вверх» нарушала инвариант денежных сумм.**

Инвариант `totalAmountMinor = worksTotalMinor + stonesTotalMinor − discountMinor`
(docs/03-data-model.md §3.2) проверяется ночным job-ом сверки. При реализации
корректировки итога «вверх» (надбавка за срочность, доплата за сложность) скидка
обнулялась как «не могущая быть отрицательной», а итог присваивался напрямую.
В результате сумма строк и скидка перестали давать итог: для заказа 450 ₽,
поднятого до 600 ₽, формула давала 450 ₽ при итоге 600 ₽.

Дефект внесён вместе с модулем корректировок и найден при проверке на реальном API —
не тестами: до этого тестов на корректировки не было вовсе.

Исправление: разница считается функцией `discountForTotal` из `@app/shared`, которая
допускает **отрицательную** скидку (это и есть надбавка), и итог всегда вычисляется
общей формулой `calcOrderTotal`, а не присваивается. Трактовка знака для интерфейса
тоже вынесена в домен (`describeDiscount`) — карточка показывает строку «Надбавка»
со знаком «+», а не отрицательную скидку. Добавлены 5 тестов, один из которых
воспроизводит старую логику и доказывает, что инвариант в ней нарушался.

**12. Корректировка строки не проверяла принадлежность заказа.**

`targetId` строки калькуляции искался без условия `orderId`, поэтому чужой
идентификатор строки позволил бы изменить строку другого заказа, а «было» было бы
взято не из того заказа. Исправление: строка ищется вместе с `orderId`; несовпадение
отдаёт `404` (не подтверждаем существование чужой строки). Проверено запросом с
`targetId` строки другого заказа.

**13. QR-код квитанции не читался сканером (прозрачный фон).**

Код печатался через `bwip-js` без указания фона, а по умолчанию библиотека рисует
QR на ПРОЗРАЧНОМ фоне. Такой код кодирует данные правильно и в PDF выглядит
нормально, но не декодируется: проверка показала «не прочитан» на всех масштабах
(4, 6, 8, 10, 12, 16), тогда как тот же код с белым фоном читается сразу.

Это главный сценарий квитанции («сканируем при выдаче»), и он не работал бы.
Дефект нельзя заметить при чтении кода — только декодированием. Исправление: фон
задан явно (`backgroundcolor: 'FFFFFF'`); тест `receipt.service.spec.ts`
воспроизводит прозрачный вариант и доказывает, что он не читается, а белый — читается.
Проверено также декодированием QR, извлечённого из **готовой страницы PDF**:
`repair://order/MSK1-2509-000001` → номер заказа разобран.

**14. `qrPayload` не заполнялся при создании заказа.**

Поле есть в схеме и упоминается в ADR 0006, но заказ создавался с `qrPayload = null`:
номер генерировался прямо в объекте `data`, и взять его для второго поля того же
`create` было нельзя. Исправление: номер вычисляется до создания заказа и передаётся
и в `orderNo`, и в `buildOrderQrPayload(orderNo)`. Проверено на новом заказе.

**15. Миниатюры фотографий не отображались (адрес без префикса API).**

API возвращал `url: /photos/{id}`, а прокси перенаправляет на API только пути
`/api/v1/*`. Ссылка попадала в маршрутизацию Next и отдавала 404 — миниатюры
не появлялись, хотя файл на сервере существовал и через API открывался.
Исправление: адреса формируются с префиксом (`/api/v1/photos/{id}`).

**16. `loading="lazy"` делал фотографии невидимыми там, где не работает `IntersectionObserver`.**

Отложенная загрузка опирается на `IntersectionObserver`; в headless-браузере
(и части встроенных просмотрщиков) он не срабатывает, и изображения не
загружаются вовсе — сотрудник видел пустые рамки. Уменьшенная копия весит
меньше килобайта, поэтому экономия не оправдывает риск. `loading="lazy"`
убран; проверено, что миниатюры отображаются (320×240).

**17. Сканирование квитанции не работало на экране приёма оплаты.**

Разбор ввода сканера был реализован ВНУТРИ компонента глобального поиска
(`global-search.tsx`) и нигде больше. Экран приёма оплаты — основной сценарий
ТЗ п. 2.5 — отправлял в поиск строку `repair://order/MSK1-2509-000001` целиком
и получал **ноль результатов**, хотя подсказка в поле обещала работу со
сканером. То есть приём оплаты по отсканированному номеру не работал.

Причина не в одной забытой строке, а в том, что функция-помощник жила в
компоненте: её нельзя было переиспользовать, и второй экран остался без неё.

Исправление: разбор перенесён в домен (`normalizeScanInput` в
`@app/shared`) и вызывается на обоих экранах. Функция возвращает ГОДНЫЙ
ПОИСКОВЫЙ ЗАПРОС, а не только номер: если ввод не распознан как номер заказа,
он передаётся дальше как есть — поиск по телефону и фамилии не ломается.
Проверено: URI из QR и URI с переводом строки находят заказ, телефон и фамилия
ищутся по-прежнему. Добавлены 5 тестов.

### Дефекты, выявленные при развёртывании

Подробности и команды — в `infra/db/deployment-report.md` §5.7–5.8.

**1. `npm ci` удалял Prisma Client, и сборка API падала.**

Prisma Client лежит в `node_modules/.prisma/client` и содержит типы всех моделей.
`npm ci` пересоздаёт `node_modules` целиком, а шага `postinstall` в проекте не
было, поэтому клиент не восстанавливался: подставлялась заглушка, и сборка падала
с `Namespace 'Prisma' has no exported member 'OrderWhereInput'`.

Исправлено скриптом `scripts/postinstall.mjs`, который `npm install` вызывает
автоматически. Он намеренно **не** падает при отсутствии Prisma CLI (установка с
`--omit=dev`): инструмент сборки не должен ломать установку боевых зависимостей.

**2. Standalone-сборка Next.js не отдавала статику — страницы были пустыми.**

Симптом обманчив: сервер отвечает `200`, API исправен, но в браузере виден только
спиннер. `output: 'standalone'` **не копирует** `.next/static` и `public` в
standalone-каталог — в Docker это делает сборщик образа, а у нас его нет.

Причина в том, что HTML ссылается на чанки, которых рядом не лежит: гидратация
не запускается, и клиентские страницы остаются пустыми. Исправление —
скопировать оба каталога внутрь `.next/standalone/apps/web/` и перезапустить
сервис. **Это обязательный шаг при развёртывании без Docker**, а не разовая
настройка.

### Что ещё не реализовано

См. `docs/09-roadmap.md`. Работают: доменное ядро, схема БД (41 таблица),
аутентификация с ротацией refresh-токенов, RBAC с областями видимости, модуль заказов
с переходами статусов и историей, а также интерфейс в объёме **вход → дашборд →
список заказов → карточка заказа → перевод статуса** и глобальный поиск.

Реализовано также: **мастер создания заказа** (5 шагов, справочники магазинов, цехов,
прейскуранта), **приём оплаты** (с идемпотентностью, переплатой и сторно),
**справочник клиентов** с поиском по телефону, **прейскурант по металлам** (24 позиции
утверждённого документа, ADR 0009), **перевод статусов** с историей и **глобальный поиск**.

Полностью не реализованы: логистика и партии, интеграции с 1С и IP-АТС (отложены
заказчиком), отчётность, гарантия и рекламации, генерация PDF-квитанции с QR-кодом
(поля `qrPayload` и `receiptPrintCount` в схеме есть, кнопка печати пока вызывает
`window.print()`).
