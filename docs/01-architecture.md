> **PostgreSQL — внешняя система.** База данных предприятия **общая**: с ней работают
> 1С и другие системы. Отсюда два следствия, влияющих на архитектуру: пул соединений
> приложения ограничен (нельзя занять все соединения сервера), а резервное копирование
> выполняет администратор БД — система **уже настроена** на отдельном сервере PostgreSQL.
> Требования — `infra/db/README.md`.

`packages/shared` — ключевой пакет: он держит **статусную модель, матрицу прав и схемы
валидации**, которые импортируют и API, и веб. Это исключает расхождение правил между
фронтендом и бэкендом.

## 3. Слои backend

```
HTTP Controller  →  DTO (Zod validation)  →  Application Service  →  Domain Service  →  Prisma Repository
       ▲                     ▲                        ▲                   ▲
   guards:               валидация             транзакции,          бизнес-правила:
   JwtAuthGuard                                 оркестрация,         переходы статусов,
   RolesGuard                                   аудит                блокировка предоплаты,
   ScopeGuard                                                        условие выдачи
```

**Принципы:**
1. **Контроллеры тонкие.** Никакой бизнес-логики — только приём DTO и вызов сервиса.
2. **Доменные правила — в доменных сервисах**, не в контроллерах и не в UI.
   `OrderWorkflowService.canTransition()` — единственная точка правды.
3. **Транзакции — на уровне application service.** Изменение заказа + запись истории +
   аудит + outbox — одна транзакция (`prisma.$transaction`).
4. **Scope-фильтр обязателен.** Репозиторий списков принимает `scopeFilter` из guard-а;
   прямой `findUnique({ where: { id } })` по заказу без проверки scope запрещён
   (правило ESLint + ревью).

## 4. Ключевые технические решения

| Решение | Обоснование |
|---------|-------------|
| **REST + OpenAPI**, без GraphQL | Меньше сложности, интеграции с 1С предпочитают HTTP/JSON; автогенерация клиента для веба из OpenAPI |
| **Монорепо с npm workspaces** | Общие типы домена; в окружении заказчика нет pnpm, npm workspaces работает на голом Node |
| **Оптимистичная блокировка** (`Order.version`) | Двое сотрудников не перезапишут карточку молча: конфликт → `409` + перечитывание |
| **Transactional outbox** для 1С | Платёж фиксируется в БД независимо от доступности 1С; отправка ретраится воркером. 1С может быть выключена — система продолжает работать |
| **Идемпотентность платежей** | `idempotencyKey` (UUID, генерируется на клиенте) защищает от двойного списания при ретрае и повторной доставке вебхука |
| **Redis только как ускоритель** | Остановка Redis не теряет данные: очереди восстанавливаются из `IntegrationOutbox`, кэш деградирует до прямых запросов к БД |
| **Файлы в S3 (MinIO)** | БД не раздувается бинарями; записи звонков за год — это десятки ГБ |
| **SSR в Next.js** | Приёмщик на слабом планшете в магазине получает готовую страницу, а не ждёт бандл |

## 5. Аутентификация и безопасность

- **Пароли:** Argon2id (memory 64 МБ, iterations 3, parallelism 4).
- **Токены:** access JWT 15 минут в httpOnly+Secure cookie, refresh 30 дней,
  refresh-токен хранится хешированным в `UserSession` (ротация при каждом обновлении,
  повторное использование → отзыв всей цепочки).
- **CSRF:** double-submit cookie для мутирующих запросов; SameSite=Lax.
- **Блокировка:** 5 неудачных попыток → блок на 15 минут (`lockedUntil`).
- **Парольная политика:** минимум 6 символов, требований к составу символов нет
  (решение заказчика; обоснование — `docs/10-nfr-security.md`). Проверка по словарю
  частых паролей **не реализована** — прежняя формулировка этого раздела её
  обещала, хотя в коде её никогда не было.
- **Аудит:** каждое чтение карточки заказа записывается опционально (настройка
  `audit.read`); каждое изменение — обязательно.
- **Разграничение прав:** guard-цепочка `JwtAuthGuard → RolesGuard → ScopeGuard`,
  плюс проверка на уровне домена для критичных переходов (защита от обхода через API).

## 6. Производительность

Ориентиры (целевой масштаб — до 50 магазинов, 1000+ заказов/мес ≈ 35 заказов/день):

| Операция | Целевое время p95 |
|----------|-------------------|
| Открытие карточки заказа | ≤ 400 мс |
| Поиск по номеру/телефону | ≤ 300 мс |
| Список заказов с фильтрами | ≤ 500 мс |
| Создание заказа с калькуляцией | ≤ 800 мс |
| Приём платежа | ≤ 400 мс |
| Построение отчёта за месяц | ≤ 3 с (кэш 15 мин) |

Меры: индексы из `schema.prisma`, keyset-пагинация (`createdAt + id`) вместо `OFFSET`
на больших списках, агрегаты отчётов — SQL, материализованные представления для тяжёлых
срезов, реплика для отчётных запросов.

## 7. Наблюдаемость

- **Метрики** Prometheus: RED по эндпоинтам, длина очередей, лаг outbox, число просрочек.
- **Логи** — структурированный JSON с `requestId`, `userId`, `orderId`; собираются Loki.
- **Трейсинг** — OpenTelemetry, экспорт в Tempo (опционально).
- **Health** — `/health/live` (процесс жив) и `/health/ready` (БД и Redis доступны).
- **Алерты:** БД недоступна, лаг outbox > 15 мин, ошибки 5xx > 1 %, очередь эскалаций не
  обрабатывается > 30 мин.

## 8. Резервное копирование (ТЗ п. 4)

**База данных внешняя** (ответ A1), поэтому ответственность разделена: копии БД делает
**администратор БД**, файлы проекта — **мы**.

| Объект | Метод | Частота | Retention | Кто | RPO / RTO |
|--------|-------|---------|-----------|-----|-----------|
| PostgreSQL | `pg_basebackup` + WAL-архив (PITR) | непрерывно | по регламенту БД | **Администратор БД** — настроено | RPO ≤ 5 мин *(при наличии PITR)* |
| PostgreSQL | `pg_dump` логический | по регламенту БД | по регламенту БД | **Администратор БД** — настроено | — |
| S3 (MinIO) | репликация бакета + версионирование | непрерывно | — | Проект | RPO ≤ 1 ч |
| S3 (MinIO) | архив `tar.gz` (шифруется) | ежедневно | 90 дней | Проект | — |
| Конфигурация | Git + шифрованный бэкап `.env` | при изменении | — | Проект | — |

Восстановление **тестируется ежеквартально** на отдельном стенде; результат оформляется
актом. Наш скрипт файлов — `infra/backup/backup.sh`; восстановление БД проверяется
скриптом `infra/backup/restore-drill.sh`, который запускает администратор БД (нужны права
`CREATE DATABASE` на общем сервере). Целевые показатели: **RTO ≤ 4 часа**, **RPO ≤ 5 минут**
(достижим при охвате PITR — уточняется на этапе 0).

> **Риск R12 (снижен):** система резервного копирования БД **уже настроена** на отдельном
> сервере, поэтому создавать и настраивать ничего не нужно. Остаётся подтвердить, охвачен
> ли **PITR** — без него фактический RPO равен интервалу между дампами, а не 5 минутам,
> и тогда требование фиксируется как принятое отклонение. Второе: **проводилась ли проверка
> восстановлением** — копия без проверки гарантии не даёт. Учебное восстановление — до
> пилота (`infra/db/README.md` §5.1).

## 9. Развёртывание

Полное руководство — **`docs/14-deployment.md`** (Docker в LXC, внешний nginx-proxy,
внешний PostgreSQL, инструкция для UI прокси). Схема маршрутизации — `infra/proxy/README.md`.
Требования к БД — `infra/db/README.md`.

- **Среда разработки:** `docker compose -f infra/docker/docker-compose.dev.yml up`
  (PostgreSQL, Redis, MinIO, Mailhog). Локальный PostgreSQL нужен только разработчику,
  чтобы не требовался доступ к продовой БД.
- **Продакшн (on-premise, Proxmox VE 7.4):** Docker Compose в LXC-контейнере
  (вложенный Docker разрешён — ответ A1). Альтернатива без Docker — `docs/14-deployment.md` §6.
- **PostgreSQL НЕ запускается в Docker:** используется существующий сервер предприятия
  (ответ A1). В продовом compose сервиса `postgres` нет. Пул соединений ограничен
  (`DATABASE_POOL_SIZE`) — сервер общий с 1С, занимать все соединения нельзя.
- **TLS и маршрутизация — внешний nginx-proxy заказчика** (ответ A1). Проект **не содержит**
  собственного прокси и не терминирует TLS: публикует только `web:3000` и `api:4000`,
  на которые прокси заказчика направляет трафик. Сертификаты Let's Encrypt, HSTS и
  общесетевые правила настраиваются централизованно администратором **через UI**.
- **Доверие к прокси:** `TRUST_PROXY=1` обязателен. Без него ограничение частоты запросов
  (`ThrottlerGuard`) видит адрес прокси у всех клиентов и после нескольких неудачных
  входов блокирует вход всей сети.
- **Миграции:** отдельный шаг деплоя `prisma migrate deploy`, до запуска новой версии API.
  Откат — только через новую миграцию (down-миграции не практикуем), поэтому изменения
  схемы делаются обратно совместимыми: сначала добавить, потом переключить код, потом удалить.
- **Zero-downtime:** health-check и rolling update — обновление по одной реплике.

## 10. Что сознательно НЕ делаем

| Не делаем | Почему |
|-----------|--------|
| Микросервисы | Масштаб до 1000 заказов/мес — один модульный монолит проще в эксплуатации и разработке |
| Kafka / RabbitMQ | BullMQ на Redis покрывает потребности; меньше компонентов на on-premise |
| GraphQL | Не оправдан: один основной потребитель — наше же веб-приложение |
| Собственное мобильное приложение | Решение заказчика: PWA |
| Собственный экземпляр PostgreSQL | В инфраструктуре есть настроенный сервер 16 (ответ A1) — второй экземпляр не нужен |
| Собственный nginx / терминирование TLS | Внешний nginx-proxy заказчика уже это делает (ответ A1, ADR 0007) |
| Хранение записей звонков > 1 года | Прямое требование ТЗ п. 2.4 |
| `Float` для денег | Недопустимая точность в финансовом учёте |
