# 02. Домен, роли и права доступа

## 1. Глоссарий

| Термин | Значение |
|--------|----------|
| **Заказ** | Единица учёта ремонта: от приёма изделия в магазине до выдачи клиенту |
| **Изделие** | Физический предмет, принятый в ремонт (может быть несколько в одном заказе) |
| **Магазин** | Точка приёма/выдачи, место работы приёмщика и кассира |
| **Цех (производство)** | Место выполнения ремонта |
| **Партия** | Набор заказов, физически перемещаемых между магазином и цехом одной поставкой |
| **Прейскурант** | Версионируемый справочник типовых работ с ценами |
| **Калькуляция** | Расчёт стоимости конкретного заказа: строки работ + строки камней |
| **Согласование** | Фиксация договорённости с клиентом по сумме и сроку (в т.ч. устной) |
| **Норматив этапа** | Плановое время нахождения заказа в статусе, задаётся в рабочих днях/часах |
| **Эскалация** | Автоматическое уведомление при просрочке норматива |
| **Предоплата** | Частичная или полная оплата до начала работ |
| **Невостребовано** | Заказ, готовый к выдаче и не полученный клиентом 30 дней |

## 2. Роли

Роль — набор прав и область видимости данных. Один пользователь может иметь несколько ролей
(например, приёмщик + кассир в маленьком магазине), поэтому модель — **RBAC с множественным
назначением**, а не единичное поле `role`.

Всего **8 ролей**: 5 ролей из ТЗ п. 2.10 (без «Мастер-ювелира» — см. G1) плюс
`CASHIER`, `AUDITOR` и `CHIEF_ACCOUNTANT` (последняя — по ответу A2).

| Код | Название | Основная задача |
|-----|----------|-----------------|
| `RECEIVER` | Приёмщик магазина | Приём заказа, первичная оценка, согласование с клиентом, выдача |
| `PRODUCTION_MANAGER` | Менеджер обработки поступающих ремонтов | Приём заказов в производство, распределение по исполнителям, контроль сроков цеха, коммуникация с ювелирами. **Ответственный за приёмку этапов и эксплуатацию системы** (ответ A2) |
| `LOGISTICIAN` | Логист / курьер | Формирование партий, акты приёма-передачи, статус «в пути» |
| `CASHIER` | Кассир / бухгалтер точки | Приём предоплат и финальной оплаты, работа с ККТ, сверка с 1С |
| `MANAGER` | Руководитель | Утверждение прейскуранта, эскалации, отчётность, аналитика |
| `ADMIN` | Администратор | Пользователи, роли, справочники, настройки интеграций |
| `AUDITOR` | Наблюдатель / аудитор | Read-only доступ к заказам и журналу действий |
| `CHIEF_ACCOUNTANT` | Главный бухгалтер | **Соутверждение прейскуранта** (достаточно одной подписи — руководителя или главбуха), финансовая отчётность, аудит платежей. Операционной работой с заказами не занимается |

> **Нормативы сроков.** Утверждённых нормативов у заказчика нет (ответ A3). Система
> поставляется со **стартовыми значениями** (см. `docs/00-decisions.md` §6.11), которые
> менеджер обработки поступающих ремонтов корректирует по факту в первый месяц.
> Изменение норматива не пересчитывает `dueAt` у уже начатых этапов.

> **Мастер-ювелир не является пользователем системы.** Он учитывается как **исполнитель
> производства** (`Performer`) — запись справочника с ФИО и специализацией, назначаемая
> менеджером производства на работу. Учётной записи и доступа у него нет.
> Это решение заказчика, зафиксировано в `docs/00-decisions.md` §2.

## 3. Область видимости данных (Data Scope)

Право отвечает на вопрос «что можно делать», область видимости — «с какими данными».

| Область | Код | Поведение |
|---------|-----|-----------|
| Только свой магазин | `STORE` | Видны заказы, принятые в магазинах пользователя |
| Свой магазин + поиск по номеру глобально | `STORE_PLUS_GLOBAL_SEARCH` | Основная выборка — свои; поиск по точному номеру находит заказ любой точки (для приёма оплаты) |
| Всё производство | `PRODUCTION` | Видны все заказы, находящиеся в производстве или следующие в/из цеха |
| Все магазины | `ALL_STORES` | Видны все заказы всех точек |
| Только чтение, все данные | `READ_ALL` | Полный read-only доступ |

Правило проверки на сервере: `scopeFilter(user)` добавляется к **каждому** запросу списка
и к загрузке карточки. Прямой доступ по `id` без прохождения scope-фильтра запрещён — это
защита от IDOR.

## 5. Ключевые бизнес-правила

### 5.1. Блокировка старта работ (ТЗ п. 2.5)
Заказ переходит в производственный статус **только** если выполнено одно из:
- `requiresPrepayment = false` (предоплата не требуется для данного вида работ);
- сумма подтверждённых предоплат ≥ `prepaymentRequired` (в минорных единицах).

Проверка выполняется в доменном сервисе `OrderWorkflowService`, а не в UI. Попытка обхода
возвращает `409 Conflict` с кодом `PREPAYMENT_REQUIRED`.

### 5.2. Условие выдачи (ТЗ п. 2.8)
Переход в `COMPLETED` (выдан) возможен только при `paidAmount >= totalAmount`.
При отказе клиента от оплаты оформляется `RefusalAct`, заказ переходит в `REFUSED`
и изделие остаётся на ответном хранении в магазине.

### 5.3. Невостребовано (ТЗ п. 2.8)
Плановая задача (cron, ежедневно) переводит заказы в статусе `READY_FOR_PICKUP`,
у которых `readyAt + 30 дней < today`, в статус `UNCLAIMED`. Уведомление — приёмщику магазина.

### 5.4. Гарантия (ТЗ п. 2.9)
- Обычный ремонт — 6 месяцев, закрепка камня — 3 месяца.
- `warrantyUntil` рассчитывается при выдаче от `completedAt` по `max(warrantyMonths)` работ.
- Гарантийный заказ имеет `isWarranty = true`, `parentOrderId` — ссылку на исходный заказ,
  стоимость работ может быть 0.

### 5.5. Рекламация (ТЗ п. 2.9)
Срок рассмотрения — **10 рабочих дней** от `claimOpenedAt`, с учётом рабочего календаря.
Рекламация — дочерняя сущность заказа (`WarrantyClaim`), не отдельный заказ; она записывается
в основной заказ (ТЗ п. 2.9) и видна в его истории.

### 5.6. Записи разговоров (ТЗ п. 2.4)
- При регистрации заказа с клиента берётся согласие на запись разговоров —
  обязательный пункт заявки; без него заказ создать нельзя (`consentCallRecording = true`).
- Записи хранятся **1 год**, после чего удаляются плановой задачей вместе с объектом в S3.
- Запись из IP-АТС автоматически привязывается к заказу по номеру телефона + времени звонка
  и к ближайшему согласованию.
