# 10. Нефункциональные требования

## 1. Производительность и масштабирование

| Параметр | Целевое значение | Как достигается |
|----------|------------------|-----------------|
| Одновременных пользователей | до 200 (пик — утро, приём заказов) | Stateless API, 2+ реплики за прокси |
| Заказов в системе | 500 000+ без деградации | Индексы, keyset-пагинация, партиционирование `audit_log` по месяцам при росте |
| Заказов в месяц | 1000+ (запас до 5000) | Один сервер приложений справляется, горизонтальное масштабирование доступно |
| Отклик API p95 | ≤ 500 мс на операционных эндпоинтах | Индексы, отсутствие N+1, кэш справочников |
| Отчёты | ≤ 3 с (месяц), асинхронно (год) | SQL-агрегаты, материализованные представления, реплика |
| Вес страницы карточки заказа | ≤ 250 КБ JS (gzip) | Code splitting, SSR, дерево компонентов по вкладкам |
| Время первой отрисовки (3G) | ≤ 3 с | SSR + критический CSS |
| Загрузка фото с телефона | ≤ 5 с на кадр 3 МБ | Presigned URL напрямую в S3, сжатие на клиенте |

**Нагрузочное тестирование:** k6 на синтетических данных объёмом ×10 от ожидаемого
(10 000 заказов в месяц, 5 лет истории). Проводится перед пилотом и перед каждым крупным релизом.

## 2. Доступность и отказоустойчивость

| Показатель | Значение |
|------------|----------|
| Целевая доступность | 99.5 % в рабочее время (08:00–21:00) |
| Плановые окна обслуживания | вне рабочих часов, с уведомлением за 24 ч |
| RTO (восстановление после сбоя) | ≤ 4 часа |
| RPO (потеря данных) | ≤ 5 минут — **достижим при охвате PITR** существующей системой копирования БД; уточняется на этапе 0 (§5.1) |
| Деградация без БД (внешний PostgreSQL) | **Полная остановка записи** — БД критична. При недоступности сервера БД операции не проводятся; система не «копит» заказы локально. Поэтому доступность внешней БД — критический фактор |
| Деградация без 1С | **Полная работоспособность**, платежи копятся в outbox |
| Деградация без АТС | Заказы работают; записи догружаются позже |
| Деградация без Redis | Очереди восстанавливаются из `IntegrationOutbox`, кэш отключается |
| Деградация без S3 | Приём заказа работает; фото догружаются из локальной очереди клиента |

Ключевой принцип: **внешние системы не блокируют основную работу магазина.**
Приёмщик не должен слышать «подождите, 1С недоступна» — это прямое требование бизнеса.

## 3. Безопасность

### 3.1. Аутентификация и сессии
- Argon2id для паролей (memory 64 МБ, iterations 3, parallelism 4).
- Access JWT 15 минут, refresh 30 дней с ротацией; повторное использование refresh → отзыв цепочки.
- Токены в httpOnly + Secure + SameSite=Lax cookie; в `localStorage` токены **не хранятся**.
- Блокировка после 5 неудачных попыток на 15 минут.
- Опционально: TOTP-двухфакторная аутентификация для ролей `ADMIN` и `MANAGER` (этап 5).

### 3.2. Авторизация
- Три уровня проверки: роль (`RolesGuard`) → область видимости (`ScopeGuard`) → доменное
  правило (например, блокировка предоплаты).
- Загрузка объекта по `id` **всегда** проходит scope-фильтр. Отсутствие доступа возвращает
  `404`, а не `403` — не раскрываем существование чужих заказов.
- Управление правами централизовано в `packages/shared`; расхождение фронта и бэка исключено.

### 3.3. Защита приложения
| Угроза | Мера |
|--------|------|
| SQL-инъекции | Prisma с параметризованными запросами; сырой SQL только с `$queryRaw` и типизацией |
| XSS | Экранирование React, CSP (`default-src 'self'`), запрет `dangerouslySetInnerHTML` |
| CSRF | SameSite=Lax + double-submit токен на мутирующих запросах |
| Брутфорс | Rate limit: 10 попыток входа / 15 мин на IP + блокировка учётки |
| Перебор номеров заказов | Номера содержат случайную часть; публичный статус — только с кодом из SMS |
| IDOR | Scope-фильтр на всех загрузках по `id` + тесты |
| Подделка платежа | Идемпотентность + проверка суммы на сервере + аудит каждой операции |
| Раскрытие в логах | Логи не содержат паролей, токенов, полных номеров карт; PII маскируется |
| Загрузка вредоносных файлов | Проверка MIME и magic bytes, лимит размера, файлы не исполняются, отдача только с `Content-Disposition: attachment` |

### 3.4. Шифрование
- TLS 1.2+ на всём внешнем трафике. **Терминирование TLS выполняет существующий
  nginx-proxy заказчика** (ответ A1): он выдаёт сертификаты Let's Encrypt, задаёт HSTS
  и протоколы. Проект не содержит собственного прокси — схема в `infra/proxy/README.md`.
- **Внутренний трафик между прокси и приложением идёт по HTTP** во внутренней сети LXC.
  Это допустимо: трафик не покидает хост Proxmox. Если политика требует шифровать и его,
  прокси настраивается на `https` до upstream — приложение это поддерживает.
- **`X-Forwarded-Proto: https` обязателен** от прокси: без него приложение считает
  соединение небезопасным и не отдаёт cookies с флагом `Secure` (токены доступа) —
  пользователь не сможет войти. Проверяется в чек-листе `infra/proxy/README.md` §6.
- **`TRUST_PROXY=1` обязателен.** За прокси `req.ip` без этой настройки — адрес прокси.
  Последствие: ограничение частоты запросов (`ThrottlerGuard`) считает всех клиентов одним
  адресом, и несколько неудачных попыток входа одного сотрудника блокируют вход всей сети.
  Запрещено использовать `true`: IP подделывается заголовком `X-Forwarded-For`.
- Шифрование диска сервера (LUKS) — на стороне заказчика.
- Бэкапы шифруются (age/GPG) перед выгрузкой за пределы сервера.
- Секреты — в переменных окружения / Docker secrets, **не в репозитории**. `.env` в `.gitignore`.

### 3.5. Персональные данные (152-ФЗ)
- Обрабатываются: ФИО, телефон, email, дата рождения, записи голоса.
- Размещение on-premise на территории РФ — требование выполнено по инфраструктуре.
- Согласие на запись разговоров — обязательный пункт заявки; отзыв согласия удаляет записи.
- Срок хранения записей — **1 год** (ТЗ п. 2.4), затем автоматическое удаление.
- Доступ к ПДн — только у ролей, которым это необходимо для работы; все обращения логируются.
- Экспорт ПДн фиксируется в аудите (кто, что, когда, зачем).
- Формулировки согласий согласуются с юристом заказчика (риск R7).

## 5. Резервное копирование (ТЗ п. 4)

### 5.1. База данных — зона администратора БД (ответ A1)

**PostgreSQL в проекте внешний** — это существующий сервер предприятия, общий с другими
системами. Резервное копирование БД выполняет **администратор БД**, а не наш проект:
наши скрипты не имеют прав, нужных для `pg_basebackup`, и не должны управлять копированием
общего сервера.

> **Статус: система резервного копирования уже организована и настроена** на отдельном
> сервере PostgreSQL (подтверждено заказчиком). Создавать и настраивать ничего не нужно —
> требуется **получить параметры** существующего регламента и сверить с требованиями
> проекта.

| Объект | Кто выполняет | Статус |
|--------|---------------|--------|
| `pg_basebackup` + WAL-архив (PITR) | **Администратор БД** | Настроено; **уточнить, охвачен ли PITR** |
| `pg_dump` логический (периодический) | **Администратор БД** | Настроено |
| Хранение и ротация копий | **Администратор БД** | Настроено; **уточнить срок хранения** |
| Проверка восстановлением | **Администратор БД** | **Уточнить, проводилась ли** |

**Два параметра требуют подтверждения** (`infra/db/README.md` §5.1):

1. **Охвачен ли PITR (непрерывная архивация WAL).** Требование RPO ≤ 5 минут
   (см. §2) достигается только так. Если настроены только периодические дампы,
   фактический RPO равен интервалу между ними — обычно 24 часа. Тогда это фиксируется
   как **осознанно принятое отклонение**, а не как выполненное требование.
2. **Проводилась ли проверка восстановлением.** Настроенный бэкап и **проверенный**
   бэкап — разные вещи: копия может быть нечитаемой, зашифрованной ключом, которого
   нет, или лежать на том же диске, что и данные. Проверка до пилота обязательна.

### 5.2. Файлы проекта — зона проекта

| Объект | Метод | Частота | Хранение | Где |
|--------|-------|---------|----------|-----|
| S3 (фото, записи, документы) | Репликация бакета + версионирование | непрерывно | — | Второй узел MinIO |
| S3 (фото, записи, документы) | Архив `tar.gz` (шифруется) | ежедневно | 90 дней | Внешний носитель |
| Конфигурация | Git + шифрованный архив `.env` | при изменении | — | Внешний носитель |

**Правило 3-2-1:** три копии, два носителя, одна копия вне сервера.
**Проверка восстановления** — ежеквартально, на отдельном стенде, с оформлением акта
и замером фактического RTO. Наши скрипты: `infra/backup/backup.sh` (файлы и конфигурация).
Учебное восстановление БД: `infra/backup/restore-drill.sh` — запускается администратором БД,
поскольку требует прав `CREATE DATABASE` на общем сервере.

**Мониторинг:** успешность бэкапа файлов — алерт администратору при ошибке или отсутствии
файла за сутки. Успешность бэкапа БД контролирует администратор БД по своему регламенту
(система копирования настроена).

> **Важно не смешивать два объекта.** Копирование БД **не покрывает** файлы: фотографии
> изделий, записи разговоров и PDF лежат в S3/MinIO и имеют отдельный регламент.
> Настроенная система копирования PostgreSQL не делает их резервную копию — это наша
> зона ответственности (`infra/backup/backup.sh`).

> **Риск R12** (`docs/09-roadmap.md`) — **снижен**: система резервного копирования БД
> уже организована и настроена на отдельном сервере. Остаётся подтвердить два параметра:
> охвачен ли **PITR** (иначе фактический RPO = интервал между дампами, а не 5 минут)
> и **проводилась ли проверка восстановлением**. Копия без проверки восстановления
> гарантии не даёт — о её непригодности узнают в момент аварии.

## 7. Сопровождаемость

- **Покрытие тестами:** доменное ядро (статусы, права, деньги) ≥ 80 %; API ≥ 60 %;
  E2E — все критичные сценарии.
- **Типизация:** TypeScript strict, `noUncheckedIndexedAccess`, запрет `any` (ESLint error).
- **Миграции:** только через Prisma migrate; проверка на копии продовых данных в CI.
- **Документация:** OpenAPI автогенерируется; ADR (Architecture Decision Records) на каждое
  значимое решение в `docs/adr/`.
- **Логи:** структурированный JSON, обязательные поля `requestId`, `userId`, `route`.
  Без `console.log` в продакшне (ESLint-правило).
- **Конфигурация:** всё настраиваемое (нормативы, шаблоны, форматы номеров, лимиты) — в БД
  или переменных окружения, **не в коде**. Хардкод бизнес-значений запрещён.

## 8. Локализация и форматы

- Интерфейс — русский; тексты в словаре (задел на многоязычность).
- Часовой пояс — по магазину (`Store.timezone`), хранение в UTC.
- Формат даты `дд.мм.гггг`, времени `ЧЧ:ММ`.
- Суммы: `12 500,00 ₽` — неразрывный пробел как разделитель разрядов, запятая как десятичный.
- Телефоны: ввод в любом формате, хранение в E.164, отображение `+7 916 123-45-67`.

| Аспект | Решение |
