# 14. Развёртывание: Proxmox, Docker и LXC

Документ отвечает на вопросы заказчика: **нужен ли Docker или проще LXC**, как использовать
**существующий nginx-proxy** и **существующий PostgreSQL 16** (ответы A1).

---

## 1. Ответы на вопросы по инфраструктуре

Заказчик подтвердил (ответы на этапе 0):

| Вопрос | Ответ | Что это меняет |
|--------|-------|----------------|
| Разрешён ли вложенный Docker? | **Да** (`nesting=1`) | Разворачиваем **Docker внутри LXC** — образы готовы |
| Как добавлять сервис в nginx-proxy? | **Через UI** (Nginx Proxy Manager) | Правка файлов не нужна — инструкция для администратора, см. §5 |
| Есть ли доступ LXC к 1С и IP-АТС? | **Да** | Интеграции этапов 3–4 работают напрямую |
| Есть ли PostgreSQL? | **Да, PostgreSQL 16 настроен** | **Свой PostgreSQL НЕ поднимаем** — используем существующий, см. §3 |

---

## 2. Краткий ответ про Docker и LXC

**Docker внутри LXC — рекомендуемый вариант, и он подтверждён ответом A1.**

Docker не обязателен, но даёт то, чего LXC сам по себе не даёт — **воспроизводимую упаковку
приложения**. LXC изолирует операционную систему, но не фиксирует версии Node.js, PostgreSQL,
Redis и MinIO. Без Docker развёртывание превращается в ручную установку и настройку, которую
придётся повторять на staging и при каждом обновлении.

| Критерий | Docker в LXC | Чистый LXC |
|----------|--------------|------------|
| Воспроизводимость сборки | **Высокая** | Низкая |
| Обновление | **Смена тега + рестарт** | Ручные шаги |
| Совпадение dev/prod | **Полное** | Требует дисциплины |
| Требования к хосту | `nesting=1` (подтверждено) | Нет |
| Скорость базы | Неприменимо — **БД внешняя** | Неприменимо |
| Срок этапа 0 | **1 день** | +2–3 дня |

> **Важно:** поскольку PostgreSQL теперь внешний (§3), сравнение скорости базы и
> конкурентного доступа к диску между вариантами теряет смысл. Остаётся главный
> аргумент — воспроизводимость. Docker в LXC выигрывает по нему однозначно.

### 2.1. Что запускается в контейнерах

| Сервис | В Docker? | Почему |
|--------|-----------|--------|
| `web` (Next.js PWA) | **Да** | Наше приложение |
| `api` (NestJS) | **Да** | Наше приложение |
| `worker` (фоновые задачи) | **Да** | Наше приложение |
| PostgreSQL 16 | **НЕТ** | **Существует в инфраструктуре** (ответ A1) |
| Redis 7 | Да | Очереди; если есть в инфраструктуре — можно использовать его |
| MinIO (S3) | Да | Файлы; если есть S3-совместимое хранилище — использовать его |

Если в инфраструктуре есть собственные Redis или S3-совместимое хранилище, задайте
`REDIS_URL` и `S3_ENDPOINT` на них и удалите соответствующие сервисы из compose —
приложение от этого не зависит.

## 3. Использование существующего PostgreSQL 16

**Свой PostgreSQL проект не устанавливает.** Это зафиксировано в
`infra/docker/docker-compose.prod.yml`: сервиса `postgres` там нет.

### 3.1. Чем это отличается от типовой схемы

| Аспект | Было (свой PostgreSQL) | Стало (внешний PostgreSQL) |
|--------|------------------------|----------------------------|
| Установка | Контейнер `postgres:16` | **Ничего не устанавливаем** |
| Адрес в `DATABASE_URL` | `localhost` / имя сервиса | **Сервер предприятия** |
| Резервное копирование БД | Наш скрипт | **Уже настроено** на отдельном сервере БД |
| PITR (WAL) | Наш `archive_command` | **Администратор БД** — уточнить, охвачен ли |
| Расширения (`pg_trgm`) | В `shared_preload_libraries` контейнера | **Администратор БД**, один раз |
| Пул соединений | Не критичен (свой сервер) | **Критичен**: сервер общий! |
| Обновление версии PG | Смена тега образа | **Администратор БД** |

### 3.2. Два риска и их статус

**Риск с соединениями (высокий).** PostgreSQL допускает `max_connections` соединений
на **весь сервер**. Если наше приложение займёт их все, встанут 1С и другие системы.
Решение: пул ограничен переменной `DATABASE_POOL_SIZE`, роль имеет `CONNECTION LIMIT`,
а `infra/db/preflight.sh` проверяет бюджет **до** развёртывания.

**Дефект, найденный при сверке документации с кодом.** Ограничение применялось в
`packages/db/src/index.ts` (общие клиенты `prisma` и `prismaReplica`), но **работающий API
использует не их**: `apps/api/src/common/prisma/prisma.service.ts` создаёт СВОЙ экземпляр
`PrismaClient`, который эту логику не применял. То есть `DATABASE_POOL_SIZE` была
объявлена, задокументирована как «применяется автоматически» и проверялась скриптом
`preflight.sh` — но на реально работающий сервис не влияла, и пул оставался
неограниченным. Исправлено: `PrismaService` применяет ту же функцию `connectionLimit`
из `@app/db`.

**Риск с бэкапами (снижен).** Система резервного копирования **уже организована и
настроена** на отдельном сервере PostgreSQL — создавать ничего не нужно. Остаётся
подтвердить два параметра: охвачен ли **PITR** и **проводилась ли проверка
восстановлением**. Требование RPO ≤ 5 минут (docs/10-nfr-security.md §5) достигается
только непрерывной архивацией WAL; при периодических дампах фактический RPO равен
интервалу между ними (обычно 24 часа). Тогда это фиксируется как **принятое отклонение**.
Зафиксировано как риск R12.

### 3.3. Порядок подготовки

```bash
# 1. Администратор БД создаёт базу, роль и расширения.
#    Готовые команды: infra/db/README.md §1
#    Ключевое: БД с локалью ru_RU.UTF-8 (иначе ФИО сортируются неверно,
#    исправляется только пересозданием БД) и роль НЕ суперпользователь.

# 2. Мы проверяем готовность:
export DATABASE_URL="postgresql://repair_app:<пароль>@pg-server.remixgold.ru:5432/repair?sslmode=prefer"
./infra/db/preflight.sh
# Скрипт проверит версию, права, расширения, бюджет соединений и локаль —
# и вернёт понятный отчёт вместо неясной ошибки при первом деплое.

# 3. Только после успешной проверки — разворачиваем приложение.
```

### 3.4. Согласовать с администратором БД

Резервное копирование **уже настроено** — создавать ничего не нужно, требуется лишь
подтвердить параметры.

| # | Вопрос | Почему важно |
|---|--------|--------------|
| 1 | Охвачен ли **PITR** (непрерывная архивация WAL), или только периодические дампы? | Определяет **фактический** RPO. Без PITR он равен интервалу между дампами (обычно 24 ч), а не 5 мин |
| 2 | Если дампы — какова их периодичность? | Чтобы зафиксировать RPO честно, а не декларативно |
| 3 | **Проводилась ли проверка восстановлением?** Когда? | Копия без проверки гарантии не даёт: о непригодности узнают при аварии |
| 4 | Срок хранения копий | Требуется ≥ 90 дней (3-2-1) |
| 5 | Есть ли **отдельная база для staging**? Можно ли развернуть её из копии? | Нужна для приёмки и проверки миграций без риска для прода |
| 6 | Каково `max_connections` и сколько свободно? | Бюджет нашего пула |
| 7 | Требует ли сервер TLS (`sslmode=require`)? | Настройка строки подключения |
| 8 | Кто и когда выполняет `VACUUM`/переиндексацию? | Не пересекаться по нагрузке |
| 9 | Есть ли окна обслуживания (совпадающие с 1С)? | Время применения миграций |

**Если PITR не охвачен** — это не блокирует проект, но требование «RPO ≤ 5 минут»
фиксируется как **принятое отклонение** с указанием фактического значения. Для системы
ремонта потеря суточного объёма заказов означает ручное восстановление из бумажных
квитанций, поэтому решение должно быть осознанным, а не подразумеваемым.

## 4. Схема развёртывания

```
Proxmox VE 7.4
│
├── существующий nginx-proxy (LXC или VM)
│     └── TLS (Let's Encrypt), маршрутизация       ← уже есть
│           │
│           └── repair.remixgold.ru ──▶ 192.168.1.50:3000
│
├── существующий PostgreSQL 16                        ← уже есть
│     └── база repair, роль repair_app                ← создаёт администратор
│           ▲
│           │ 5432 (локальная сеть)
│           │
└── LXC «repair-crm» (nesting=1)                      ← создаём мы
      └── docker compose
            ├── web      (Next.js PWA)   :3000
            ├── api      (NestJS)        :4000
            ├── worker   (фоновые задачи)
            ├── redis    (очереди)       ← только внутри сети
            └── minio    (файлы)         ← только внутри сети
```

**Порты наружу:** только `3000` (web) и `4000` (api). PostgreSQL, Redis и MinIO
наружу не публикуются.

**Ресурсы LXC.** Поскольку PostgreSQL внешний, требования ниже, чем в типовой схеме:
базе не нужны ни CPU, ни RAM, ни диск внутри контейнера.

| Ресурс | Минимум | Рекомендуется |
|--------|---------|---------------|
| vCPU | 2 | 4 |
| RAM | 4 ГБ | 8 ГБ |
| Диск (система + Redis + MinIO) | 40 ГБ | 100 ГБ SSD |
| Диск под бэкапы файлов | — | отдельный, по объёму фото |

> **Требование к hardware.** При выборе диска учтите объём файлов: фотографии изделий
> и записи разговоров (хранение 1 год, ТЗ п. 2.4). Оценка — `docs/10-nfr-security.md`.

## 5. Развёртывание в LXC с Docker (пошагово)

Предполагается, что nginx-proxy и PostgreSQL уже работают (ответы A1).

> **Порядок важен:** сначала администратор БД готовит базу (§3.3), затем мы проверяем
> её готовность через `infra/db/preflight.sh` и **только потом** разворачиваем приложение.
> Иначе первый деплой упадёт на миграции с неясной ошибкой прав.

```bash
# ---------- На хосте Proxmox ----------
pct create 200 local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst \
  --hostname repair-crm \
  --cores 4 --memory 8192 --swap 2048 \
  --rootfs local-zfs:100 \
  --features nesting=1 \
  --net0 name=eth0,bridge=vmbr0,ip=192.168.1.50/24,gw=192.168.1.1 \
  --unprivileged 1 --onboot 1
```

> **Ресурсы уменьшены** относительно типовой схемы (4 vCPU / 8 ГБ вместо 6/16):
> PostgreSQL теперь внешний, и база не расходует память и диск внутри контейнера.
>
> **`nesting=1` обязателен** — подтверждено ответом A1. Для Docker рекомендуется
> `--unprivileged 1` (безопаснее). Если Docker не запускается из-за прав на keyring,
> администратор добавляет нужные правила AppArmor — вместо отключения профиля целиком.

```bash
pct start 200
pct exec 200 -- bash

# ---------- Внутри LXC ----------
apt update && apt upgrade -y
apt install -y curl git ca-certificates

# Docker (официальный способ)
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/debian/gpg \
  -o /etc/apt/keyrings/docker.asc
chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/debian $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  > /etc/apt/sources.list.d/docker.list
apt update
apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
systemctl enable --now docker

# Проверка, что вложенность и keyctl работают
docker run --rm hello-world
```

> Если `docker run` падает с ошибкой прав доступа к keyring — администратор
> настраивает AppArmor/keyctl для контейнера. Это единственная известная сложность
> с Docker в LXC; после её решения конфигурация стабильна.

```bash
# ---------- Код и данные ----------
# Каталогов postgres больше нет — БД внешняя.
mkdir -p /srv/repair-crm/{redis,minio,backup}
git clone <репозиторий> /opt/repair-crm
cd /opt/repair-crm

cp .env.example .env
nano .env
#  - NODE_ENV=production
#  - APP_URL=https://repair.remixgold.ru
#  - TRUST_PROXY=1
#  - DATABASE_URL → существующий PostgreSQL предприятия (§3.3)
#  - DATABASE_POOL_SIZE → согласованный бюджет соединений
#  - JWT_*_SECRET и CSRF_SECRET → openssl rand -base64 48
#  - S3_ACCESS_KEY, S3_SECRET_KEY
```

```bash
# ---------- Проверка внешней БД ДО развёртывания ----------
./infra/db/preflight.sh     # должен вернуть «Всё готово к развёртыванию»

# ---------- Сборка и запуск ----------
docker compose --env-file .env -f infra/docker/docker-compose.prod.yml up -d --build

# ---------- Миграции (отдельным шагом, ДО переключения трафика) ----------
docker compose --env-file .env -f infra/docker/docker-compose.prod.yml exec api \
  npx prisma migrate deploy --schema packages/db/prisma/schema.prisma

# ---------- Ручные шаги после миграции (права суперпользователя БД) ----------
# Ограничения CHECK и запрет изменения audit_log:
#   packages/db/prisma/migrations/README.md §4 и §6
# Выполняет администратор БД.

# ---------- Начальные справочники ----------
docker compose --env-file .env -f infra/docker/docker-compose.prod.yml exec api \
  npx tsx packages/db/prisma/seed.ts
```

```bash
# ---------- Проверка ----------
curl -fsS http://localhost:3000/           && echo "web OK"
curl -fsS http://localhost:4000/health/live && echo "api OK"
# /health/ready проверяет доступность ВНЕШНЕЙ БД — важнее всего при внешней базе
curl -fsS http://localhost:4000/health/ready && echo "БД доступна"

# ---------- Автозапуск ----------
systemctl enable docker   # compose-сервисы поднимаются с restart: always
```

Остаётся направить внешний nginx-proxy на `192.168.1.50:3000` через его UI — см. §5.

## 6. Вариант без Docker (чистый LXC)

Если Docker неприемлем, приложение разворачивается как системные сервисы. Ниже — только
отличия; логика приложения не меняется.

```bash
# PostgreSQL НЕ устанавливаем — используем существующий сервер предприятия (§3).
apt install -y redis-server nodejs npm
# MinIO — бинарником в /usr/local/bin/minio + systemd-юнит
# Node.js ≥ 20: из NodeSource, если в репозитории Debian версия старше
```

> **Установка PostgreSQL в этом варианте не требуется** — база внешняя (ответ A1).
> Нужен только клиент для проверки и миграций: `apt install -y postgresql-client-16`.

Сборка монорепозитория:

```bash
cd /opt/repair-crm
npm ci
npm run build --workspace @app/shared   # обязательно первым: API зависит от него
npx prisma generate --schema packages/db/prisma/schema.prisma
npx tsc -p apps/api/tsconfig.json       # API → apps/api/dist
npm run build --workspace @app/web      # веб → apps/web/.next
```

Два systemd-юнита — API и воркер (у воркера меняется только `ExecStart`):

```ini
# /etc/systemd/system/repair-api.service
[Unit]
Description=CRM ремонта — API
# postgresql.service НЕ указан: БД внешняя, её запуск от нас не зависит.
After=network-online.target redis-server.service
Wants=network-online.target

[Service]
Type=simple
User=repair
WorkingDirectory=/opt/repair-crm
EnvironmentFile=/opt/repair-crm/.env
ExecStart=/usr/bin/node apps/api/dist/main.js
Restart=always
RestartSec=5
# Ограничения безопасности: процессу не нужны привилегии
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

> **`After=network-online.target` важен:** база теперь по сети, поэтому нельзя стартовать
> до готовности сети. Иначе API упадёт при загрузке, если БД недоступна в первые секунды.
> Перезапуск спасает (`Restart=always`), но чистое решение — ждать сеть.

```bash
systemctl daemon-reload
systemctl enable --now repair-api repair-worker
```

> **Не запускайте Next.js в продакшне через `next dev`** — используйте `next start`
> (или `node apps/web/.next/standalone/apps/web/server.js` при `output: 'standalone'`).

#### Шаблоны уведомлений и воркер

Два шага развёртывания, которые легко пропустить, потому что их отсутствие не
видно: API отвечает 200, страницы открываются.

* **Шаблоны уведомлений.** Настроечные данные, которые сид в продакшне не
  создаёт: он добавляет демонстрационные заказы и учётные записи. Синхронизация
  выполняется `scripts/sync-templates.mjs` — она **добавляет** недостающие
  шаблоны и сообщает о расхождении текстов, **не перезаписывая** их: правка
  формулировки администратором не должна теряться при выпуске. Для намеренного
  обновления текстов — флаг `--update-texts`. Без этого шага уведомление уходит
  по запасному тексту из кода: оно работает, но выглядит иначе, чем задумано.

* **Воркер.** `repair-worker` выполняет эскалации просрочки (раз в 15 минут) и
  перевод в «Невостребовано» (раз в сутки). Его отсутствие **не проявляется
  никак**: уведомления просто никогда не приходят. Юниты хранятся в
  `infra/systemd/` и устанавливаются при каждом развёртывании, а `deploy.sh`
  включает воркер и проверяет, что он активен. В журнале при старте видно обе
  задачи:

  ```bash
  systemctl is-active repair-worker
  tail -5 /opt/repair/logs/worker.log
  # {"worker":"runner","message":"Воркер запущен: escalations (интервал 900000 мс)"}
  # {"worker":"runner","message":"Воркер запущен: unclaimed-orders (интервал 86400000 мс)"}
  ```

**Что учесть в этом варианте:**

- **Обновления ОС и зависимостей** — на вас: Redis, Node.js, MinIO (PostgreSQL
  обслуживает администратор БД, и это единственный компонент, который в этом варианте
  не добавляет работы).
- **Откат версии** — снапшотом LXC (Proxmox) перед обновлением. Удобно, но требует
  остановки сервиса на время снапшота.
- **Совпадение с dev** — разработка идёт в Docker, продакшн без него: возможно
  расхождение версий. Минимизируется фиксацией версий в документации.
- **Срок этапа 0** увеличивается на 2–3 дня.

> **Важно:** даже без Docker **база данных остаётся внешней**. Этот вариант не возвращает
> необходимость следить за резервным копированием БД, обновлениями PostgreSQL и его
> параметрами — всё это по-прежнему зона администратора БД (`infra/db/README.md`).

## 7. Сравнение вариантов

| Критерий | Docker в LXC | Чистый LXC | VM |
|----------|--------------|------------|-----|
| Воспроизводимость сборки | **Высокая** | Низкая | Высокая |
| Простота обновления | **Одна команда** | Ручные шаги | Одна команда |
| Ресурсы | **Экономно** | Экономно | Требует больше |
| Совпадение dev/prod | **Полное** | Требует дисциплины | Полное |
| Требования к хосту | `nesting=1` — **подтверждено** | Нет | Виртуализация |
| Скорость базы | Неприменимо — БД внешняя | Неприменимо | Неприменимо |
| Изоляция | Средняя | Средняя | **Высокая** |
| Риск при обновлении | Низкий | Средний | Низкий |

**Решение принято: Docker внутри LXC.** Ответ A1 подтвердил, что вложенность разрешена,
поэтому единственное препятствие снято. Вариант без Docker сохранён в §6 как резервный —
если политика инфраструктуры изменится.

## 8. Настройка nginx-proxy через UI

Ответ A1: маршрутизация настраивается **через UI** — это Nginx Proxy Manager или аналог.
Правка файлов на диске **не требуется**, поэтому администратору нужны только параметры
ниже. Технические детали заголовков — `infra/proxy/README.md`.

### 8.1. Что создать в UI

**Proxy Host** со следующими полями:

| Поле | Значение |
|------|----------|
| Domain Names | `repair.remixgold.ru` |
| Scheme | `http` |
| Forward Hostname / IP | `192.168.1.50` (адрес LXC с приложением) |
| Forward Port | `3000` |
| Cache Assets | выключено (интерфейс динамический) |
| Block Common Exploits | включено |
| Websockets Support | **включено** (нужно для live-обновлений Next.js) |

**SSL** (вкладка в том же окне):

| Поле | Значение |
|------|----------|
| SSL Certificate | `Request a new SSL Certificate` (Let's Encrypt) |
| Force SSL | **включено** — перенаправляет HTTP на HTTPS |
| HTTP/2 Support | включено |
| HSTS Enabled | включено |
| HSTS Subdomains | по политике предприятия |
| Email | контакт для уведомлений Let's Encrypt |
| I Agree to the Let's Encrypt Terms | включено |

**Advanced** (поле «Custom Nginx Configuration») — добавить:

```nginx
# Размер загрузки: фото изделий с телефона.
client_max_body_size 25m;

# X-Forwarded-Proto обязателен: без него приложение считает соединение
# небезопасным и не отдаёт cookies с флагом Secure — вход не работает.
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Request-Id      $http_x_request_id;

# Таймауты: выгрузка отчётов может занимать время.
proxy_read_timeout 60s;
proxy_send_timeout 60s;

# Проверка живости не пишется в лог.
location = /health/live {
    access_log off;
    proxy_pass http://192.168.1.50:4000/health/live;
}
```

> **Nginx Proxy Manager обычно сам передаёт `X-Forwarded-*`.** Но `client_max_body_size`
> по умолчанию — 1 МБ, и **загрузка фотографии с телефона упадёт с ошибкой 413**.
> Увеличение лимита — обязательный шаг, а не опциональный.

### 8.2. Проверка после настройки

```bash
# 1. Сертификат валиден, интерфейс отвечает
curl -fsS -o /dev/null -w 'HTTP %{http_code}\n' https://repair.remixgold.ru/

# 2. Проверка живости API через прокси
curl -fsS https://repair.remixgold.ru/health/live && echo "API жив"
curl -fsS https://repair.remixgold.ru/health/ready && echo "БД доступна"

# 3. ГЛАВНАЯ ПРОВЕРКА — вход в систему.
#    Если cookies с Secure не сохраняются, вход «молча» не работает:
#    это самый частый симптом неверного X-Forwarded-Proto.
#    Проверяется вручную: открыть https://repair.remixgold.ru, войти,
#    обновить страницу — сессия должна сохраниться.

# 4. Загрузка файла: прикрепить фото к тестовому заказу.
#    Ошибка 413 означает, что client_max_body_size не увеличен.
```

### 8.3. Что остаётся на стороне администратора

| Область | Ответственность администратора |
|---------|-------------------------------|
| Сертификаты Let's Encrypt и их продление | Прокси (автоматически) |
| HSTS, TLS 1.2+, HTTP/2 | Прокси |
| Домен `repair.remixgold.ru` → `192.168.1.50:3000` | Прокси (UI) |
| `client_max_body_size`, таймауты | Прокси (UI, Advanced) |
| Лимиты запросов на вход | Приложение (Throttler) + грубый лимит в прокси |
