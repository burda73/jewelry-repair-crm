# 06. Спецификация API

Базовый путь: `/api/v1`. Формат — JSON. Аутентификация — JWT в httpOnly-cookie.
Каждый ответ с ошибкой имеет единый формат. Спецификация генерируется автоматически
(`@nestjs/swagger`) и доступна на `/api/docs` в средах dev/staging.

## 1. Общие правила

### 1.1. Формат ошибки

```json
{
  "statusCode": 409,
  "code": "PREPAYMENT_REQUIRED",
  "message": "Старт работ заблокирован: предоплата 3000 ₽ не внесена",
  "details": { "requiredMinor": 300000, "paidMinor": 0 },
  "requestId": "01J8Z..."
}
```

Машиночитаемый `code` — часть контракта, фронтенд ориентируется на него, а не на текст.

### 1.2. Пагинация (keyset)

```
GET /orders?limit=50&cursor=eyJjIjoiMjAyNS0wOS0xNVQxMDowMDowMFoiLCJpIjoiY20xIn0
```

```json
{
  "items": [ ... ],
  "nextCursor": "eyJjIjoi...",
  "hasMore": true
}
```

`OFFSET` не используется — на больших объёмах он деградирует.

### 1.3. Идемпотентность

Мутирующие запросы, влияющие на деньги (`POST /payments`), принимают заголовок
`Idempotency-Key`. Повтор с тем же ключом возвращает результат первой операции,
а не создаёт дубль.

### 1.4. Оптимистичная блокировка

`PATCH /orders/:id` и `PUT /orders/:id/works` принимают `version`. При расхождении:
`409 STALE_VERSION` + актуальный объект в `details`.

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/orders/:id/approvals` | Список согласований |

| POST | `/orders/:id/approvals` | Создать согласование (`approval:create`: RECEIVER, PRODUCTION_MANAGER, ADMIN) |
| PATCH | `/approvals/:id` | Изменить результат |
| GET | `/orders/:id/recordings` | Записи звонков по заказу |
| POST | `/orders/:id/recordings/:recId/link` | Привязать запись вручную |
| GET | `/recordings/unmatched` | Неразобранные звонки |
| GET | `/recordings/:id/stream` | Подписанная ссылка на прослушивание |

```json
// Устное согласие (ТЗ п. 2.4)
POST /orders/:id/approvals
{ "channel": "PHONE_VERBAL", "result": "APPROVED",
  "amountMinor": 1250000, "termDays": 10,
  "comment": "Клиент согласился по телефону, запись сохранена" }
```

**`isVerbal` и `promisedAt` в запрос НЕ передаются — их вычисляет сервер:**

| Поле | Как определяется | Почему не от клиента |
|------|------------------|----------------------|
| `isVerbal` | `channel === 'PHONE_VERBAL'` | Это следствие канала, а не отдельный флаг. Иначе запрос `channel: SMS, isVerbal: true` дал бы бейдж «согласовано устно» без устного разговора |
| `promisedAt` | `addWorkingDays(сейчас, termDays)` по производственному календарю | Присланную дату можно поставить на выходной или задним числом, и нормативы этапов (ТЗ п. 2.7) посчитали бы дедлайн неверно |

`approvedAt` заполняется только для `result = APPROVED`: у ответа «не дозвонились»
момента согласия не существует.

**Согласованная сумма может отличаться от суммы заказа.** Тогда сервер фиксирует
корректировку с причиной «Согласование с клиентом (…канал…)», и
`totalAmountMinor` приводится к согласованной сумме. Иначе сумма заказа и
согласованная сумма разошлись бы молча — а клиент подтвердил именно вторую.

```json
// Корректировка калькуляции (ТЗ п. 2.3)
POST /orders/:id/adjustments
{ "targetType": "TOTAL", "amountAfterMinor": 300000, "reason": "Клиент отказался от полировки" }
```

`amountBeforeMinor` и `deltaMinor` вычисляет сервер: если принять «было» от
клиента, в истории окажется сумма, которой в заказе не было.

**Инвариант `totalAmountMinor = worksTotalMinor + stonesTotalMinor − discountMinor`
выполняется всегда** (docs/03-data-model.md §3.2). При согласовании суммы БОЛЬШЕ
суммы строк `discountMinor` становится отрицательным — это надбавка (срочность,
сложность); интерфейс показывает её строкой «Надбавка». Расчёт выполняет
`discountForTotal` из `@app/shared`, а не присваивание итога напрямую.

| Код | Когда |
|-----|-------|
| `409 ADJUSTMENT_BELOW_PAID` | Новая сумма ниже уже внесённой — это возврат, оформляется операцией `REFUND` |
| `409 ORDER_FINAL` | Заказ в терминальном статусе (закрыт, выдан, отменён) |
| `404 NOT_FOUND` | `targetId` не принадлежит этому заказу (не подтверждаем существование чужой строки) |

### 6.1. Квитанция (`GET /orders/:id/receipt`)

Отдаётся готовый PDF (`Content-Type: application/pdf`,
`Content-Disposition: inline`, `Cache-Control: no-store`). Браузер открывает его
во встроенном просмотрщике, откуда печатают на обычном A4 — драйверы и агенты
печати не нужны.

| Что печатается | Откуда берётся |
|----------------|----------------|
| Организация, магазин | `COMPANY_NAME`, `Store.name` |
| Номер заказа крупно, текстом | `Order.orderNo` |
| QR-код | `buildReceiptQr()` → `repair://order/{номер}` |
| Резервный `Code128` | `buildReceiptBarcode()` → номер заказа |
| Изделия, металл, работы, камни | строки заказа, цены на момент приёма |
| Сумма, скидка/надбавка, предоплата, внесено | денежные поля заказа |
| Срок готовности, телефон, статус | `Order.dueAt`, `Customer.phoneNormalized`, статус |
| Строки для подписей сторон | — |

**Это действие, а не чтение.** Каждый запрос увеличивает `Order.receiptPrintCount`
и пишет `Order.receiptLastPrintedAt`, в аудит добавляется `RECEIPT_PRINT` с номером
копии. Перепечатки видны в истории заказа — они защищают от ситуации «клиент принёс
квитанцию, а по ней уже выдали другое изделие».

**Кэширование запрещено** (`no-store`): квитанция содержит ФИО и телефон клиента,
хранить её в браузере или на промежуточном прокси нельзя.

**Область видимости проверяется до увеличения счётчика** — неудачная попытка
напечатать чужой заказ не оставляет следа в его истории и отдаёт `404` (не `403`,
чтобы не подтверждать существование чужого заказа).

**Требования к фону кодов.** `bwip-js` по умолчанию рисует код на ПРОЗРАЧНОМ фоне.
Такой код выглядит верным, но не декодируется ни на одном масштабе, то есть основной
сценарий («сканируем квитанцию») не работает. Фон задан белым явно; проверено
декодированием QR, извлечённого из готовой страницы PDF.

## 6.2. Фотографии изделий (ТЗ п. 2.1)

| Метод | Путь | Описание | Роли |
|-------|------|----------|------|
| POST | `/orders/:id/items/:itemId/photos` | Загрузить фото (`multipart/form-data`, поле `files`) | `order:update` |
| GET | `/orders/:id/items/:itemId/photos` | Фотографии изделия | `order:read` |
| GET | `/photos/:id` | Файл фото (`?variant=thumb` — уменьшенная копия) | `order:read` |
| DELETE | `/photos/:id` | Удалить фото | `order:update` |

```http
POST /api/v1/orders/:id/items/:itemId/photos
Content-Type: multipart/form-data; boundary=...

files=<файл>[,<файл>...]   // до 10 файлов за запрос
kind=INTAKE                // INTAKE | DEFECT | RESULT | AFTER_REPAIR
caption=Состояние при приёме
```

**Хранилище — локальный диск, раздача через API** (`STORAGE_DRIVER=LOCAL`).
S3/MinIO в инфраструктуре нет (ответ A1), а на диске LXC есть запас. В базе
хранится только ключ объекта (`FileObject.objectKey`), поэтому переезд на S3
не потребует миграции ссылок; драйвер переключается переменной окружения.

**Ответ содержит `url` и `thumbnailUrl` с префиксом `/api/v1`.** Без префикса
ссылка была бы нерабочей: браузер обращается к тому же источнику, что и
интерфейс, а прокси перенаправляет на API только пути `/api/v1/*` — миниатюры
не отображались, хотя файл на сервере был.

**Обработка изображения.** Фото перекодируется в JPEG, уменьшается до 1600 px
по длинной стороне, ориентация из EXIF применяется к пикселям (`rotate()`),
рядом кладётся копия 320 px для списков. Побочный эффект — геометка телефона
сотрудника не сохраняется: фото изделия не должно содержать его персональные
данные.

| Код | Когда |
|-----|-------|
| `400 INVALID_IMAGE` | Файл не является изображением или больше `UPLOAD_MAX_BYTES` |
| `400 INVALID_PHOTO_KIND` | `kind` вне списка видов |
| `400 NO_FILES` | Не передан ни один файл |
| `404 NOT_FOUND` | Заказ вне области видимости, либо изделие не принадлежит заказу |

**Права и область видимости.** Загрузка и удаление требуют `order:update`,
чтение — `order:read`. Область видимости проверяется по **заказу**: чужой
магазин получает `404` (не `403` — не подтверждаем существование заказа).
Файлы отдаются только через API, а не статикой: прямая раздача каталога
открыла бы любой файл по угадываемому адресу.

`PRODUCTION` (LOGISTICIAN, PRODUCTION_MANAGER) видят все рейсы; области магазина
— только рейсы через свои точки. У логиста список магазинов пуст, поэтому
ограничение по области, а не по числу магазинов: у логиста магазинов нет вовсе,
и проверка «нет магазинов → ничего не видно» отдавала бы ему пустой список.

к логистике (`403 FORBIDDEN_ROLE`). Приём партии (задача 2.5) — отдельное
действие со своим правом, оно появится вместе с этой задачей.

### 8.1 Правила состава партии (задача 2.1)

Правило одно и то же в API и в интерфейсе: функция `checkBatchEligibility` из
`@app/shared`. Иначе две реализации одного правила расходятся — это уже
случалось в проекте со словарями этапов (`docs/15` «Дефект 26»).

| Условие | Направление | Отказ |
|---------|-------------|-------|
| Заказ уже в активной партии (`DRAFT`, `ACT_FORMED`, `IN_TRANSIT`) | любое | `ALREADY_IN_BATCH` |
| Статус не `QUEUED_FOR_DISPATCH` | TO_PRODUCTION | `WRONG_STATUS` |
| Статус не `IN_TRANSIT_TO_STORE` | TO_STORE | `WRONG_STATUS` |
| Принят в другом магазине | TO_PRODUCTION | `WRONG_STORE` |
| Закреплён за другим цехом | TO_PRODUCTION | `WRONG_WORKSHOP` |
| Уже числится в этом магазине | TO_STORE | `SAME_STORE` |

`RECEIVED` и `CANCELLED` заказ **не блокируют**: принятая партия выполнила
задачу, отменённая не состоялась. Если бы они блокировали, заказ навсегда
остался бы «в партии», которой уже нет.

Состав проверяется **целиком до первой записи**: иначе половина заказов
добавилась бы, а запрос завершился ошибкой, и логист не понял бы, что именно
попало в партию.

Исключение заказа не удаляет строку, а помечает её `removedAt` с причиной:
состав входит в акт приёма-передачи, и «куда делся заказ» должно быть
объяснимо после подписания. Повторное включение снимает отметку.

### 8.2 Акт приёма-передачи (задача 2.2)

Акт формируется по партии в статусе `DRAFT` и переводит её в `ACT_FORMED` — в
одной транзакции. Если бы акт создался, а статус не сменился, партия осталась бы
черновиком и допускала правку состава под уже существующим актом.

| Правило | Поведение |
|---------|-----------|
| Пустая партия | `400`: «акт на ноль изделий» подписывать бессмысленно |
| Повторное формирование | `409` с номером уже существующего акта |
| Партия не в `DRAFT` | `409` |
| Партия вне области видимости | `404` |

**Состав замораживается.** После формирования акта добавление и исключение
заказов запрещены (`409`). Акт — документ о передаче конкретных изделий: если
после подписания убрать заказ из партии, подписанный акт перестанет
соответствовать действительности, а изделие окажется «переданным» без записи о
том, что с ним стало.

**Снимок состава** (`BatchAct.itemsSnapshot`) фиксируется один раз в момент
формирования и больше не пересчитывается. Иначе переименованный заказ или
исправленное ФИО клиента меняли бы уже подписанный документ. Снимок содержит
номер партии, направление, наименования отправителя и получателя, число заказов,
общую сумму в копейках и список заказов, отсортированный по номеру — порядок
предсказуем, поэтому два экземпляра одного акта выглядят одинаково.

**Номер акта годовой** (`АПП-25-000118`, счётчик `ACT:25`), в отличие от номера
партии, который дневной (`П-250916-004`, счётчик `BATCH:20250916`). Так задан
формат в `docs/03` §2.

### 8.3 PDF акта и подпись сторон (задача 2.3)

`GET /batches/:id/act/pdf` отдаёт PDF потоком (`inline`, без сохранения на
диске): акт чаще всего открывают на печать. `POST /batches/:id/act/store`
сохраняет ту же версию в хранилище и привязывает её к акту — потоковый PDF
нельзя предъявить, а сохранённый можно.

**Документ собирается из снимка состава**, а не из текущих заказов: подписанный
акт обязан оставаться тем же документом, даже если заказ позже переименовали.

**Шрифт встраивается в PDF.** На сервере нет ни одного системного шрифта
(`/usr/share/fonts` отсутствует), поэтому без встроенного DejaVu кириллица
вышла бы пустыми квадратами. Тот же приём, что в PDF-квитанции заказа.

Строки подписей печатаются **всегда** — и до подписания (пустые линии, чтобы
подписать на бумаге), и после (ФИО и дата). Акт без строк подписей юридически
бессмыслен. Состав переносится по страницам: партия из 40 заказов занимает
несколько листов, а не по странице на строку.

| Подпись | Правило |
|---------|---------|
| Повторная подпись той же стороны | `409`: подпись означала бы не конкретный момент передачи, а любой |
| Акт не сформирован | `409` (партия не в `ACT_FORMED`) |
| Партия без акта | `404` |
| Неизвестная сторона | `400` |

Сторона задаётся явно (`FROM` / `TO`), а не выводится из роли: получатель и
отправитель подписывают один и тот же документ, и система не должна решать за
человека, с чьей стороны он подписывает.

### 8.4 Отправка и приём партии (задача 2.5)

Отправка переводит в «в пути» СРАЗУ все заказы партии, приём — в производство
или в «готов к выдаче». Оба действия идут в **одной транзакции**: если каждый
заказ откроет собственную, половина партии уедет, а половина останется — и на
складе окажется состав, которого нет ни в одном документе. Акт подписан на все
изделия, а в пути только часть.

Перевод идёт через общую таблицу переходов (`OrderWorkflowService`), а не
собственным `UPDATE status`: иначе были бы обойдены проверка роли,
обязательность акта и запись в историю статусов — заказ уехал бы без следа о
том, кто и когда его отправил.

**Целевой статус зависит от направления**, и ветки не пересекаются:

| Направление | Отправка | Приём |
|-------------|----------|-------|
| `TO_PRODUCTION` (в цех) | `IN_TRANSIT_TO_PRODUCTION` | `IN_PRODUCTION` |
| `TO_STORE` (в магазин) | `IN_TRANSIT_TO_STORE` | `READY_FOR_PICKUP` |

Перепутать ветки значит отправить заказ в цех, который ждёт его из цеха.

| Действие | `DRAFT` | `ACT_FORMED` | `IN_TRANSIT` | `RECEIVED` | `CANCELLED` |
|----------|---------|--------------|--------------|------------|-------------|
| Отправить | `409` | да | `409` | `409` | `409` |
| Принять | `409` | `409` | да | `409` | `409` |

Из `DRAFT` отправить нельзя: перевозка изделий клиентов без акта приёма-передачи
означает, что при утрате нечем подтвердить, что именно и в каком виде приняли.
Пустую партию отправить тоже нельзя — акт подписан на нулевой состав.

**Роль проверяется таблицей переходов, а не правом `logistics:manage`.**
Отправку рейса в цех выполняет логист или руководитель производства, приём
цехом — только руководитель производства, приём магазином — приёмщик или
логист. Логист, попытавшийся принять партию в цехе, получит `403`: право
`logistics:manage` есть, а перехода `IN_TRANSIT_TO_PRODUCTION → IN_PRODUCTION`
для его роли в таблице нет.

Операция **повторяема**: заказ, уже находящийся в целевом статусе, пропускается.
Повторный вызов после частичного сбоя доводит партию до конца, а не падает на
«переход недопустим».

### 8.4.1 Экран курьера (задача 2.7)

| Метод | Путь | Описание | Право |
|-------|------|----------|-------|
| GET | `/batches/my-deliveries` | Незавершённые рейсы курьера | `logistics:read` |
| GET | `/batches/scan?code=…` | Найти партию по отсканированному коду | `logistics:read` |

**`my-deliveries` показывает только назначенное на сотрудника.** Отдельной роли
«курьер» в системе нет: по матрице ролей (docs/02 §4) доставку ведёт
`LOGISTICIAN` — «Логист / курьер». Поэтому «свой список» определяется
**назначением** (`courierId`), а не ролью. Исключение — `PRODUCTION_MANAGER` и
`ADMIN`: они рейсы распределяют и видят все незавершённые, включая ещё не
назначенные, иначе раздать было бы нечего. Завершённые рейсы (`RECEIVED`,
`CANCELLED`) в список не попадают. Порядок: сначала рейсы «в пути», самые
задержанные сверху, затем ожидающие отправки.

**`scan` принимает то, что прочитал сканер, без предварительной обработки на
клиенте.** Разбор (`repair://order/…`, перевод строки, регистр) выполняется на
сервере — там же, где лежат правила (`normalizeScanInput`, `parseOrderNoFromScan`).
Поиск идёт в два шага: сначала по **точному номеру партии** (`П-250916-001`,
без учёта регистра), затем по **номеру заказа из состава** — курьер может
сканировать квитанцию изделия, чтобы понять, в каком рейсе оно едет. Если ничего
не найдено, ответ `404` с кодом `BATCH_NOT_FOUND`, а не пустой объект: пустой
ответ выглядел бы как «рейс есть, но пустой». Область видимости применяется в
обоих запросах, поэтому чужой рейс не находится и по известному номеру.

### 8.5 Отслеживание «в пути» (задача 2.6)

Каждая партия в ответе содержит поле `transit`:

```json
{
  "elapsedHours": 20.4,
  "normHours": 8,
  "level": "OVERDUE",
  "isOverdue": true,
  "message": "В пути 20 ч при норме 8 ч — доставка не подтверждена"
}
```

**Состояние считается на чтение, а не хранится в базе.** «В пути 6 часов» — это
разница между текущим моментом и `dispatchedAt`; записанное значение устарело бы
сразу после записи и требовало бы воркера для обновления.

**Уровней три, а не флаг «просрочено».** Флаг загорается сразу и перестаёт
различать «опаздывает на 20 минут» и «пропала сутки назад» — а это разные
действия. Границы: до `normHours` включительно — `ON_TIME`, дальше `LATE`, от
`normHours × 2` — `OVERDUE`.

**Норматив берётся из настройки `logistics.transitNormHours`**, по умолчанию 8
часов. Городской и междугородний рейс имеют разную норму, и «в пути 6 часов» без
неё ничего не значит; менять значение должен логистик, а не разработчик. Значение
ноль, отрицательное или не число **заменяется значением по умолчанию**: деление
на ноль дало бы `Infinity`, и партия навсегда осталась бы «в норме» — тревога не
сработала бы никогда.

**Отметка отправки в будущем** (сбитые часы, ручная правка) даёт `elapsedHours: 0`:
«в пути −3 часа» бессмысленно.

`GET /batches/in-transit` возвращает только партии в статусе `IN_TRANSIT` и
сортирует их **по убыванию времени в пути**, а не по дате создания. В обычном
списке машина, пропавшая сутки назад, оказалась бы ниже вчерашней городской — то
есть ровно то, что требует вмешательства, логист увидел бы последним. Сортировка
выполняется в памяти: `ORDER BY` по вычисляемому полю невозможен, а число партий
«в пути» ограничено числом машин в рейсе.

### 8.6 Фотофиксация партии (задача 2.4)

Снимок — доказательство состояния тары и содержимого на момент передачи. При
споре «изделие поцарапано» или «недостача» решает не подпись (её ставят, не
разглядывая каждый пакет), а фотография с датой и автором.

Файлы обрабатываются так же, как фото изделий: уменьшение до 1600 px, поворот по
EXIF, отдельная миниатюра 320 px. Ключ хранилища наружу не отдаётся — в ответе
только адрес `/api/v1/batches/photos/:id`, а доступ проверяется правами и
областью видимости партии. Файл отдаётся с `Cache-Control: private, no-store`:
это свидетельство о передаче изделий клиентов, и кэшировать его нельзя.

**Загружать фото можно и после отправки** (в пути, при приёмке): снимок при
приёмке так же ценен, как при отправке, — он фиксирует, в каком виде партия
доехала, и разбирает спор «повредили в дороге или сдали такими». **Удалять —
только до отправки:** после отъезда фото уже часть записи о передаче, и
пропавшее задним числом доказательство хуже, чем его отсутствие.

| Действие | `DRAFT` | `ACT_FORMED` | `IN_TRANSIT` | `RECEIVED` | `CANCELLED` |
|----------|---------|--------------|--------------|------------|-------------|
| Загрузить фото | да | да | да | да | `409` |
| Удалить фото | да | да | `409` | `409` | `409` |

Причина отказа разная для «в пути» и «принята»: в первом случае фото ещё можно
переснять и дополнить, во втором запись закрыта.

Если запись в базу не создалась, файл убирается с диска: иначе остался бы
«фото-призрак» — файл, который никто не найдёт и не удалит.

### 8.7 График и лимит (задача 2.1)

«Формирование партий по графику» (ТЗ п. 2.6) нигде не было конкретизировано.
Принято так:

* **Дата в номере партии — плановая дата отправки**, а не момент создания
  записи. Рейс на 16 сентября логист планирует заранее, и `П-250916-004`
  означает «четвёртая партия рейса 16 сентября». Если плановая дата не задана,
  берётся текущий момент.
* **Счётчик партий — на календарный день по Москве**, привязанный к той же
  дате, что стоит в номере.
* **Лимит состава настраивается** ключом `Setting.logistics.batchMaxItems` и по
  умолчанию **не задан**. Включённый «на глазок» лимит блокировал бы работу
  точки, поэтому по умолчанию его нет, а бессмысленное значение настройки
  (ноль, отрицательное, строка) лимитом не становится — иначе опечатка
  администратора остановила бы логистику.

### 10.1. Администрирование справочников (задача 1.3.1)

Реализовано. Чтение (`GET`) открыто всем, у кого есть право на чтение заказов;
изменение — только администратору, а исполнители производства ещё и менеджеру
производства (строка «Исполнители производства» в матрице прав,
docs/02-domain-and-roles.md §4).

| Метод | Путь | Описание | Право |
|-------|------|----------|-------|
| POST | `/stores` | Создать магазин | `settings:manage` |
| PATCH | `/stores/:id` | Изменить магазин | `settings:manage` |
| POST | `/workshops` | Создать цех | `settings:manage` |
| PATCH | `/workshops/:id` | Изменить цех | `settings:manage` |
| POST | `/performers` | Создать исполнителя | `performer:manage` |
| PATCH | `/performers/:id` | Изменить исполнителя | `performer:manage` |
| POST | `/work-categories` | Создать категорию работ | `settings:manage` |
| PATCH | `/work-categories/:id` | Изменить категорию работ | `settings:manage` |
| POST | `/stone-types` | Создать тип камня | `settings:manage` |
| PATCH | `/stone-types/:id` | Изменить тип камня | `settings:manage` |

**Удаления нет ни у одного ресурса.** Справочники только отключаются
(`isActive: false`): на магазины, цеха и исполнителей ссылаются заказы, на
категории — позиции прейскуранта, на типы камней — строки камней в заказах
(`OrderStone.stoneTypeId`). Удаление разорвало бы историю расчётов. Отключённая
запись остаётся в справочнике и в уже созданных документах, но исчезает из
выбора при оформлении заказа.

Поля `code` у всех справочников уникальны. Формат: заглавные латинские буквы,
цифры и дефис (`^[A-Z0-9]+(?:-[A-Z0-9]+)*$`), от 2 до 20 символов. Конфликт
кода возвращает `409 CODE_TAKEN`.

Проверки, зависящие от состояния базы (возвращают `409`), — администратор
получает объяснение вместо ошибки внешнего ключа:

| Код | Когда |
|-----|-------|
| `STORE_CODE_IN_USE` | Меняют `code` магазина, у которого есть заказы: код входит в их номера (`MSK1-2609-000001`) |
| `LAST_ACTIVE_STORE` | Отключают последний активный магазин: приём заказов остановится |
| `STORE_HAS_ACTIVE_USERS` | Отключают магазин с активными сотрудниками |
| `WORKSHOP_HAS_ACTIVE_PERFORMERS` | Отключают цех с активными исполнителями |
| `WORKSHOP_HAS_OPEN_ORDERS` | Отключают цех с заказами вне `COMPLETED`/`REFUSED`/`CANCELLED` |
| `WORKSHOP_INACTIVE` | Заводят исполнителя в отключённый цех |
| `PERFORMER_HAS_OPEN_ASSIGNMENTS` | Отключают исполнителя с назначениями в статусе `ASSIGNED`/`IN_PROGRESS` |
| `CATEGORY_HAS_ACTIVE_ITEMS` | Отключают категорию с активными позициями прейскуранта |

Каждое изменение пишется в `AuditLog` (`action: CREATE`/`UPDATE`, `entity` —
имя модели Prisma) **в той же транзакции**, что и само изменение: иначе при
сбое в журнале осталась бы правка, которой нет в данных. У `CREATE` поле
`before` равно `null`; у `UPDATE` заполнены и `before`, и `after`, иначе по
журналу нельзя доказать, каким значение было до правки.

```json
      "note": "работаем в каникулы", "isHoliday": true, "redundant": false }
  ],
  "holidays": ["2027-01-01", "2027-01-02", "2027-01-03", "2027-01-04"]
}
```

`holidays` — праздники по ТК РФ ст. 112 (1–8 января, 23 февраля, 8 марта, 1 и
9 мая, 12 июня, 4 ноября), вычисленные кодом (`isStateHoliday`) и нерабочие даже
при отсутствии записи. Поле `isHoliday` у записи показывает то же самое для
конкретной даты, а `redundant` — что запись ничего не меняет (см. ниже).

**Почему это важно, а не деталь реализации.** Прежде календарь заполнялся строкой
на каждый день, среди которых праздники среди недели были помечены рабочими. Так
как запись из базы приоритетнее встроенного списка, срок «5 рабочих дней от
25 декабря» попадал на 1 января. Миграция `20260919000000` удалила эти строки, а
API теперь **отклоняет** попытку создать такую запись заново (`400
CALENDAR_REDUNDANT_DAY`): запись, совпадающая с правилом «праздник + день
недели», не несёт смысла, но маскирует праздник.

Порядок при определении рабочего дня — от сильного к слабому: **исключение из
базы → государственный праздник → день недели**. Поэтому администратор может
объявить рабочим даже праздник (магазин работает в каникулы) — и это не будет
перезаписано кодом.

| Код | Когда |
|-----|-------|
| `CALENDAR_REDUNDANT_DAY` | Запись ничего не меняет: день и без неё такой же (в том числе при изменении, которое превратило бы запись в такую) |
| `CALENDAR_DAY_EXISTS` | На дату уже есть запись календаря |
| `VALIDATION_ERROR` | Несуществующая дата (`2027-02-31`), период больше года, перевёрнутый период, «рабочий день 0 часов» или «выходной 8 часов» |

**`DELETE` здесь есть, и это осознанное исключение** из правила «не удалять,
только отключать» (задача 1.3.1). На строку календаря не ссылается ни одна
таблица — внешних ключей на `working_calendar` нет, — а «отключить дату» смысла
не имеет: каждая дата либо есть в календаре, либо нет. Снятие возвращает день к
обычному правилу и пишется в журнал (`action: DELETE`, `before` — прежнее
значение), поэтому действие обратимо.

Период обязателен и ограничен годом: календарь за 10 лет — это тысячи строк, и
запрос без периода превратил бы экран администратора в выгрузку всей таблицы.


### 9.1. Цена зависит от металла (ADR 0009)

Утверждённый прейскурант задаёт **две цены** на услугу — по золоту и по серебру.
Металл сданного изделия выбирает ставку.

Позиция в ответах `GET /price-lists/active`, `GET /price-list-items`,
`GET /price-lists/:id` содержит:

| Поле | Смысл |
|------|-------|
| `priceMinor` | цена по умолчанию (по золоту); для позиций без разбивки — единственная |
| `priceFrom` | цена указана как «от» (минимальная) — 5 позиций документа |
| `metalCostSeparate` | стоимость металла в цену не входит, считается отдельно — 3 позиции |
| `unit` | `шт` либо `грамм` (родирование, золочение — 3 позиции) |
| `rates[]` | `{ metal, priceMinor, isFrom }` — ставки по металлам (золото, серебро) |

`costMinor` (себестоимость) в ответ **не включён**: право чтения прейскуранта есть и у
приёмщика, и у кассира, которым маржинальность видеть не нужно.

`POST /orders` принимает `works[].itemIndex` (индекс изделия в `items`, по умолчанию 0) —
по металлу этого изделия подбирается ставка.

**Сервер проверяет присланную цену** и отвечает `409`:

```json
{
  "code": "PRICE_MISMATCH",
  "message": "Цена работы не совпадает с действующим прейскурантом. Обновите страницу и повторите приём.",
  "details": { "mismatches": [{ "code": "PRICE-1", "expectedMinor": 45000, "gotMinor": 90000 }] }
}
```

Нетиповые работы (`isCustom: true`) проверке не подлежат — их цену назначает сотрудник.
Металл распознаётся из свободного текста («Серебро 925», «Ag925»); если распознать не
удалось, применяется цена по умолчанию, и интерфейс обязан предупредить приёмщика.

### 10.3. Нормативы этапов (задача 1.3.4)

Нормативы задают срок, который система обещает клиенту, и по ним считается просрочка
исполнителей (ТЗ п. 2.7). Справочник версионируется: правка создаёт новую версию, прежняя
остаётся в истории — по ней объясняют сроки уже принятых заказов.

| Метод | Путь | Описание | Право |
|-------|------|----------|-------|
| GET | `/stage-norms` | Действующая версия с составом | `settings:manage` |
| GET | `/stage-norms/versions` | Все версии, новые сверху | `settings:manage` |
| POST | `/stage-norms/versions` | Создать версию и сразу применить | `settings:manage` |

**`PATCH` и `DELETE` отсутствуют намеренно.** Норматив не «правят»: изменение — это новая
версия, потому что прежняя должна остаться объяснением для уже принятых заказов. Удалить
отдельную строку тоже нельзя — набор версии самодостаточен, и «дырка» в нём означала бы
этап без срока.

**Активация одношаговая.** Создавать и применять норматив может только администратор, то
есть автор и утверждающий — одно лицо; разделение на «черновик → утверждение», как у
прейскуранта, ничего не защищало бы, но удвоило бы число состояний. Поля `approvedById` и
`approvedAt` заполняются при активации и фиксируют, кто ввёл версию в действие.

Если действующей версии нет, `GET /stage-norms` возвращает `null` (не `404`): это состояние
«нормативы не заданы», при котором сроки по этапам не рассчитываются. Молчаливая подстановка
значений по умолчанию скрыла бы его.

**Тело `POST /stage-norms/versions`:**

```json
{
  "changeReason": "Увеличили срок производства сложного ремонта до 20 дней",
  "effectiveFrom": "2026-10-01",
  "norms": [
    { "stage": "PRODUCTION", "workType": "COMPLEX", "value": 20, "unit": "WORKDAY",
      "escalateToRole": "PRODUCTION_MANAGER" }
  ]
}
```

| Поле | Обязательность | Значение |
|------|----------------|----------|
| `norms` | да | Полный набор версии, 1–64 записи |
| `norms[].stage` | да | Одно из `NORM_STAGE`: `APPROVAL`, `PREPAYMENT`, `QUEUE`, `LOGISTICS_OUT`, `PRODUCTION`, `LOGISTICS_IN`, `PICKUP`, `CLAIM` |
| `norms[].workType` | нет | `ANY` (по умолчанию), `SIMPLE`, `COMPLEX` |
| `norms[].value` | да | Целое 1–365 |
| `norms[].unit` | да | `WORKHOUR`, `WORKDAY`, `CALENDAR_DAY` |
| `norms[].escalateToRole` | нет | Роль для эскалации просрочки |
| `changeReason` | да | 5–500 символов: норматив меняет сроки всех новых заказов |
| `effectiveFrom` | нет | Дата начала действия, по умолчанию — сегодня |

Набор версии — ПОЛНЫЙ, а не отдельная правка: уникальность ключа `[version, stage, workType]`
не позволяет ответить «какая версия действует», собирая её из нескольких версий.

**Проверки, помимо схемы** (каждая защищает от конкретной ошибки):

| Код | Когда | Почему это важно |
|-----|-------|------------------|
| `VALIDATION_ERROR` | Неизвестный этап, дубль «этап + тип работ», пустой набор, значение вне 1–365, причина короче 5 символов | Дубль нарушил бы уникальный индекс и оставил бы неопределённым, какое значение применять |
| `VALIDATION_ERROR` | Для `PRODUCTION` задан только один из типов работ и нет общего | Для одной из сложностей срок не найдётся, и заказ останется без `dueAt` |

**Нераспознанная сложность.** `Order.complexity` по умолчанию `ANY`, и задать его пока
негде (калькуляция не реализована). Поэтому набор обязан содержать общий норматив
производства (`workType = ANY`) либо оба конкретных; общий делается консервативным — равным
сроку сложного ремонта.

**Этап, а не статус.** Норматив привязан к этапу; соответствие «статус → этап» задаёт
`stageForStatus()`. Расчёт, ищущий норматив по имени статуса, не нашёл бы ни одного — именно
это было дефектом 26 (docs/15-known-issues.md).

Все отчёты принимают `from`, `to`, `storeId[]`, `groupBy`, `limit` и возвращают готовые
агрегаты (без вычислений на клиенте).

### 12.1. Единый формат ответа (задачи 5.1–5.5)

Ответ одинаков для всех отчётов: `meta` (период, момент построения, признак кэша,
число строк), `columns` (ключ, заголовок, тип), `rows` и `totals`. Тип колонки
(`string`, `number`, `money`, `duration`, `percent`, `date`) говорит интерфейсу, как
показать значение: `62.4` — это часы, `0.87` — доля. Благодаря единому формату
интерфейс рендерит любой отчёт одной таблицей, а выгрузка в XLSX (задача 5.6)
делается универсально, без кода под каждый отчёт.

### 12.2. Область видимости и параметры

Область видимости накладывается **в сервисе**, а не в контроллере, и мимо неё не
пройти. Параметр `storeId[]` приходит из строки запроса, то есть от клиента, и
только **сужает** доступный набор, но не расширяет его: приёмщик одного магазина,
дописав в адрес чужой идентификатор, получит пустой отчёт, а не отчёт по сети.
Роль без магазинов не видит ничего.

Границы периода — **московские сутки** (`ГГГГ-ММ-ДД`): при разборе как UTC отчёт за
сентябрь захватил бы часть 31 августа, и числа не сошлись бы с отчётом за август.
Верхняя граница расширяется до конца суток, иначе из отчёта выпадал бы последний
день периода. Предел периода — 800 дней: годовой срез считается, а «с 2015 года» —
это выгрузка всей базы, замедляющая работу приёмщиков.

### 12.2.1. Права на отчёты (задача 5.6)

Права разделены: `report:operational` — сроки по этапам, загрузка производства,
просрочки; `report:revenue` — выручка и предоплаты; `report:export` — выгрузка
файлом. Маршрут `/reports/{name}` пускает по **любому** из прав на отчёты, а
право на конкретный отчёт проверяется внутри: иначе кассир, у которого есть
`report:revenue`, не смог бы открыть выручку — право есть, а доступа нет. Этот
дефект был найден при сверке матрицы прав с этой таблицей и исправлен.

Аудитор (`report:operational` + `report:revenue` без `report:export`) видит
отчёты на экране, но не может выгружать данные файлом.

### 12.3. Особенности отчётов

**Сроки по этапам** (`deadlines`). Источник — `OrderStatusHistory`. Переходы без
`durationMinutes` (первый переход, когда предыдущего статуса нет) в статистику не
попадают: иначе среднее занижалось бы нулями. «Доля в норме» считается только по
этапам, у которых норматив задан, — иначе показатель улучшался бы за счёт этапов
без норматива. Срок ровно по нормативу нарушением **не** считается.

**Загрузка производства** (`production-load`). Фактические часы берутся из
завершённых назначений (`finishedAt − startedAt`), а не от текущего момента: иначе
одно и то же задание показывало бы разную трудоёмкость при каждом запросе.
Исполнитель без назначений показывается нулями — он свободен, и именно ему можно
отдать работу из очереди.

**Выручка** (`revenue`). Выручка считается по **дате платежа** (`paidAt`), а не по
дате заказа: заказ, оформленный в августе и оплаченный в сентябре, — сентябрьская
выручка. Иначе отчёт не сойдётся с 1С, где доход признаётся по документу оплаты, и
расхождение будут искать в интеграции, а не в отчёте. Учитываются только
подтверждённые платежи (`PENDING` — намерение, `FAILED` — деньги, которых не
будет). Возвраты и сторно вычитаются из чистой выручки и показываются отдельно:
рост возвратов — самостоятельный сигнал, в свёрнутом виде не виден. Средний чек
делится на **число заказов**, а не платежей: заказ может быть оплачен предоплатой и
доплатой, и деление на платежи занизило бы чек вдвое. Неделя начинается с
понедельника.

**Предоплаты** (`prepayments`). Разрез — по магазину **внесения** (`Payment.storeId`),
а не по магазину заказа: клиент часто платит не там, где оформил заказ, и отчёт по
магазину заказа показал бы деньги не той точке, у которой они в кассе. «Зачтено» —
предоплаты по заказам, дошедшим до `COMPLETED`; «в работе» — остальные. Зависшими
считаются предоплаты, по которым работы **не начаты** (`productionStartedAt` пуст)
дольше 14 дней — потенциальная потеря клиента (docs/06 §5).

**Выгрузка** (`format=xlsx|csv`). Выгрузка строится из **того же результата
отчёта**, что показан на экране, — то есть из уже отфильтрованного по роли.
Отдельного запроса к базе у выгрузки нет, поэтому обойти область видимости через
`format=xlsx` нельзя. Требуется право `report:export`; без него — `403
FORBIDDEN_ROLE`. Деньги выгружаются в **рублях** (в базе копейки) и остаются
числами: строку Excel не просуммирует. Единица измерения дописана в заголовок
колонки, потому что сама ячейка — число без форматирования. CSV отдаётся с
разделителем `;`, переводами строк CRLF и маркером UTF-8: без них Excel в русской
локали покажет кириллицу нечитаемыми знаками, а файл попадёт в одну колонку.

**Просрочки** (`overdue`). «Просрочено сейчас» и «просрочено за период» — разные
числа, и оба нужны. Первое исключает терминальные статусы (выданный заказ — не
просрочка), второе их **не** исключает: заказ, выданный с опозданием, в текущем
состоянии не виден, но в оценке работы точки остаётся.

### Управление учётными записями: поведение

Реализовано в задаче 1.2.4 (модуль `apps/api/src/modules/users`).

* **Пароли не отдаются наружу никогда.** Поле `passwordHash` не выбирается из
  базы, поэтому утечь в ответ не может по построению; в журнал аудита пароль и
  его хеш также не попадают.
* **`mustChangePassword`.** При создании учётной записи и при сбросе пароля
  флаг выставляется в `true`. Он возвращается в `POST /auth/login` и
  `GET /auth/me`, а `POST /auth/change-password` его снимает. Пароль при
  создании задаёт администратор, поэтому система требует заменить его на
  известный только владельцу.
* **Смена прав завершает сессии.** Отключение учётной записи
  (`PATCH /users/:id` с `isActive: false`), снятие роли и сброс пароля отзывают
  все активные сессии пользователя: иначе отключённый сотрудник продолжал бы
  работать в уже открытой вкладке до истечения refresh-токена (30 дней).
* **Снятие последней роли запрещено** (код `LAST_ROLE`). Учётная запись без
  ролей не может войти в систему, поэтому её нужно именно отключить, а не
  оставить «рабочей» без ролей.
* **Администратор не блокирует сам себя:** отключение собственной учётной
  записи и снятие своей основной роли отклоняются.
* **Роль, ограниченная магазином, требует магазин.** Для `RECEIVER` и `CASHIER`
  поле `storeId` обязательно: без него область видимости не построить.
* **Чужая роль по прямому `id` — 404, не 403:** иначе по коду ответа можно было
  бы узнать о существовании роли у другой учётной записи.
* **Коды ошибок:** `EMAIL_TAKEN`, `ROLE_ALREADY_ASSIGNED`, `LAST_ROLE`,
  `NOT_FOUND`, `VALIDATION_ERROR`.

## 13.1 Эскалации (задача 2.8)

| Метод | Путь | Описание | Право |
|-------|------|----------|-------|
| GET | `/escalations/overdue` | Дашборд просроченных заказов | `report:operational` |
| POST | `/escalations/run` | Запустить прогон эскалаций вручную | `settings:manage` |
| POST | `/escalations/unclaimed/run` | Перевести просроченные выдачи в «невостребовано» | `settings:manage` |

Плановый прогон выполняет воркер раз в 15 минут; ручной запуск нужен, чтобы
проверить настройку нормативов, не ожидая расписания, и повторить прогон после
сбоя.

Ответ:

```json
{ "scanned": 12, "notified": 3, "escalated": 3, "withoutResponsible": 0 }
```

**Уровень повышается только при успешной рассылке.** Если ответственный не
найден или уведомление не создалось, `escalationLevel` не меняется: иначе заказ
считался бы оповещённым, хотя сообщения никто не получил, и следующий прогон уже
молчал бы — просрочка «сгорела» бы без единого уведомления.

**Повторная эскалация того же уровня не отправляется.** Воркер может быть
запущен дважды (перезапуск сервиса, два экземпляра приложения), а ежедневное
повторение одного и того же сообщения превращает ленту в шум.

**Адресат зависит от этапа:** на производстве — назначенный менеджер
(`productionManagerId`), на логистике — логисты, на приёме, согласовании и выдаче
— приёмщик, оформивший заказ (резерв — приёмщики магазина). Руководитель
получает **отдельное** уведомление по шаблону `ESCALATION_MANAGER`, а не то же
самое, что ответственный; в переменную `responsible` подставляется **имя
ответственного** (`productionManager.fullName`, при его отсутствии —
`createdBy.fullName`), а не номер заказа.

`POST` отвечает `200`, а не `201`: прогон ничего не создаёт как ресурс.

### 13.1.1 Дашборд просрочек (задача 2.9)

`GET /escalations/overdue` возвращает сводку и список:

```json
{
  "total": 12,
  "needsManager": 3,
  "totalAmountMinor": 1450000,
  "byStore": [{ "key": "...", "label": "Тверская", "count": 7, "totalAmountMinor": 900000 }],
  "byStage": [{ "key": "IN_PRODUCTION", "label": "Производство", "count": 5, "totalAmountMinor": 600000 }],
  "orders": [
    {
      "orderNo": "MSK1-2509-000001",
      "status": "IN_PRODUCTION",
      "overdueWorkingHours": 20.4,
      "needsManager": true,
      "storeName": "Тверская",
      "customerName": "Клиентов Иван Петрович",
      "totalAmountMinor": 100000
    }
  ]
}
```

**Просрочка считается по `dueAt`, а НЕ по факту отправки уведомления.** Дашборд
обязан показывать просрочку и тогда, когда уведомление не ушло: недоступная почта
не отменяет просроченный срок. Обратная зависимость скрыла бы ровно те заказы,
которые остались без оповещения.

**Набор заказов совпадает с набором воркера эскалаций.** Расхождение означало бы,
что дашборд показывает просрочку, о которой никого не оповестили.

**Список отсортирован по убыванию времени в пути-просрочки**, а разрезы — по
числу заказов: и то и другое существует, чтобы увидеть, за что взяться первым.
Просрочка выражается в **рабочих** часах: «просрочено на 11 календарных часов» с
пятницы — это 2 рабочих часа, и календарный счёт показал бы срок, которого не
было.

### 13.1.2 Невостребованные заказы (задача 2.10)

`POST /escalations/unclaimed/run` переводит заказы в `READY_FOR_PICKUP`, готовые
более 30 календарных дней назад (ТЗ п. 2.8), в статус `UNCLAIMED`. Плановый
прогон — раз в сутки в воркере.

Перевод идёт **через таблицу переходов** (переход 19), а не прямым
`UPDATE status`: переход несёт проверку порога `UNCLAIMED_THRESHOLD`, запись в
историю статусов и роль `SYSTEM`. Прямая запись обошла бы проверку, и заказ стал
бы «невостребованным» раньше срока из-за сбоя в данных.

Порог читается из настройки `orders.unclaimedAfterDays` (по умолчанию 30).
Значение ноль, отрицательное или не число заменяется значением по умолчанию: ноль
перевёл бы в «невостребовано» заказ, готовый час назад. Приёмщикам магазина
отправляется уведомление `ORDER_UNCLAIMED`; сбой уведомления не отменяет перевод —
статус уже изменён, и откатывать его из-за недоступной почты нельзя.

## 14. Уведомления

Состояние: **канал `IN_APP` реализован** (задача 2.6). Внешняя отправка
(`EMAIL`, `SMS`, `MESSENGER`) появится на этапе 5 (задачи 5.9–5.10); контракт —
`NotificationPort` (docs/05 §6.3). С задачей 5.9 доставка выполняется воркером
`notifications`: уведомление `IN_APP` считается доставленным в момент записи, письмо
уходит по SMTP. Каналы настраиваются окружением (`SMTP_HOST` и далее); без
`SMTP_HOST` приложение работает, а письма остаются в базе со статусом `FAILED` и
причиной «SMTP не настроен».

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/notifications` | Мои уведомления (`?unreadOnly=true`, `?limit=N`) |
| PATCH | `/notifications/:id/read` | Отметить прочитанным |
| POST | `/notifications/read-all` | Прочитать все |
| GET | `/notifications/unread-count` | Счётчик для колокольчика |

Отдельным правом маршруты не закрыты намеренно: уведомления адресованы лично
сотруднику, а не роли. Доступ ограничен владельцем записи — чужие уведомления не
видны и не читаются, и попытка вернёт `404`, а не `403`: `403` подтвердил бы
существование записи, а идентификаторы угадываемы.

**Уведомление сначала создаётся со статусом `PENDING`, и только потом
отправляется.** Запись в базе — это и есть очередь отправки: при недоступности
провайдера сообщение не теряется, а остаётся с текстом ошибки и числом попыток
(`FAILED`, `attempts`), и его можно повторить.

**Текст берётся из `NotificationTemplate`; отсутствие шаблона не отменяет
операцию.** Партия обязана отправиться даже тогда, когда текст уведомления ещё не
заполнен, — иначе незаполненный справочник блокировал бы перевозку изделий
клиентов. Плейсхолдер без значения заменяется пустой строкой, а не остаётся как
`{{batchNo}}`.

Приёмка партии создаёт уведомление `BATCH_RECEIVED` её отправителю. Оно создаётся
**после** транзакции: держать блокировки на строках заказов, пока отвечает
почтовый сервер, — верный способ получить таймаут, а при откате транзакции
уведомление о несостоявшейся перевозке уже не отозвать. Сбой уведомления не
отменяет приёмку: изделия физически у получателя.
