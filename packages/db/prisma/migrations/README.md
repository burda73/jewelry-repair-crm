# Миграции базы данных

Схема — `prisma/schema.prisma`. Стратегия описана в `docs/03-data-model.md` §5.

> **ВАЖНО: база данных внешняя.** PostgreSQL — **существующий сервер предприятия**,
> общий с 1С и другими системами (ответ A1, ADR `docs/adr/0008-external-postgresql.md`).
> Отсюда два правила:
>
> 1. **Шаги, требующие прав суперпользователя, выполняет администратор БД** — установка
>    расширений, `REVOKE` на журнал аудита, ограничения `CHECK`. Наша роль `repair_app`
>    их выполнить не может. Требования и список согласований — `infra/db/README.md`.
> 2. **Миграции идут на общем сервере**, поэтому их время согласуется с окнами
>    обслуживания 1С и не совпадает с пиковой нагрузкой.
>
> Перед первым деплоем проверьте готовность БД: `./infra/db/preflight.sh`

## Основные команды

```bash
npm run db:migrate    # создать и применить миграцию (dev)
npm run db:deploy     # применить миграции (staging/prod, без создания новых)
npm run db:reset      # сбросить БД и залить seed (ТОЛЬКО локально!)
npm run db:studio     # Prisma Studio
```

> `db:reset` и `db:seed` **нельзя запускать против продовой базы** — они удаляют данные.
> Убедитесь, что `DATABASE_URL` указывает на локальную БД.

## Ручные шаги после первой миграции

Prisma не умеет выражать часть конструкций PostgreSQL напрямую. Их нужно добавить
в миграцию вручную — **иначе часть гарантий целостности не работает**.
Шаги 1, 4 и 6 выполняет **администратор БД** (нужен суперпользователь).

### 1. Расширения (выполняет администратор БД)

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- нечёткий поиск по ФИО и телефону
CREATE EXTENSION IF NOT EXISTS btree_gin; -- составные GIN-индексы
```

### 2. Уникальность общего рабочего календаря

`WorkingCalendar.storeId = null` означает общий календарь сети. Составной unique
`(storeId, date)` **не защищает** такие записи от дублей: в PostgreSQL значения `NULL`
в unique-ограничении считаются различными. Нужен частичный индекс:

```sql
CREATE UNIQUE INDEX working_calendar_global_date_uq
  ON working_calendar (date)
  WHERE store_id IS NULL;
```

Без него повторный запуск seed или параллельные запросы создадут дубликаты дней,
и расчёт рабочих дней начнёт давать неверный результат.

### 2.1. Нормативы этапов: `workType` НЕ nullable

Та же ловушка PostgreSQL, что и выше, но **устранена в схеме**: в `StageNorm`
поле `workType` объявлено как `String @default("ANY")`, а не `String?`.

Причина: при `workType = null` составной unique `(version, stage, workType)` **не работал бы** —
для одного этапа можно было бы создать неограниченное число нормативов с `workType = null`.
Повторный запуск seed добавлял бы новые строки, а `loadStageNorm` выбирал бы произвольную
из них — расчёт `dueAt` стал бы недетерминированным.

Значение `ANY` означает «норматив для этапа в целом». При выборе норматива конкретный тип
работ (`SIMPLE`/`COMPLEX`) приоритетнее общего (`ANY`), см.
`OrderWorkflowService.loadStageNorm`.

**Если база уже создана со старой схемой** (`workType` nullable), перед деплоем:

```sql
UPDATE stage_norm SET work_type = 'ANY' WHERE work_type IS NULL;
ALTER TABLE stage_norm ALTER COLUMN work_type SET NOT NULL;
ALTER TABLE stage_norm ALTER COLUMN work_type SET DEFAULT 'ANY';
```

### 3. Индексы нечёткого поиска

```sql
CREATE INDEX customer_fullname_trgm_idx
  ON customer USING gin (full_name gin_trgm_ops);

CREATE INDEX customer_phone_trgm_idx
  ON customer USING gin (phone_normalized gin_trgm_ops);
```

Обслуживают поиск по ФИО с опечатками и по частичному номеру телефона (ТЗ п. 2.1).

### 4. Аудит — только добавление (ТЗ п. 4) — выполняет администратор БД

Приложению запрещено изменять и удалять записи журнала. Выполняется от имени
суперпользователя, один раз. **Имя роли подставьте своё** — в примерах используется
`repair_app` (см. `infra/db/README.md` §1.2):

```sql
-- Роль приложения не должна иметь прав на изменение журнала
REVOKE UPDATE, DELETE, TRUNCATE ON audit_log FROM repair_app;
GRANT SELECT, INSERT ON audit_log TO repair_app;
```

Проверяется тестом: попытка `UPDATE audit_log` должна завершиться ошибкой прав.

### 5. Партиционирование журнала (при росте)

Когда `audit_log` превысит ~50 млн строк, таблицу переводят на помесячные партиции.
Выполняется отдельной миграцией в окно обслуживания; до этого момента — обычная таблица
с индексами по `created_at`.

### 6. Проверки целостности данных (выполняет администратор БД)

```sql
-- Сумма заказа не может быть отрицательной
ALTER TABLE "order" ADD CONSTRAINT order_total_non_negative
  CHECK (total_amount_minor >= 0 AND paid_amount_minor >= 0);

-- Скидка не может превышать сумму работ и камней
ALTER TABLE "order" ADD CONSTRAINT order_discount_sane
  CHECK (discount_minor <= works_total_minor + stones_total_minor);

-- Количество в строке калькуляции положительное
ALTER TABLE order_work ADD CONSTRAINT order_work_quantity_positive
  CHECK (quantity > 0);

-- Сумма платежа строго положительная
ALTER TABLE payment ADD CONSTRAINT payment_amount_positive
  CHECK (amount_minor > 0);
```

Эти ограничения — вторая линия защиты после валидации в приложении. Они ловят ошибки
в коде, который обходит доменные сервисы.

## Правила изменения схемы

1. **Только обратно совместимые изменения**, в три шага:
   `add column (nullable)` → backfill → переключить код → `drop`.
   Иначе rolling update сломается на старой версии API.
2. **Тяжёлые операции — отдельно.** `CREATE INDEX CONCURRENTLY` не выполняется внутри
   транзакции, поэтому идёт отдельной миграцией и отдельным запуском.
3. **Никаких down-миграций.** Откат — новой миграцией, исправляющей проблему.
4. **Проверка на копии продовых данных** до применения (job `migrations` в CI).
5. **Никогда не редактировать применённую миграцию** — Prisma зафиксирует расхождение
   контрольной суммы и `migrate deploy` упадёт на всех средах.

## Восстановление после неудачной миграции

**Действует иначе, чем при своей БД:** дампа у нас нет — копии делает администратор БД.
Поэтому порядок начинается с обращения к нему.

```bash
# 1. Остановить API и воркер (чтобы не писали в БД)

# 2. Запросить у администратора БД восстановление из копии на момент до миграции.
#    Если настроен PITR — на конкретную метку времени (RPO ≤ 5 минут).
#    Команды восстановления выполняет администратор, у нас нет на это прав.

# 3. Пометить миграцию как откаченную (это уже наша операция)
npx prisma migrate resolve --rolled-back <migration_name>

# 4. Исправить миграцию и применить заново
```

> **Почему нельзя восстановить самим:** `pg_restore` в рабочую базу требует прав и
> заблокирует её для других систем, а база **общая**. Кроме того, наш дамп может быть
> старее, чем данные 1С, — восстановление затронет чужие данные.

**Профилактика вместо восстановления:** миграции проверяются на **отдельной staging-БД**
до применения на проде (задача 0.5, п. 4 ниже). Это основной способ не доводить до отката.

Регламент восстановления, целевые RTO/RPO и распределение ответственности:
`docs/10-nfr-security.md` §5 и `infra/db/README.md` §5.
