# Требования к внешнему PostgreSQL 16

В инфраструктуре предприятия **уже есть настроенный PostgreSQL 16** (ответ A1), поэтому
проект его **не устанавливает** и не поднимает в Docker. Этот документ описывает, что нужно
подготовить на стороне БД и какие проверки выполнить до развёртывания.

> Кратко: создать БД и роль, установить два расширения, применить ограничения целостности.
> Всё остальное (миграции, индексы) делает Prisma.

---

## 1. Что создаёт администратор БД

### 1.1. База данных

```sql
-- Кодировка и локаль: ru_RU.UTF-8 нужна для корректной сортировки ФИО.
CREATE DATABASE repair
  WITH ENCODING = 'UTF8'
       LC_COLLATE = 'ru_RU.UTF-8'
       LC_CTYPE  = 'ru_RU.UTF-8'
       TEMPLATE  = template0;
```

> **Почему `template0` и локаль обязательны:** сортировка по ФИО в отчётах и поиске
> зависит от локали. Если создать БД с `C`-локалью, русские фамилии будут сортироваться
> неверно (`Ё` в конец, `Я` перед `А`). Исправить это после создания БД нельзя — только
> пересозданием, а значит потерей данных.

### 1.2. Отдельная роль приложения

Приложение **не должно работать под суперпользователем** и не должно иметь прав
на чужие базы.

```sql
CREATE ROLE repair_app WITH
  LOGIN
  PASSWORD '<надёжный пароль>'      -- сгенерировать: openssl rand -base64 24
  NOSUPERUSER
  NOCREATEDB
  NOCREATEROLE
  NOINHERIT
  CONNECTION LIMIT 40;              -- защита от исчерпания max_connections сервера

GRANT CONNECT ON DATABASE repair TO repair_app;
GRANT USAGE  ON SCHEMA public TO repair_app;

-- Права на таблицы: Prisma создаёт их при миграции, но роль должна уметь
-- создавать объекты в своей схеме.
GRANT CREATE ON SCHEMA public TO repair_app;
```

### 1.3. Расширения

Установка расширений требует суперпользователя, поэтому выполняется администратором
**один раз до первой миграции**.

```sql
\c repair

CREATE EXTENSION IF NOT EXISTS pg_trgm;    -- нечёткий поиск по ФИО (ТЗ п. 2.1)
CREATE EXTENSION IF NOT EXISTS btree_gin;  -- составные GIN-индексы
```

Проверка:

```sql
SELECT extname FROM pg_extension WHERE extname IN ('pg_trgm', 'btree_gin');
-- Ожидается две строки.
```

Если `pg_trgm` недоступен, проверьте наличие пакета:

```bash
# Debian/Ubuntu
apt list --installed | grep postgresql-contrib
# Установка (на сервере БД, требует прав root)
apt install postgresql-contrib-16
```

### 1.4. `max_connections` — важная проверка

Наш PostgreSQL **общий**: с ним работают и другие системы, включая 1С. Если наше
приложение займёт все соединения, **встанут чужие системы**. Поэтому:

```sql
SHOW max_connections;         -- типовое значение 100
SHOW superuser_reserved_connections;  -- обычно 3 (зарезервировано)
```

Бюджет соединений для проекта:

| Компонент | Процессов | Пул на процесс | Итого |
|-----------|-----------|----------------|-------|
| API (2 реплики) | 2 | `DATABASE_POOL_SIZE` (10) | 20 |
| Воркер | 1 | `DATABASE_POOL_SIZE` (10) | 10 |
| Миграции (кратковременно) | 1 | 1 | 1 |
| **Итого** | | | **≤ 31** |

При `max_connections = 100` это оставляет больше половины соединений другим системам.
Значение задаётся переменной `DATABASE_POOL_SIZE` (см. §2) и ролью `CONNECTION LIMIT`.

### 1.5. Ограничения целостности данных

Добавляются **после первой миграции** Prisma (таблицы должны существовать):
`packages/db/prisma/migrations/README.md` §6. Там же — запрет изменения журнала аудита
(`REVOKE UPDATE, DELETE` на `audit_log`), который тоже требует прав суперпользователя.

## 2. Переменные окружения

```bash
# Внешний PostgreSQL предприятия (ответ A1). Не localhost!
DATABASE_URL="postgresql://repair_app:<пароль>@pg-server.remixgold.ru:5432/repair?schema=public&sslmode=prefer"

# Необязательно: реплика для отчётных запросов.
DATABASE_REPLICA_URL=""

# Пул соединений на процесс. См. расчёт в §1.4.
DATABASE_POOL_SIZE=10
```

Параметр `sslmode`:

| Значение | Когда применять |
|----------|-----------------|
| `disable` | Только если БД в изолированном сегменте, трафик не покидает хост |
| `prefer` | **По умолчанию.** Шифрует, если сервер поддерживает; иначе продолжает без TLS |
| `require` | Если сервер БД настроен на TLS — рекомендуется для трафика между хостами |

**Ограничение пула применяется автоматически.** `packages/db/src/index.ts` добавляет
`connection_limit` к строке подключения, поэтому пул нельзя забыть настроить.
Если в `DATABASE_URL` уже есть `connection_limit`, явное значение сохраняется.

## 3. Сетевое взаимодействие

Приложение в LXC обращается к БД по сети предприятия. Нужно убедиться, что:

1. **DNS-имя или IP сервера БД** доступны из контейнера.
2. **`pg_hba.conf`** на сервере БД разрешает подключение с адреса LXC:
   ```
   # Тип  База    Пользователь  Адрес              Метод
   host  repair  repair_app    192.168.1.50/32    scram-sha-256
   ```
3. **`listen_addresses`** в `postgresql.conf` включает нужный интерфейс
   (обычно `'*'` или `'localhost,192.168.1.x'`).
4. **Межсетевой экран** (uncomplicated firewall, фильтры Proxmox) пропускает 5432
   между LXC и сервером БД.

> `scram-sha-256` — обязательный метод аутентификации. `md5` и `trust` не использовать.

## 4. Проверка готовности до развёртывания

Запустите скрипт — он выполнит все проверки и вернёт понятный отчёт:

```bash
./infra/db/preflight.sh
```

Скрипт проверяет: доступность сервера, версию PostgreSQL, права роли, наличие расширений,
бюджет соединений, возможность выполнить DDL (нужно Prisma для миграций), состояние часов.

### Ручная проверка

```bash
# 1. Подключение и версия
psql "$DATABASE_URL" -c "SELECT version();"
# Ожидается PostgreSQL 16.x

# 2. Права на создание объектов (нужно Prisma)
psql "$DATABASE_URL" -c "CREATE TABLE __prisma_probe(id int); DROP TABLE __prisma_probe;"

# 3. Расширения
psql "$DATABASE_URL" -c "SELECT extname FROM pg_extension WHERE extname IN ('pg_trgm','btree_gin');"

# 4. Бюджет соединений
psql "$DATABASE_URL" -c "SELECT current_setting('max_connections') AS max_conn;"
```

## 5. Резервное копирование — зона ответственности администратора БД

**Статус: система резервного копирования УЖЕ ОРГАНИЗОВАНА И НАСТРОЕНА** на отдельном
сервере PostgreSQL (ответ заказчика). Это изменение относительно первоначального плана:
раньше PostgreSQL был нашим контейнером, и бэкапы делал наш скрипт
(`infra/backup/backup.sh`). Теперь БД **вне нашего контура**:

| Аспект | Ответственность |
|--------|-----------------|
| Резервное копирование БД | **Администратор БД** — уже настроено |
| PITR (архивация WAL) | **Администратор БД** |
| Хранение и ротация копий | **Администратор БД** |
| Проверка восстановления | Администратор БД, по регламенту |
| Резервное копирование файлов (S3/MinIO) | **Наш проект** (`infra/backup/`) |

### 5.1. Что нужно подтвердить (а не настроить)

Создавать и настраивать ничего не требуется — нужно лишь **получить параметры**
существующего регламента и сверить их с требованиями проекта. Вопросы адресные:

| # | Что спросить | Зачем |
|---|--------------|-------|
| 1 | **Делается ли непрерывная архивация WAL (PITR)?** Или только периодические дампы? | Требуется RPO ≤ 5 мин (`docs/10-nfr-security.md` §2). Периодические дампы дают RPO = интервал между ними |
| 2 | Если дампы — **какова периодичность**? | Позволяет зафиксировать **фактический** RPO честно, а не декларативный |
| 3 | **Срок хранения** копий | Нужно ≥ 90 дней (правило 3-2-1) |
| 4 | **Проводилась ли проверка восстановления** из этих копий? Когда? | Настроенный бэкап и **проверенный** бэкап — разные вещи. Скрипт для проверки — `infra/backup/restore-drill.sh` |
| 5 | Есть ли **копия вне сервера** (второй носитель)? | Правило 3-2-1: три копии, два носителя, одна вне сервера |
| 6 | Есть ли **отдельная БД для staging** и можно ли восстановить в неё копию? | Нужна для приёмки и проверки миграций без риска для прода |
| 7 | **Уведомление перед миграциями.** Есть ли автоматические операции обслуживания (vacuum full, переиндексация), которые стоит разнести по времени? | Наши миграции меняют схему |

> **Пункт 4 — самый важный и самый недооценённый.** Копии, которые создаются, но из которых
> никогда не восстанавливали, не дают гарантии восстановления: о непригодности копий
> становится известно в момент аварии — то есть тогда, когда исправить уже нельзя
> (не тот формат, потерян пароль шифрования, копия на том же диске, что и данные).
> Поэтому учебное восстановление **до пилота**, а не после, — остаётся обязательным,
> даже при полностью настроенной системе копирования.

### 5.2. Если по пункту 1 ответ «только дампы»

Это не блокирует проект, но тогда:

1. **Фактический RPO фиксируется письменно** (например, 24 часа) — и заказчик осознанно
   принимает риск потери данных за этот интервал. Для системы ремонта потеря суточного
   объёма заказов и платежей означает ручное восстановление из бумажных квитанций.
2. Требование ТЗ «RPO ≤ 5 минут» в матрице требований помечается как **принятое
   отклонение** (`docs/12-requirements-traceability.md`), а не как выполненное.
3. Либо согласуется включение PITR — тогда параметр достигается.

### 5.3. Что остаётся за нашим проектом

`infra/backup/backup.sh` отвечает **только за файлы** MinIO (фото изделий, записи
звонков, PDF) и конфигурацию. Дамп базы из него исключён: он дублировал бы работу
администратора и мог бы выполняться с недостаточными правами.

**Разделение важно понимать правильно:** база и файлы — **разные** объекты с разными
регламентами. Настроенное копирование БД **не покрывает** фотографии изделий, записи
разговоров и PDF-документы. Они лежат в S3/MinIO, и их копирование — наша задача.

## 6. Обслуживание и согласования

| Операция | Кто выполняет | Когда |
|----------|---------------|-------|
| `CREATE DATABASE`, расширения | Администратор БД | Один раз при внедрении |
| Ограничения `CHECK`, `REVOKE audit_log` | Администратор БД | После первой миграции |
| Миграции схемы (`prisma migrate deploy`) | **Мы**, роль `repair_app` | При каждом деплое |
| `VACUUM`, `ANALYZE`, переиндексация | Администратор БД | По регламенту предприятия |
| Обновление версии PostgreSQL | Администратор БД | По регламенту предприятия |
| Резервное копирование и PITR | Администратор БД | **Уже настроено и работает** |

**Требование к окружению для миграций:** наша роль должна иметь право `CREATE` в схеме
`public` (см. §1.2). Без этого `prisma migrate deploy` упадёт с ошибкой прав.

**Отдельно: staging-база.** Для приёмки и проверки миграций нужна **отдельная база**,
чтобы тесты не затрагивали рабочую. Если её нет — обсудить на этапе 0. Удобный вариант:
разворачивать её из существующей копии, что дополнительно проверяет пригодность бэкапа.

## 7. Чего делать нельзя

| Нельзя | Почему |
|--------|--------|
| Работать под `postgres` или другим суперпользователем | Ошибка приложения сможет разрушить чужие базы (система общая!) |
| Ставить `max_connections` слишком большим для нашего пула | Займём соединения — встанут 1С и другие системы |
| Использовать `md5` или `trust` в `pg_hba.conf` | Пароли и доступ передаются небезопасно |
| Менять `shared_buffers`, `work_mem` «под нас» | Сервер общий: настройки влияют на все системы. При нехватке — согласовать с администратором |
| Создавать БД с локалью `C` | Русские ФИО будут сортироваться неверно, исправить без пересоздания нельзя |
| Делать миграции во время окна обслуживания 1С | Нагрузка на общий сервер; согласовывать время |
| Обновлять PostgreSQL силами проекта | Ответственность администратора БД |
