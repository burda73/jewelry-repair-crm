### Повторное развёртывание

Обновление кода на сервере выполняет `scripts/deploy.sh`. Он не просто копирует
файлы, а выполняет шаги в порядке, который ломается при ручном повторении:

```bash
./scripts/deploy.sh                 # обычное обновление
SERVER=root@10.0.0.5 ./scripts/deploy.sh
./scripts/deploy.sh --skip-sync     # только пересборка и перезапуск
```

Скрипт: передаёт код с нужными исключениями → выставляет владельца `repair` →
выполняет `npm ci` и **проверяет, что Prisma Client действительно сгенерирован**
(заглушка ~4 КБ вместо ~3,5 МБ означает, что postinstall не сработал) → собирает
shared, API и веб → **копирует `.next/static` и `public` в standalone-сборку** →
перезапускает сервисы → проверяет, что API отвечает, страница отдаётся и её чанк
статики доступен.

Последняя проверка — не формальность: оба дефекта §5.7–5.8 давали серверу
«зелёный» статус при нерабочем интерфейсе. Без проверки чанка пустая страница
проходит незамеченной.

### 3.1. Работа через HTTPS (`https://repair.remixgold.ru/`)

Развёртывание проверено по домену заказчика, а не только по внутреннему адресу.

| Проверка | Результат |
|----------|-----------|
| DNS | `repair.remixgold.ru` → `192.168.2.201` |
| Сертификат | Let's Encrypt, `CN=*.remixgold.ru`, действует до 02.12.2026 |
| Перенаправление HTTP → HTTPS | 301 |
| `GET /login` | 200 |
| Cookie сессии | `HttpOnly; Secure; SameSite=Lax` — флаг `Secure` работает только по HTTPS |
| `X-Frame-Options` | `SAMEORIGIN` (от прокси), `DENY` (от API) |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `no-referrer` |
| Swagger | 404 (`/api/docs`, `/api/v1/docs`, `/docs`) |
| Внутренние IP в HTML | не найдены |
| Кэш приватных страниц | HTML байт-в-байт одинаков для анонима, `receiver1` и `admin` — утечки нет |
| **Сквозной сценарий** | вход → дашборд → список заказов → карточка → перевод статуса → глобальный поиск |
| **Мастер создания заказа** | 5 шагов, поиск клиента, прейскурант (25 позиций), расчёт суммы |
| **Платежи** | приём, идемпотентность, переплата 409, сторно с причиной, повторное сторно 409 |
| Ошибки в консоли браузера | отсутствуют на всех шагах |

**Проверка денежного пути на боевом сервере** (заказ создан и удалён в ходе проверки):
без `Idempotency-Key` → `400 IDEMPOTENCY_KEY_REQUIRED`; платёж → `201`;
повтор с тем же ключом → тот же платёж, `paidAmountMinor` не удвоился;
переплата → `409 OVERPAYMENT`; сторно без причины → `400 VALIDATION_ERROR`;
сторно → `200`, `paidAmountMinor` пересчитан в 0; повторное сторно → `409 ALREADY_REVERSED`.

**Дефект, выявленный на этом шаге: HSTS не отдаётся на HTML-страницах.**
Заголовок `Strict-Transport-Security` присутствует в ответах API (его ставит helmet),
но `GET /login` и `GET /dashboard` приходят без него — эти ответы формирует
Next.js, а не API, и helmet их не покрывает. Компенсирующая мера уже действует:
HTTP-запросы перенаправляются на HTTPS (301), поэтому перехватить первый запрос
возможности нет. Но без HSTS браузер не запоминает требование HTTPS, и защита
держится только на этом перенаправлении. Закрывается одной строкой в
nginx-proxy (`add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`)
— см. §7.

**Ловушка при проверке платежей вручную:** `Idempotency-Key` обязателен, а
приёмщик (`receiver1`) не имеет права `PAYMENT_CREATE` — попытка принять платёж
от его имени возвращает `403 FORBIDDEN_ROLE`, и это не дефект, а разделение
ответственности за наличные. Проверять денежный путь нужно от `cashier@`.

## 5. Дефекты, найденные при развёртывании

Все проявились **только при развёртывании с нуля** — ни тесты, ни проверка типов

### 5.1. Линт не работал вообще

`eslint.config.mjs` импортирует пакет `typescript-eslint`, но в `package.json`
были объявлены только `@typescript-eslint/eslint-plugin` и `@typescript-eslint/parser`.
`npm run lint` падал с `ERR_MODULE_NOT_FOUND`.

**Исправлено:** пакет `typescript-eslint` добавлен в `devDependencies`.
После исправления линт заработал и сразу выявил 16 ошибок и 73 предупреждения —
см. §6.

### 5.2. Сборка shared не выполнялась из-за устаревшего `tsconfig.tsbuildinfo`

`tsc -b` считает сборку актуальной по файлу `*.tsbuildinfo`. При передаче кода
через `rsync` с исключением `dist/` этот файл переносился, а результат сборки — нет.
`tsc -b` сообщал «успех», не создавая `packages/shared/dist`, и сборка API падала с
6 ошибками `TS7006` (типы из `@app/shared` не находились).

**Исправлено** удалением `tsconfig.tsbuildinfo` и пересборкой.

**Урок для развёртывания:** передавать код нужно **либо** через `git clone`
(`.gitignore` исключает `*.tsbuildinfo` автоматически), **либо** удалять артефакты
сборки перед сборкой. Правильный набор исключений `rsync`:

```
--exclude node_modules --exclude .next --exclude dist
--exclude '*.tsbuildinfo' --exclude .env
```

### 5.3. Владелец файлов не совпадал с пользователем сервиса

`rsync -a` сохранил владельцев с рабочей машины (UID 501). На сервере такого
пользователя нет, файлы оказались недоступны для чтения пользователю `repair`.
API падал с `Cannot find module '@app/shared'` — при том что от `root` тот же
`require` работал.

**Исправлено:** `chown -R repair:repair /opt/repair/app`.

**Урок:** после передачи кода всегда выставлять владельца. Либо использовать
`rsync --no-owner --no-group --chmod=Du=rwx,Dgo=rx,Fu=rw,Fgo=r`.

### 5.4. `PORT` в общем `.env` конфликтовал с портом веб-сервиса

В `.env` был `PORT=4000`. В systemd `EnvironmentFile` **переопределяет**
`Environment=`, поэтому веб-сервис тоже пытался занять 4000 и падал с
`EADDRINUSE`.

**Исправлено:** `PORT` удалён из `.env`; порт задаётся юнитом каждого сервиса —
единственное место правды.

### 5.6. Дефект JWT: вход работал, сессия не сохранялась
Описан подробно в `docs/15-known-issues.md`. Кратко: `JwtModule.register({ secret:
process.env.JWT_ACCESS_SECRET })` вычислялся до загрузки `.env`, поэтому подпись
токена работала (секрет передавался явно), а проверка — нет (`undefined`).
Пользователь видел «Сессия истекла» сразу после успешного входа.

**Исправлено** переходом на `JwtModule.registerAsync()` с `ConfigService`.

**Проверено на сервере:** запрос после входа возвращает список заказов.

### 5.7. Prisma Client не генерировался после `npm ci` (сборка API падала)

Первая сборка после обновления кода упала с 10 ошибками вида
`Namespace 'Prisma' has no exported member 'OrderWhereInput'`,
`Module '@prisma/client' has no exported member 'StageNorm'`,
`Property 'validator' does not exist on type 'typeof Prisma'`.

**Причина:** `npm ci` удаляет `node_modules/.prisma/client` вместе с остальным
деревом, а в проекте **не было шага `postinstall`**, который бы его
восстанавливал. Prisma подставляла заглушку `index.d.ts` размером 3 КБ вместо
сгенерированного типизированного клиента. Сборка падала, потому что все типы
моделей живут именно там.

**Исправлено:**
`npx prisma generate --schema packages/db/prisma/schema.prisma`.

**Урок:** `prisma generate` — часть сборки, а не разовая настройка. После любого
`npm ci`/`npm install` его нужно выполнять до `tsc`. Надёжное решение —
добавить `postinstall` в `packages/db/package.json`.

### 5.8. Standalone-сборка Next.js не отдавала статику (страницы были пустыми)

После развёртывания интерфейса страницы отвечали `200`, но в браузере
**оставался только спиннер**: все запросы к `/_next/static/chunks/*.js`
возвращали `404`. Форма входа не отрисовывалась.

**Причина:** веб-сервис запускается из standalone-сборки
(`.next/standalone/apps/web/server.js`), но `output: 'standalone'` **не копирует**
в неё каталоги `.next/static` и `public` — Next.js намеренно перекладывает это
на сборщик образа. В нашем развёртывании без Docker копировать было некому.

HTML содержал ссылки на чанки, которых рядом не было. Отсюда «пустая» страница:
разметка приходила, но гидратация не запускалась.

**Исправлено** копированием статики в standalone-каталог:

```bash
cd /opt/repair/app/apps/web
mkdir -p .next/standalone/apps/web/.next
cp -r .next/static .next/standalone/apps/web/.next/static
cp -r public .next/standalone/apps/web/public
chown -R repair:repair .next/standalone
systemctl restart repair-web
```

**Проверено:** `/_next/static/chunks/webpack-*.js` → `200`; в браузере форма
входа отрисована, кнопка «Войти» высотой 44 px, шрифт Inter — то есть CSS
применился.

**Урок:** при развёртывании без Docker копирование статики — **обязательный**
шаг. Без него ошибка выглядит как «интерфейс не работает», хотя сервер и API
исправны.

## 7. Что осталось настроить (не блокирует работу)

1. **Домен и TLS — выполнено.** `https://repair.remixgold.ru/` настроен в
   nginx-proxy заказчика: HTTP → HTTPS 301, сертификат Let's Encrypt
   `*.remixgold.ru` (до 02.12.2026). API проксируется через тот же домен
   (`/api/v1`), отдельный маршрут для порта 4000 не нужен. Проверено — см. §3.1.
2. **Cookie `Secure` — работает.** По HTTPS браузер сохраняет сессию, вход
   проходит. Прежняя оговорка («полноценная работа возможна только по HTTPS»)
   снята: HTTPS настроен.
3. **HSTS на HTML-страницах.** `Strict-Transport-Security` отдаётся API (helmet),
   но **не** отдаётся страницами Next.js (`/login`, `/dashboard`) — их формирует
   не API, и helmet их не покрывает. Сейчас защита держится на перенаправлении
   HTTP → HTTPS (301), но браузер не запоминает требование HTTPS. Добавить в
   nginx-proxy для домена:
   `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`
4. **Сменить пароль БД.** Пароль передавался в переписке. Сменить и обновить
   `DATABASE_URL` в `/opt/repair/app/.env`, затем `systemctl restart repair-api`.
5. **Демо-данные.** Загружены для проверки (9 учётных записей с паролем
   `DemoPassword123`). Перед эксплуатацией удалить или сменить пароли.
6. **Бэкап конфигурации.** Сохранить `/etc/systemd/system/repair-*.service` и
   `.env` (секреты) в защищённое хранилище.
