# Маршрутизация через внешний nginx-proxy заказчика

По ответу A1 в инфраструктуре **уже есть отдельный nginx-proxy**, который выдаёт
сертификаты Let's Encrypt и маршрутизирует трафик между сервисами. Поэтому наш проект
**не содержит собственного прокси** и не терминирует TLS: он лишь публикует порты,
на которые прокси заказчика отправляет запросы.

Преимущество такой схемы: сертификаты, HSTS и общесетевые правила безопасности
настраиваются **в одном месте** администратором, а не дублируются в каждом сервисе.

---

## 1. Что публикует проект

`infra/docker/docker-compose.prod.yml` открывает два порта:

| Сервис | Порт по умолчанию | Назначение | Переменная |
|--------|-------------------|------------|------------|
| `web` | `3000` | Веб-интерфейс (Next.js, PWA) | `WEB_PORT` |
| `api` | `4000` | REST API (`/api/v1`), health-проверки | `API_PORT` |

PostgreSQL в проекте **вообще не запускается** — используется существующий сервер
предприятия (`infra/db/README.md`). Redis и MinIO портов наружу **не публикуют** — они
доступны только внутри docker-сети `repair-crm`.

> Настройка выполняется **через UI прокси** (ответ A1) — правка файлов на диске не нужна.
> Пошаговая инструкция с полями UI: `docs/14-deployment.md` §8. Файл
> `repair_proxy_params` в этом каталоге нужен только для варианта с правкой конфигурации
> вручную или как справка по требуемым заголовкам.

## 2. Два варианта маршрутизации

### Вариант A. Всё через веб-приложение (проще, рекомендуется)

Next.js сам проксирует `/api/v1` на внутренний API (rewrite в `apps/web/next.config.ts`).
Для прокси заказчика внешне это **один сервис** — один upstream, один сертификат.

```
Клиент → nginx-proxy → web:3000 ─┬─ отдаёт интерфейс
                                 └─ /api/v1/* → api:4000 (внутренний rewrite)
```

**Плюсы:** cookies с `SameSite=Lax` работают без CORS; одна точка входа; API не виден извне.
**Минус:** API доступен только через веб-приложение.

**Конфигурация в прокси заказчика:**

```nginx
upstream repair_web {
    server <IP_LXC_ИЛИ_ХОСТА>:3000;
    keepalive 32;
}

server {
    listen 443 ssl;
    http2 on;
    server_name repair.remixgold.ru;

    # Сертификаты уже обслуживает ваш прокси — путь подставьте свой.
    ssl_certificate     /etc/nginx/certs/remixgold.ru/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/remixgold.ru/privkey.pem;

    # Ограничение размера загрузки: фото изделий с телефона.
    client_max_body_size 25m;

    # Проверка живости — без записи в лог, чтобы не засорять его.
    location = /health/live {
        access_log off;
        proxy_pass http://repair_web/health/live;
    }

    # Нагрузочный лимит даёт приложение (Throttler), здесь — только грубая защита.
    location /api/v1/auth/login {
        limit_req zone=repair_login burst=5 nodelay;
        proxy_pass http://repair_web;
        include /etc/nginx/repair_proxy_params;
    }

    location / {
        proxy_pass http://repair_web;
        include /etc/nginx/repair_proxy_params;
    }
}

# Зона лимита объявляется в http-блоке основного конфига:
#   limit_req_zone $binary_remote_addr zone=repair_login:10m rate=10r/m;
```

### Вариант B. Раздельные хосты для веб и API

Применяйте, если нужен доступ к API извне (мобильные клиенты, внешние интеграции)
или если политика требует разделить сервисы.

```
repair.remixgold.ru      → web:3000
api.repair.remixgold.ru  → api:4000
```

При этом варианте **обязательно** учесть два момента:

1. **CORS.** `APP_URL` в `.env` должен указывать на веб-домен, и API разрешает только
   его. Cookie между доменами потребуют `SameSite=None; Secure` — это ослабление защиты
   от CSRF, поэтому вариант A предпочтительнее.
2. **Rate limit на входе** должен видеть реальный IP клиента. Обязательно настройте
   `TRUST_PROXY` (см. §4) и передавайте заголовки — иначе все клиенты будут выглядеть
   одним адресом.

## 3. Обязательные заголовки проксирования

Приложению нужны заголовки `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`,
`X-Request-Id`. Готовый файл — `repair_proxy_params`; положите его рядом с конфигом
прокси и подключайте через `include`.

```nginx
proxy_http_version 1.1;
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
# request_id связывает запрос клиента с записями в логах приложения.
proxy_set_header X-Request-Id $http_x_request_id;
proxy_set_header Connection "";
proxy_connect_timeout 5s;
proxy_send_timeout 60s;
proxy_read_timeout 60s;
```

**`X-Forwarded-Proto: https` обязателен.** Без него приложение считает соединение
небезопасным, и cookies с флагом `Secure` (а у нас именно такие для токенов)
браузер не сохранит — пользователь не сможет войти.

## 4. `TRUST_PROXY` — критично для защиты от брутфорса

В `apps/api` включено ограничение частоты запросов (Throttler). Стоя за прокси,
API без правильной настройки видит **IP прокси**, а не клиента. Тогда:

> несколько неудачных попыток входа **одним** сотрудником заблокируют вход
> **всей сети**, потому что для приложения все клиенты — один адрес.

Поэтому в `.env` задаётся:

```bash
TRUST_PROXY=1   # доверяем одному хопу — внешнему nginx-proxy
```

Не ставьте `TRUST_PROXY=true` (доверять всей цепочке): тогда клиент сможет подделать
свой IP заголовком `X-Forwarded-For` и обойти ограничение. Если между прокси и
приложением есть ещё один слой (например, HAProxy), увеличьте значение до числа хопов.

## 5. Сертификаты

Сертификаты, их продление и HSTS — **зона ответственности существующего прокси**.
Проект их не запрашивает и не хранит.

Ответ A1: маршрутизация настраивается **через UI**, поэтому сертификат обычно
выпускается там же, одной кнопкой (`Request a new SSL Certificate` → Let's Encrypt).
Осталось уточнить у администратора:

- выпускается ли один wildcard-сертификат `*.remixgold.ru` (удобнее — не нужно
  трогать прокси при добавлении сервисов) или отдельный на поддомен;
- требуется ли открывать 80-й порт наружу для HTTP-01, или сертификат загружается
  вручную (DNS-01).

## 6. Проверка после настройки

```bash
# 1. Приложение живо внутри хоста
curl -fsS http://localhost:3000/        >/dev/null && echo "web OK"
curl -fsS http://localhost:4000/health/live && echo "api OK"

# 2. Готовность — проверяет доступность ВНЕШНЕЙ БД (важнее всего)
curl -fsS http://localhost:4000/health/ready && echo "БД доступна"

# 3. Маршрутизация снаружи: сертификат валиден, ответ 200
curl -fsS -o /dev/null -w '%{http_code}\n' https://repair.remixgold.ru/

# 4. Реальный IP доходит до приложения: в ответе не должно быть адреса прокси
#    (проверяется по логам API — поле req.remoteAddress при уровне LOG_LEVEL=debug)

# 5. Cookie с Secure сохраняются: вход выполняется, сессия не теряется
```

> **Шаг 4 нельзя пропускать.** Если `TRUST_PROXY` настроен неверно, внешне всё работает,
> но ограничение частоты запросов на входе считает всех клиентов одним адресом —
> и несколько неудачных попыток одного сотрудника блокируют вход всей сети.

> **Проверьте загрузку файла.** В Nginx Proxy Manager `client_max_body_size` по умолчанию
> 1 МБ: фотография изделия с телефона не загрузится (ошибка 413). Лимит нужно поднять
> до 25 МБ — поле «Custom Nginx Configuration», см. `docs/14-deployment.md` §8.1.
