# CRM управления и контроля операций ремонта ювелирных изделий

Система для ювелирного сервисного центра: единая база заказов, контроль сроков на каждом
этапе, фиксация согласований с клиентом (включая записи звонков), контроль предоплат и оплат,
отчётность по загрузке, срокам и выручке.

> **Текущий статус: сквозной сценарий приёма заказа работает.** Ответы заказчика на
> блокирующие вопросы получены (`docs/00-decisions.md` §1.1). Реализация ведётся
> по плану из `docs/09-roadmap.md`. Доменное ядро (статусы, права, деньги,
> сроки, номера и QR-коды) реализовано и покрыто **97 тестами**. Система развёрнута
> в LXC и доступна по HTTPS (`https://repair.remixgold.ru/`,
> `infra/db/deployment-report.md`).
>
> Реализовано и проверено фактическим запуском: вход и сессии, ролевой доступ с
> изоляцией магазинов, список и карточка заказа, перевод статусов по матрице
> переходов, глобальный поиск, дашборд, справочники (магазины, цеха, категории,
> камни, прейскурант), клиенты с нормализацией телефона, платежи с идемпотентностью
> и сторно, а также **мастер создания заказа из 5 шагов** (клиент → согласие →
> изделие → работы → итог) с расчётом суммы доменными функциями.
>
> Отложено по решению заказчика: интеграция с 1С и IP-АТС (`docs/05-integrations.md`).
> В работе: печать квитанции с QR-кодом, логистика и партии, отчётность, гарантия
> и рекламации.

## Быстрый старт

### Требования

| Компонент | Версия | Обязателен |
|-----------|--------|-----------|
| Node.js | ≥ 20 (проверено на 26) | да |
| npm | ≥ 10 | да |
| Docker + Docker Compose | любая актуальная | **нет** — есть способ без Docker |
| PostgreSQL | 16 | **в продакшне — существующий сервер предприятия** |
| Redis | 7 | пока не используется в коде |

### Важно про базу данных

**В продакшне PostgreSQL — существующий сервер предприятия (ответ A1):** проект его
**не устанавливает** и не поднимает в Docker, а использует уже настроенный PostgreSQL 16.
БД общая с 1С и другими системами, поэтому подготовка базы, права роли, расширения и
бюджет соединений согласуются с администратором БД:

```bash
# Подготовка БД (выполняет администратор): infra/db/README.md §1
# Проверка готовности перед развёртыванием:
export DATABASE_URL="postgresql://repair_app:<пароль>@pg-server.remixgold.ru:5432/repair"
./infra/db/preflight.sh
```

**Локально для разработки** есть два пути: PostgreSQL из npm-пакета без Docker
(`npm run local:setup` — рекомендуется) или контейнер (`npm run infra:up`). В обоих случаях
разработчику не нужен доступ к продовой базе.

### Установка

Есть два способа поднять локальную среду. Выбирайте по наличию Docker.

#### Способ А. Без Docker (проще, ничего не устанавливается в систему)

```bash
npm install
npm run local:setup   # поднимает PostgreSQL 16.14, создаёт .env, применяет схему и seed
npm run dev           # API + веб
```

`local:setup` поднимает **настоящий PostgreSQL 16.14** из npm-пакета
(`scripts/local-db.mjs`): бинарники лежат в `node_modules`, данные — в `.local/postgres`,
права root не нужны. Версия совпадает с продакшном, поэтому поведение БД и сортировка
русских ФИО такие же, как на сервере.

```bash
npm run local:db:status   # состояние локальной БД
npm run local:db:stop     # остановить
npm run local:db:reset    # удалить данные и создать заново
```

#### Способ Б. Через Docker (полный набор сервисов)

```bash
npm install
cp .env.example .env      # замените JWT_*_SECRET и CSRF_SECRET
npm run infra:up          # PostgreSQL, Redis, MinIO, Mailhog
npm run db:migrate
npm run db:seed
npm run dev
```

MinIO: http://localhost:9001 (minioadmin/minioadmin) · Mailhog: http://localhost:8025

> **Про `npm run db:generate`.** Отдельной командой его выполнять не нужно:
> `npm install` вызывает `scripts/postinstall.mjs`, который генерирует Prisma
> Client автоматически. Шаг нужен только после установки с `--omit=dev`, когда
> Prisma CLI не ставится, — скрипт в этом случае предупредит и пропустит
> генерацию, не роняя установку.

#### Адреса после запуска

| Сервис | Адрес |
|--------|-------|
| Веб-интерфейс | http://localhost:3000 |
| API | http://localhost:4000/api/v1 |
| Swagger | http://localhost:4000/api/docs |
| Проверка живости | http://localhost:4000/health/live |
| Готовность (проверяет БД) | http://localhost:4000/health/ready |

**Вход после seed:** `receiver1@remixgold.ru` или `admin@remixgold.ru`, пароль
`DemoPassword123`. Полный список из 9 учётных записей печатает сам seed.

> **Redis и S3 в текущей реализации не используются** — модули интеграций ещё не
> написаны. Для запуска достаточно PostgreSQL. Переменные `REDIS_URL`, `S3_*`
> обязательны в конфигурации, но соединение не устанавливается.

## Структура проекта

```
├── apps/
│   ├── api/          NestJS — REST API, доменные сервисы, воркеры
│   └── web/          Next.js — PWA для сотрудников + публичные страницы

│   ├── db/           Prisma schema, миграции, seed
│   └── shared/       Доменное ядро: статусы, права, деньги, даты, Zod-схемы
├── docs/             Проектная документация — начните отсюда
├── infra/
│   ├── docker/       docker-compose для разработки и продакшна
│   └── backup/       Скрипты резервного копирования и учебного восстановления
└── .github/workflows CI: линт, типы, тесты, миграции, сборка, безопасность
```

**Ключевой принцип:** `packages/shared` — единый источник правды по домену.
Статусная модель, матрица прав и схемы валидации используются и бэкендом, и фронтендом,
поэтому правила не могут разойтись между ними.

## Ключевые проектные решения

1. **Мастер-ювелир — не пользователь системы.** По решению заказчика исполнитель производства
   учитывается как справочная запись (`Performer`), а все взаимодействия с производством ведёт
   менеджер обработки поступающих ремонтов. Подробнее: `docs/00-decisions.md` §2.
2. **Цена фиксируется в момент приёма.** Прейскурант версионируется, в заказ копируется цена
   и ссылка на версию. Пересмотр цен не меняет принятые заказы (ТЗ п. 2.2).
   **Цена зависит от металла сданного изделия:** утверждённый прейскурант задаёт отдельные
   цены по золоту и серебру, а сервер проверяет присланную цену и отклоняет расхождение
   (`409 PRICE_MISMATCH`). Подробнее: ADR 0009, `docs/03` §3.3.1.
3. **Деньги — только целые числа** в копейках. `Float` для денег запрещён.
4. **Статус — конечный автомат** с явной таблицей переходов и guard-условиями.
   Валидация только на сервере, UI получает список доступных действий от API.
5. **1С не блокирует приём оплаты.** Платежи пишутся в БД и в transactional outbox;
   синхронизация выполняется воркером с ретраями. 1С может быть выключена — магазин работает.
6. **Разграничение по магазинам:** приёмщик видит свои заказы + глобальный поиск по точному
   номеру (нужно для приёма оплаты в чужой точке). Ответ на вопрос 4 ТЗ.
7. **PWA вместо нативного приложения.** Решение заказчика; один код, работа с телефона,
   фото с камеры, установка на домашний экран.

## Разработка

### Полезные команды

```bash
npm run dev:api        # только API
npm run dev:web        # только веб
npm run db:studio      # Prisma Studio — просмотр данных
npm run db:reset       # пересоздать БД и залить seed
npm run infra:logs     # логи инфраструктуры
npm test               # тесты
npm run typecheck      # типы
```

### Соглашения

- **Коммиты:** Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`).
- **Ветки:** `main` (продакшн) ← `develop` ← `feature/<краткое-имя>`.
- **Бизнес-значения не хардкодятся** — нормативы, шаблоны, форматы номеров и лимиты
  живут в БД или переменных окружения.
- **Изменение статусной модели** требует одновременного обновления
  `docs/04-status-workflow.md` и теста `docs-sync` — иначе CI упадёт.
- **Прямая загрузка заказа по `id` без scope-фильтра запрещена** — защита от IDOR.

### Перед коммитом

```bash
npm run lint && npm run typecheck && npm test
```
